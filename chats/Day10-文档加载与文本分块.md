# Day 10：文档加载与文本分块

**今天的目标：**把 TXT、Markdown、PDF、Word 等不同来源转成统一、可追溯的文本记录，并理解切分会影响后续检索。

## 1. 文档加载：从文件得到文本

文档加载（loader）是读取文件并提取文字的步骤。不同格式的文件内部结构不同：TXT 通常是纯文字；Markdown 有标题和列表标记；Word 有段落、表格等结构；PDF 保存的是页面布局，扫描 PDF 可能只有图片。

因此，提取出来的文字不一定等于原文结构：

- 扫描件通常需要 OCR（光学字符识别：从图像猜测文字），可能有识别错误。
- PDF 双栏内容可能被按错误顺序读出；页眉、页脚会重复混入正文。
- 表格可能被压成难以理解的一串文字。
- 文件名后缀只是标签，不证明文件真实类型、安全或可正确解析。

初学时用本地小样本文档，不必安装云服务或调用外部 API。每条加载结果至少保留：

```json
{
  "text": "退款申请需在购买后七天内提出。",
  "source": "退货说明.md",
  "title": "退款期限",
  "page": null,
  "status": "parsed"
}
```

`source`（来源）和 `page`（页码）等元数据（描述数据的数据）让后面可以说明内容来自哪里。Markdown 可以保留标题；PDF 可记录页码；格式不支持时应记录失败状态，而不是悄悄略过。

可以把统一记录理解为“内容和来源贴在一起的信封”。如果只留下 `text`，以后看到“七天内申请”却不知道来自哪份说明，就无法给出可靠出处；如果来源在解析后丢失，生成阶段通常也无法凭空恢复。一个文件切出多个块时，每块都要带自己的来源信息，而不是只在整份文件上保存一次。

## 2. 分块：为什么要把长文拆开

Chunk（文本块/片段）是从较长文档中切出的较小文本。模型输入长度有限；检索一整本手册也容易把无关内容一并带进来，所以需要切块。

切得太大：一个块里主题太多，检索可能带来大量噪声。切得太小：一句定义和它的条件可能被拆开，答案失去必要上下文。Overlap（重叠）让相邻片段共享一小段内容，减少边界处的事实被切断；但会增加重复存储和检索结果重复。

最简单的字符切分示范：

```python
def split_text(text: str, size: int, overlap: int) -> list[str]:
    if size <= 0 or overlap < 0 or overlap >= size:
        raise ValueError("需要 size > overlap >= 0")
    step = size - overlap
    return [text[start:start + size] for start in range(0, len(text), step)]

print(split_text("ABCDEFGHIJ", size=4, overlap=1))
```

输出：`['ABCD', 'DEFG', 'GHIJ']`。这个代码只是帮助看懂边界；真实资料通常优先按标题、段落或句子切分，再对超长段落限长。记录 chunk 的来源、序号、标题和稳定 ID，才能定位和更新。

按字符切分还有一个容易忽略的点：中文、英文单词和代码的“字符数”不等于语义长度。把“申请条件”和“例外情况”拆开，可能令每块都不完整。实践时先按段落/标题分，再将过长段落二次切分；例如保留标题 `"退款条件"` 作为块的 metadata，即使正文切开，读到片段时仍知道它讨论哪个主题。

遇到表格时也不要随意把每个单元格拆成孤立数字。`期限 | 7 天` 若被切成两个片段，数字就失去列名。初学样例可以先把表格转换为易读行，例如 `"退款期限：7 天"`，并保留原文件定位；真实系统则应测试解析器是否保留表头和行关系。

## 3.1 来源坐标与稳定片段

如果 PDF 有页码，片段可带 `page=4`；如果是 Markdown，则可带标题路径，例如 `["退货", "退款期限"]`。引用界面显示“退货说明.md，第 4 页”或“退货说明.md / 退款期限”，比显示“片段 2”更方便读者核查。来源坐标也要在切分后复制到每个 chunk，否则多个段落混到索引里就难以知道哪段来自哪里。

稳定 chunk ID 可以由文档 ID 和片段位置/内容版本组合形成。不要只用列表当前下标作为永久 ID：在文档前面插入一段后，后面所有块的编号可能变化。教学项目先给每个来源一个文档 ID、每块编号并记录版本即可；将来更新策略见 Day 23。

## 3.2 一个加载检查清单

处理文件前先确认允许的类型和大小；处理后检查抽取文本是否为空、是否只剩页眉、标题与段落顺序是否合理；再选择一个句子反查来源。若任一项不符合，就把任务标为待检查或解析失败，而不是继续悄悄建索引。对于扫描 PDF，若没有 OCR 步骤就应明确报告“未提取到可搜索文本”，不要把图片上的字当作已经读过。

这个检查清单不要求把所有格式都一次性支持。一个只支持 Markdown 的可靠小工具，通常比声称支持四种格式、却不识别失败的工具更容易验证。每新增一种格式，都为表格、空文档、特殊字符和损坏文件补充样例。

## 3.3 处理状态和用户反馈示例

可以为加载结果约定一种简单状态：`parsed` 表示已抽取到可检查文字，`empty` 表示文件能打开但没有文本，`unsupported` 表示格式不支持，`parse_error` 表示解析失败。状态不能仅靠猜测，要由加载步骤实际结果决定。举例来说，`.pdf` 文件读取成功但正文为空，应报告需要检查是否为扫描件，而不能伪造一个 `parsed` 状态。

运行结果也应让初学者知道下一步做什么：“文件格式暂不支持，请改用 Markdown 样例”比显示 Python 堆栈更友好；内部记录错误类型则便于开发者定位。练习时分别喂入普通文字、空字符串、随机二进制内容，确保三种情况进入不同状态。这样后续切块只接收有效文本，避免空内容悄悄污染索引。

## 3. 加载安全与失败状态

对用户上传文件，应用还要限制文件大小、数量和允许格式，避免危险路径（例如试图读出上传目录外的文件），并限制解析器耗时/内存。安全校验不能只靠文件名扩展名；要按可信规则检查实际内容和解析结果。不要为了做课程练习而执行文档里嵌入的脚本或宏。

建议定义可读状态，例如 `parsed`、`unsupported_type`、`empty`、`parse_error`。错误日志留在本地开发环境即可；对用户展示清楚的失败原因，但不要泄露机器路径或内部堆栈。

## 常见初学错误

- 以为 PDF 中“看起来清楚”的文字一定能正确抽取。
- 只检查 `.pdf` 后缀，就把文件当作可靠 PDF。
- 用固定字符数切块，却丢掉标题、页码和来源。
- 将 overlap 设得很大，让相邻块几乎重复。
- 解析失败时返回空文本并继续入库，造成“无答案”却无法解释。

## 练习（由浅入深）

1. **热身：统一记录格式。**给一段本地 TXT 文本构造上面的 JSON 记录。验收：文字、来源、状态都存在；TXT 无页码时用 `null`，不要编页码。
2. **跟做：观察分块边界。**运行 `split_text`，分别用 `size=4, overlap=0` 与 `size=4, overlap=1`。预期前者为 `ABCD / EFGH / IJ`，后者为 `ABCD / DEFG / GHIJ`。解释重叠减少边界断裂但增加重复。
3. **独立完成：小型加载清单。**为 TXT、Markdown、PDF、DOCX 样本记录提取文本、来源/页或标题和状态；加入空文件、损坏文件、不支持类型。验收：每个输入都有成功或明确失败状态；至少一个块可追溯到来源；扫描 PDF 明确标注需要 OCR 或无法提取，而不伪造结果。

## 今日验收与复习

- 说清楚不同格式为何可能提取出错，扫描件为何需要 OCR。
- 片段带来源信息，可以定位到文件和页/标题。
- 解析失败、空文件和不支持格式都有明确状态。

**小词典：**Loader＝文件加载/文本提取步骤；Chunk＝用于检索的文本片段；Overlap＝相邻片段共享的文字；OCR＝从图片识别文字；Metadata＝描述来源、页码等属性的数据。
