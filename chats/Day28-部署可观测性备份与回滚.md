# Day 28：部署、可观测性、备份与回滚

**今天的目标：**为服务写一份可执行的上线和故障处理清单，知道出了问题如何发现、解释和恢复。

## 部署不是“把程序放到服务器”

部署是把一个确定版本的程序、依赖和配置交给运行环境，并让它可启动、可检查、可更新。上线前要约定版本号、配置来源、超时、并发上限、限流和回滚目标。**超时**限制一次等待多久；**限流**限制单位时间接受多少请求，保护自身和模型供应商。不同环境（本机/测试/线上）的密钥必须分开管理。

上线前检查清单：

- 固定依赖和版本；配置从运行环境读取，秘密不写入仓库或镜像。
- `/health` 或等价探测检查服务基本可用，但不返回密钥、用户数据或内部堆栈。
- 为模型请求设置连接/总超时、并发上限和重试策略；带副作用的请求不能盲目重试。
- 限制请求大小、速率、任务队列长度和单日费用；达到上限时给出有用提示。
- 发布前保存已知可用版本、数据库/索引备份和恢复说明；演练如何切回。

## 日志、指标、告警是什么

**日志**记录某个请求发生了什么；**指标**把很多请求汇总成数字；**告警**是在数字越界时通知人。可为每次请求生成随机的 `request_id`，串联“接收、检索、模型调用、返回”各阶段，而不用把完整用户问题写日志。

常用指标：请求数、错误率、延迟分位数、队列积压、每请求 token 与费用。**P95 延迟**表示 95% 请求不超过的耗时，不是平均值；它能暴露少数很慢的请求。日志应记录阶段、状态码、错误类别和耗时，并脱敏输入、密钥、个人信息。

将错误分开处理：

- **429 限流：**服务/供应商暂时拒绝过快请求。记录请求 ID、等待时间提示和重试次数；对可重试读请求使用有上限的退避，不能无限重试。
- **自身 5xx：**应用内部错误。记录错误类别和关联 ID，告警后检查最近发布、依赖和资源。
- **供应商 5xx/超时：**外部暂时不可用。记录供应商、耗时、阶段；按策略有限重试或降级，不要返回伪造答案。
- **输入错误 4xx：**通常是客户端参数问题，不应当作服务故障反复重试。

示例告警（阈值要结合基线调整，下面是练习用起点）：

```text
若 5 分钟窗口中 5xx 比例 > 5%，且至少有 20 个请求 -> 通知维护者
若 P95 延迟 > 3 秒，连续 3 个窗口 -> 检查队列和外部依赖
若单日模型预算使用 > 80% -> 提醒；达到预算上限 -> 暂停或降级
```

## 备份与回滚

备份文件存在，不代表能恢复。**恢复演练**是在隔离环境中实际恢复数据，再验证应用可读取、权限正确、数量/校验和合理。还需知道备份频率、保留多久、谁能访问、恢复要多久。**回滚**是把应用或数据恢复到已知可用版本；不能依赖事故发生后从头训练模型。

无 GPU 时，可以使用本地 Mock 完成开发与测试，或选择满足隐私、预算、延迟要求的托管 API；不需要为了练习购买 GPU。自托管推理（例如 vLLM）需要合适硬件、部署与监控能力，是否选择应由吞吐、数据要求和总成本决定，而非“听起来更专业”。

## 常见误区

- 把“重试一次”写进所有异常分支；请求是否安全重放，要看错误类型和副作用。
- 把“日志越多越好”当作可观测性：秘密与个人数据也会被永久复制。
- 只看平均延迟，忽略 P95/P99 的慢请求。
- 429、输入错误、供应商故障和自身 5xx 用同一个“失败”处理。
- 有备份但未做恢复测试；有旧镜像却没演练回切。
- 服务暂时坏了就无限重试，造成费用、拥塞或重复副作用。

## 深入理解：从一个请求追踪到故障原因

请求 ID 是一个随机、无个人含义的标识，可在接收、排队、检索、模型调用和响应日志中重复出现。运维人员用它拼出单个请求的时间线，而不是把完整问题和答案复制进日志。例如：

```text
request_id=r-8f2 stage=accepted status=202
request_id=r-8f2 stage=retrieval duration_ms=84 result_count=4
request_id=r-8f2 stage=model duration_ms=2300 status=429 retry_after=2
request_id=r-8f2 stage=response status=503 error=provider_rate_limited
```

这些字段能说明请求在哪一段变慢/失败、检索到几条结果、是否收到重试提示；其中不应包含密钥、邮箱或完整用户原文。为避免日志被滥用，限制可访问者和保留时间；需要调试内容时，先确认授权并使用脱敏样本。

指标要同时带“数值”和“统计范围”。“错误率 5%”若不说明过去 5 分钟、最少请求数、统计哪些状态码，就可能在只有一个请求的情况下触发误报。可以先在本地 Mock 中制造 100 个成功响应和 6 个失败响应，验证 5xx 比例为 6%，再检查告警是否触发。延迟分位数也需要足够样本；低流量系统可结合绝对耗时和人工探测，而不是把几个请求的 P95 当作稳定基线。

## 如何把重试和降级落到规则

有限重试应包含最大次数、总等待上限和退避，例如最多 2 次，间隔 1 秒、2 秒，并尊重供应商给出的 `Retry-After`。随机抖动（在等待时间上加随机量）可避免多个实例同时重试造成“惊群”。输入错误和鉴权错误通常不重试；429 可排队或有限等待；外部 5xx 可对幂等读请求短暂重试。写入、发邮件、扣款等非幂等操作，先查操作状态或使用幂等键。

降级必须定义“还能安全提供什么”。例如模型故障时返回已缓存的静态帮助链接，或清楚告知暂时无法回答；不能静默切换到未经验证的模型，也不能把没有证据的猜测当作答案。给每一种降级设置开关和结束条件，服务恢复后通过健康检查与小流量试运行再恢复正常路径。

## 备份演练的验收

选一份虚构数据做演习：记录备份时间和版本，在隔离目录/服务中还原，运行读取测试，核对记录条数或校验和，并确认访问权限仍正确。记录实际恢复用了多久、缺了哪些依赖、操作步骤是否够清晰。恢复失败就更新流程并重做；“文件复制完成”的截图不是恢复证明。还应分别明确恢复点目标（最多能接受丢失多久的数据）和恢复时间目标（业务最多能停多久），据此决定备份频率和方案。

## 动手练习

1. **热身：**给 429、输入 400、应用 500、供应商超时分别选一个日志字段和用户提示。验收：不记录秘密，且能区分责任边界。
2. **引导：**写一页部署清单，至少含健康检查、超时、费用上限、脱敏、告警、备份恢复与回滚。验收：每条都有责任人或可检查动作。
3. **独立：**用虚构的 429 和 5xx 事件定义告警阈值、排查步骤和降级行为。验收：阈值有时间窗/条件；说明无 GPU 方案及取舍。

## 复习与词汇

- **复习：**从未恢复验证的备份不能证明系统可恢复，因为文件可能损坏、缺失依赖或无法被应用读取。
- **退避：**重试之间逐渐等待；**分位数：**排序后某百分比位置的值；**回滚：**恢复到先前可用版本。
