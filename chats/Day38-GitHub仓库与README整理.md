# Day 38：GitHub 仓库与 README 整理

**今天的目标：**让不认识你的开发者能判断项目是否适合自己，并按说明安全地运行 Mock 版本和测试。

## README 是使用说明，不是宣传页

GitHub 仓库是代码、文档和变更历史的集合；README 是进入仓库后的第一份指南。陌生开发者应能快速回答：项目解决什么问题、怎么运行、需要什么环境、如何测试、哪些部分只是演示、数据保存在哪。

README 建议按这个顺序写：

1. 一句话用途、项目状态和非目标。
2. 架构图或简短数据流（输入→检索/模型→输出）。
3. 环境依赖与版本。
4. 安装、配置、启动、测试命令。
5. Mock/本地模式与示例输入输出。
6. 数据/日志存放位置及清理步骤。
7. 隐私、许可证、网络/硬件/费用要求和已知限制。

变量写成名称而不是秘密，例如 `MODEL_API_KEY=请自行设置`；同时提供没有真实值的 `.env.example`。`.gitignore` 防止后续追踪 `.env`，但不能保证过去提交过的秘密消失。

## 秘密、数据和许可证

公开仓库中出现密钥后，即使删除文件，历史提交、fork、缓存或截图仍可能保留。正确处理是立即撤销/轮换密钥，再检查使用记录和历史；不要把“删除文件”当成修复完成。

数据、代码、模型权重和截图可能各自适用不同许可证。确认有权分享和使用；示例资料应使用虚构或明确获准的数据。日志和截图要检查姓名、邮箱、令牌、内部 URL 和真实问题。若仓库公开，按最坏情况判断任何内容都可能被复制。

## 干净环境验证

**干净环境**是没有作者私有 `.env`、缓存文件和本地依赖巧合的环境。按 README 从头开始，在新目录/新虚拟环境中执行克隆、安装、Mock 启动、测试。命令需要按顺序有效，依赖版本要明确，错误要能定位。不要只在自己已经配置好的电脑上“确认能跑”。

## Worked example：检查一条说明

模糊写法：“运行项目：`python app.py`。”

清楚写法应补足前提和结果，例如：“使用 Python 3.12；在仓库根目录安装依赖 `pip install -r requirements.txt`，复制 `.env.example` 为 `.env`（Mock 模式无需填写真实密钥），运行 `python app.py --mock`；访问 `http://127.0.0.1:8000/health` 预期得到 `{"status":"ok"}`；运行 `pytest` 执行测试。”命令必须与你真实项目一致，不能为了看起来完整而虚构。

## 常见错误

- 把“我按这些步骤试过”写成事实，但其实没有在没有缓存/凭据的环境运行过。
- README 只有功能介绍，没有启动、测试和清理步骤。
- 依赖“我电脑上已经有”的数据库、密钥或模型缓存。
- 误把代码许可证覆盖到数据/模型权重，或忽略来源许可。
- `.env` 被删除但没有轮换泄漏凭据。
- 示例截图/日志包含真实用户数据。

## 深入理解：陌生人第一次打开仓库会经历什么

读者通常先想知道“这个项目是做什么的、我能不能运行”。README 第一屏因此要有简短说明、成熟度（练习/原型/生产）和最小运行入口。接着用简短数据流说明模块关系，例如“上传文档→解析→切块→检索→带引用回答”。结构图若不能帮助读者理解，可以用几行文字代替，不必为了美观堆复杂图表。

每条运行命令都应配前置条件和预期结果。例如：

```text
前置条件：Python 3.12；仅使用 Mock，不需要云账户
安装：python -m venv .venv
启动：python app.py --mock
检查：访问 http://127.0.0.1:8000/health
预期：{"status":"ok"}
测试：pytest
```

命令要根据项目真实脚本校正。对 Windows 用户，明确 PowerShell 的激活方式或提供不需激活的解释器路径；对 macOS/Linux 用户也写清对应步骤。常见错误和清理指令也很重要：说明本地数据放在哪、如何删除测试数据、删除卷是否会丢失内容。这样读者不会把练习记录误当成要永久保存的数据库。

## 检查依赖、秘密与授权的具体方法

依赖文件需要能从空环境安装；若依赖版本范围过宽，可固定已验证版本或说明兼容范围。数据样例要确认来源和分享许可，不因为代码使用开源许可证就默认所有权重与数据同样开放。截图要放大检查，不仅看主要窗口，也看地址栏、状态栏、终端输出和浏览器自动填充内容。

密钥检查分为当前目录与历史两部分。当前文件中搜索常见令牌前缀、`API_KEY`、密码字段，检查 `.env` 是否被 Git 跟踪；但代码搜索不能证明历史没泄露。若确定曾提交，立刻在供应商处撤销或轮换，然后按组织流程评估历史清理和影响；强制改写历史也不能撤回已被克隆的副本。

## 小项目仓库的建议结构

```text
project/
  README.md
  requirements.txt
  .env.example
  .gitignore
  app/
  tests/
  data/README.md   # 解释数据来源，不提交私有文件
```

结构只是示意，按项目规模调整。`.env.example` 列出变量名和说明，不放默认秘密；`data/README.md` 可以说明如何获得获准使用的样例，而不是提交真实用户资料。测试失败时给出清楚诊断，避免读者误以为模型服务出错。

## 动手练习

1. **热身：**仅根据项目目录写出用途、环境和一条最小运行命令。验收：清楚标出尚未验证的内容。
2. **引导：**为项目写 README 初稿，包括依赖、配置、Mock、测试、数据位置、限制和授权。验收：每条命令都在项目实际存在，变量不含秘密。
3. **独立：**在干净目录照文档重跑，并审查当前文件、历史、日志和截图。验收：无需私有本机配置；仓库无真实凭据/未授权资料；曾泄漏的凭据已轮换。

## 复习与词汇

- **复习：**密钥虽从当前文件删除、却未轮换时风险仍未解除，因为旧值可能仍在历史或被他人复制。
- **版本控制：**记录文件随时间变化的系统；**许可证：**规定允许如何使用/分发内容的条件；**可复现：**按文档在不同干净环境重做得到预期结果。
