# Day 13：RAG 实现与个人笔记助手

**今天的目标：**把本地笔记变成可检索的问答资料，并做好引用、重复导入、更新和删除。全程用虚构 Markdown 文件和本地/模拟检索即可。

## 1. 一次问答如何经过 RAG

RAG（检索增强生成）的在线步骤是：

1. 接收用户问题和当前身份。
2. 从索引中找候选笔记片段。
3. 检查权限与相关性，去掉不能访问或明显无关的片段。
4. 将保留的证据和问题组成上下文。
5. 生成带来源的回答；证据不足时明确说资料里没有找到依据。

为什么要分开看检索和生成？如果正确笔记没被找出来，模型就看不到它；如果候选正确、回答却引用错误，问题才更可能在上下文组装或生成阶段。检查日志时至少保留问题、候选 ID、来源、过滤原因和回答（遵循数据最小化，不记录不必要的个人信息）。

## 2. 文档身份、稳定 ID 与更新

个人笔记助手不能只“不断追加”。需要识别一份笔记：

- **文档 ID：**标识来源文件，例如相对路径或应用生成的 ID。
- **内容哈希：**用文件内容计算出的摘要；内容没变时哈希相同，可跳过无意义重建。
- **Chunk ID：**文档片段的 ID，用于定位、更新和删除。
- **元数据：**标题、来源、修改时间、分块版本等。

稳定 ID 让重复导入时覆盖或跳过旧记录，而不是复制一份。更新时删除该文档的旧 chunk，再写入新 chunk；删除笔记时，索引中的文本、向量和元数据也要清理。真实向量库可能没有跨多步操作的事务（整体成功/失败保证），因此要记录任务状态并让重试安全。

下面演示本地内容哈希：

```python
import hashlib

def content_id(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

print(content_id("# 退款\n七天内可申请")[:12])
```

相同文字会得到相同 ID；任何内容变化通常会得到不同值。哈希只帮助识别内容，不加密文本，也不证明拥有访问权限。

## 3. 把例子走一遍：新增、重复导入、修改、删除

假设有文件 `notes/travel.md`，文档 ID 取其规范化相对路径，内容哈希为 `h1`。第一次导入时，程序读取文件，按标题切成两个片段 `travel-01`、`travel-02`，并保存原文、来源和向量。第二次运行时，如果 ID 和哈希仍相同，就可以报告“内容未变化、跳过”，而不是再追加两个新片段。

如果用户把其中一句改了，哈希变成 `h2`。最容易理解的策略是：在一个明确的替换操作中移除该文档旧版本的所有片段，然后重新解析并写入新版本；完成后再把文档状态标为 `ready`。处理中途失败时，状态应保持为 `failed` 或 `updating`，并记录失败步骤，不能声称新旧版本都完整。较复杂的服务可以用版本号或临时索引降低切换影响，但这是后续优化。

删除则沿着相反方向核对：按文档 ID 找到并移除所有 chunk、向量和元数据，再清除原文件或登记为待清理。完成后用一条原本能命中的问题重新检索，确认旧内容不再出现。这个测试比只看磁盘上文件消失更可靠。

## 4. 引用如何从回答回到原文

把检索结果作为结构化记录传递，比只传一串文字更容易验证：

```python
chunk = {
    "chunk_id": "return-02",
    "document_id": "return-guide",
    "source": "退货说明.md",
    "heading": "退款期限",
    "text": "退款申请需在购买后七天内提出。",
}
print(f"[{chunk['source']} / {chunk['heading']}] {chunk['text']}")
```

这个记录可以形成供模型阅读的证据，也可以作为界面引用的来源。模型回答“七天内”之后，应用仍应核实所附来源确实包含这个期限。引用应由应用使用检索到的 `document_id`、`chunk_id` 生成；模型自己写出的文件名不是数据库查询结果，不能当成证据。

本地笔记助手还需要明确它能读哪些目录。练习阶段限定在课程样例目录；不要为了省事递归读取整个用户主目录。若未来支持多用户，每条记录都应与可信身份权限绑定，并在检索之前过滤，不能只在最终回答里提醒模型保密。

可以把一条片段的生命周期写成可检查清单：`source_path` 指向相对来源，`document_id` 在一次导入中稳定，`content_hash` 用来发现内容变化，`chunk_id` 用来精确定位片段。重新导入时先按文档 ID 找旧版本；哈希相同则跳过，哈希不同则只更新该文档的片段范围。不要只按文本内容删除，因为两份不同笔记可能恰好含有同一句话。

对于失败处理，至少区分“解析失败”“索引写入失败”和“文档已删除但清理尚未完成”。这些状态能帮助重试定位该做哪一步。比如写入向量失败时，不应把文档标记为已完成；恢复后重试前先检查稳定 chunk ID 是否已存在，以免上次部分成功造成重复。练习可用字典模拟这一过程，并打印每步的状态变化。

## 5. 来源与隐私

引用最好显示文件名、标题或页码，并能在本地资料中定位到原文。不要仅引用“第 2 条”这种容易变化的位置。记录笔记保存在何处、何时清理、用户如何删除；若未来扩展为多用户服务，身份和权限隔离应由应用服务端实现。

## 6. 个人助手的最小交互流程

一次本地问答可以按固定步骤显示调试信息：先显示标准化问题，再列出候选片段 ID 和来源，最后显示回答与引用。这样使用者能知道答案不是凭空出现的。学习阶段可以用固定假回答替代模型：若检索到退款说明，就返回“资料记载退款期为七天”；若没有候选，就返回“当前笔记未找到依据”。这仍能验证检索、引用和拒答分支，不需要真实模型。

回答只引用实际传入的证据。若候选片段有 `source=退货说明.md` 和 `heading=退款期限`，界面应根据这份记录展示来源；不要只依赖模型自由输出 `[1]` 再假设它对应第一条。重排或过滤后，候选顺序可能变化，最好一直使用稳定 chunk ID 映射。

## 7. 对“个人”数据也要有边界

本地运行不等于自动安全：程序仍可能扫描不该读取的目录、把内容写进调试日志，或把删除笔记留在索引里。把样例放在专用目录，日志只保留排错所需的 ID 和状态，不保存整段私人文本。删除流程要说明哪些副本会清理、是否有备份或缓存。虚构资料足以完成练习，无需上传真实日记、工作文件或个人资料。

## 常见初学错误

- 只追加新版本，导致旧答案仍从历史 chunk 检索出来。
- 导入相同文件多次，产生重复片段。
- 删除原文件却忘记删除索引副本。
- 引用文件名但没有检查引用文本是否支持该句。
- 把内容哈希说成加密或授权机制。
- 看到相似片段就自动回答，没有“资料不足”出口。

## 练习（由浅入深）

1. **热身：计算稳定 ID。**运行 `content_id` 两次输入相同文本，再改一个字。验收：前两次前 12 位相同，修改后不同；说明哈希不能恢复或保护原文。
2. **跟做：导入虚构笔记。**创建 3 个短 Markdown 笔记（例如退货、项目会议、读书摘录），手写每篇的文档 ID、标题、chunk ID 和来源。验收：针对 3 个问题列出候选来源；答案里能指出文件/标题；找不到依据时拒答。
3. **独立完成：模拟 CRUD 生命周期。**用字典模拟索引，依次重复导入同一笔记、修改一篇、删除一篇。验收：重复导入后记录数不增加；更新后检索结果没有旧文本；删除后文本、向量占位和元数据均不存在；失败状态可定位。

## 今日验收与复习

- 引用能追踪到具体笔记；无依据时明确说明资料不足。
- 重复运行入库流程不会重复增加相同记录。
- 修改和删除会同步更新索引，不跨越未授权范围。

**复习卡片：**若文档已从磁盘删除，索引里的旧 chunk 还存在，会造成什么问题？

**小词典：**内容哈希＝根据内容计算的固定摘要；CRUD＝创建、读取、更新、删除；Chunk ID＝片段标识；幂等＝相同操作重复执行，结果不会不断重复增加。
