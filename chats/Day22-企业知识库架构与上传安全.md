# Day 22：企业知识库架构与上传安全

**今天的目标：**用简单架构图理解企业知识库的数据流，并明确上传校验、用户隔离和删除策略。所有演练使用虚构用户和本地文件。

## 1. 一个知识库由哪些部分组成

企业知识库不只是“模型 + 向量数据库”。典型流程包括：

```text
用户界面 → API/身份认证 → 上传校验 → 原文存储
                                ↓
                     解析与索引任务 → 文档/向量索引
用户问题 → 身份授权 → 权限过滤检索 → 组装证据 → 模型回答
```

- **UI/API：**接收用户操作；API 是程序之间交换请求的入口。
- **身份认证：**判断“是谁在访问”。
- **授权：**判断此用户允许做什么、读取哪些文档。
- **原文存储：**保存上传的源文件。
- **解析与索引：**提取文本、切块、生成向量并记录来源。
- **检索与模型：**找得到权限内的证据后再组织答案。

“认证”不等于“授权”：知道用户是谁，不代表此用户可以访问全部资料。

## 2. 租户隔离必须由可信服务端实施

Tenant（租户）可以理解为企业或彼此隔离的客户空间。用户 A 的问题只应搜索 A 有权访问的文档。身份/租户条件要来自服务端当前登录身份和权限策略，应用在取候选并组装 Prompt 之前过滤。

不能依赖 Prompt 里的“不要回答其他租户内容”，因为模型看到了什么取决于应用送入了什么；如果 B 的文字已经进入上下文，光靠一句要求不是隔离机制。过滤应覆盖候选、缓存和引用；不能让模型自己决定租户 ID。

## 3. 上传文件安全检查

扩展名（如 `.pdf`）只是用户提供的名字，不能单独证明内容类型。可设计多层校验：

1. 限制允许格式、单文件大小、文件数和用户配额。
2. 将文件安全地保存到受控目录，阻止 `../` 等路径穿越。
3. 检查内容是否符合预期格式，并通过受限解析器提取。
4. 对解析时间、内存和页数设限；失败时记录失败状态，不继续当成功索引。
5. 仅保存必要数据，定义谁可访问、何时过期、如何删除。

这些是设计原则，不是完整的上传安全实现；上线前还需按实际平台威胁模型进行测试和审查。

## 4. 把校验设计成明确的检查点

可以给每次上传记录一个任务 ID，并在每个阶段注明结果，而不是用单个“上传成功”覆盖所有情况：

| 检查点 | 示例判断 | 失败结果 |
|---|---|---|
| 请求入口 | 用户已登录且有上传权限 | 拒绝请求 |
| 文件限制 | 大小、数量在上限内 | 返回可理解的限制提示 |
| 路径保存 | 服务端生成文件名，不直接拼接用户路径 | 拒绝危险路径 |
| 内容解析 | 解析器能读出内容且耗时/资源在限额内 | 标记失败，不建索引 |
| 入库权限 | 每个 chunk 绑定正确文档权限 | 不允许进入检索 |

“后缀和内容匹配”不是万能检测：不同格式有自己的结构，上传校验只能降低风险，仍要使用受限解析器并安全处理失败。课程原型可以只接受自己创建的 Markdown，并明确不支持 PDF 等类型。

## 5. 权限测试要检查模型真正看到的内容

创建两份虚构记录：Alice 的 `a.txt` 与 Bob 的 `b.txt`。在测试中假设认证中间件已确认 Alice 身份；检索服务接收这个可信身份，从候选中只留下 Alice 有权读的 chunk。断言不仅检查界面答案，还要检查传给模型的上下文确实没有 `b.txt` 的文字，也不应将 Bob 的标题作为引用返回。

若系统使用缓存，缓存键至少要能区分用户/权限范围，或者在取缓存结果前重新验证权限。否则 Alice 先查出的内容可能被错误复用于 Bob 的请求。具体方案依赖应用架构，关键检查是：权限变化后，旧缓存不能绕开授权。

## 6. 删除不仅是删文件

同一文档可能存在于原文存储、抽取文本、chunk、向量、缓存、日志或备份中。删除规则要列出哪些副本需要立即删除，哪些按有记录的备份保留周期到期清理。课堂项目可以先让原文和本地索引都清理，并明确日志不存正文。

## 7. 用一个上传例子串起规则

假设 Alice 上传名为 `guide.pdf` 的文件。服务端先根据 Alice 的已认证身份检查上传配额，再把内容保存为服务端生成的文档 ID，而不是直接信任这个文件名作为磁盘路径。接着检查允许类型和大小，使用受限解析器读取；成功后每个 chunk 都带有文档 ID 与访问策略，索引任务才可继续。如果解析为空或超时，记录失败状态并停止，不创建看似有效的检索记录。

用户查询时先核对身份和文档 ACL（访问控制规则），检索只使用允许的数据。模型上下文、引用和缓存都继承同一权限范围。若 Alice 失去访问权，后续查询要立即应用新策略；缓存里旧结果也不能绕开检查。

## 8. 为规则设计负向测试

负向测试会故意给系统不该接受的输入，例如：名字伪装成 PDF 的普通文本、超出大小上限的文件、尝试路径穿越的文件名、解析器遇到损坏内容、Alice 查询 Bob 的独有文档。每个场景都应有明确拒绝或失败结果，并确认没有产生索引副本。

测试失败时记录“哪个校验点拦截、文件是否被保存、是否创建 chunk、模型是否被调用”。这比仅断言 HTTP 状态码更能证明数据流安全。课程项目只需用虚构文件和模拟身份，不要拿实际企业文件试验上传边界。

## 常见初学错误

- 以为登录成功就代表可读取所有文件。
- 将租户 ID 直接从用户输入或模型生成结果中采信。
- 只根据文件名后缀判断文件类型和安全性。
- 解析任意大文件，没有资源限制。
- 删除原文件但保留向量、引用缓存或其他可检索副本。

## 练习（由浅入深）

1. **热身：区分认证与授权。**解释“确认用户 A 登录”与“允许 A 读取财务文档”的区别。验收：前者回答是谁，后者回答能做什么。
2. **跟做：画数据流。**画 A/B 上传、索引、查询和删除，标出服务端身份验证和权限过滤位置。验收：权限过滤在构造模型上下文前；模型永远不会收到无权文档。
3. **独立完成：制定上传与隔离测试。**写至少 5 条规则，覆盖大小、类型、路径、解析失败、配额；做 A 查询只能返回 A 文档的测试。验收：加入伪造扩展名、`../` 路径、超大文件和跨租户查询案例；说明原文、文本块、向量和元数据的删除方式。

## 今日验收与复习

- 租户过滤依据可信身份，并发生在 Prompt/模型上下文构造之前。
- 上传规则有可执行检查，解析资源有限。
- 能列出原文、向量和元数据各自的删除处理。

**复习卡片：**为什么“Prompt 说不要回答其他租户的问题”不等于数据隔离？

**小词典：**认证＝确认身份；授权＝检查访问权限；租户＝相互隔离的组织/客户空间；路径穿越＝利用 `../` 等路径读取预期目录之外文件；配额＝限制用户可消耗的资源量。
