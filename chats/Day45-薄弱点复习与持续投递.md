# Day 45：薄弱点复习、持续投递与课程总结

**今天的目标：**把学习转成下一周可持续的复习、作品迭代和求职计划，而非一次性冲刺。

## 如何找出真正薄弱点

薄弱点不是“我觉得什么都不会”，而是从错误记录、项目评审和面试反馈中找出可重复的问题。先闭卷回忆，再做小练习；若能看懂但不能讲清或实现，说明还没掌握到可独立使用。

每个薄弱点至少写：要解决什么、学习材料、闭卷练习、验收标准、复查日期。例如“RAG 评估”可写：不用笔记画出流程；用虚构标注计算 Recall@5；解释它不能衡量什么；一周后重新完成。间隔复习不是每天重复读同一页，而是在间隔一段时间后主动回忆并检测遗忘。

## 下一周计划示例

按可用时间调整，不必照搬：

| 时段 | 工作 | 完成检查 |
|---|---|---|
| 周一 45 分钟 | 闭卷复述 RAG 故障分类 | 能讲清检索/生成区别 |
| 周二 60 分钟 | 为本地 Demo 补 5 条评估问题 | 有输入、预期来源、结果记录 |
| 周三 30 分钟 | 修 README 的干净环境步骤 | 按步骤能重跑 Mock 测试 |
| 周四 45 分钟 | 模拟 2 分钟项目介绍 | 说清本人贡献和限制 |
| 周五 30 分钟 | 筛选 2 个岗位，更新匹配矩阵 | 有证据链接和下一步 |
| 周末 | 缓冲、休息、复查 | 未完成时重新排程，不挤掉休息 |

每周只选 2–3 个优先薄弱点，留出缓冲。计划是帮助持续，不是惩罚；家庭、健康和精力变化时可以缩减任务。

## 持续投递与作品迭代

维护一个简单记录：岗位链接/查看日期、匹配理由、简历版本、投递日期、下一步、反馈。复盘关注“材料能否证明岗位所需能力”“面试反复出现哪些缺口”，而不是只看总投递数。

作品可以小步改进：修复一个复现问题、补一组测试、改进错误提示或解释失败案例。每次改动记录原因与验证。公开作品必须去除秘密、真实用户资料和未授权数据； README 应写清运行限制。目标是展示可信的工作方式，不是假装做过企业级生产系统。

## 常见错误

- 把每个没做过的技术都列为薄弱点，计划无限膨胀，无法区分优先级。
- 把长期待办列表当作学习计划，任务没有具体验收。
- 一直重读笔记，却没有闭卷回忆和动手检查。
- 排满每一天，没有休息或缓冲，稍有延误就放弃。
- 用投递数量衡量能力或价值。
- 只写成功案例，不记录失败与改进证据。

## 深入理解：把“会了”定义得可观察

学习目标若写“掌握 Docker”，没有办法判断何时完成。把它缩小为动作，例如“能解释镜像与容器区别”“能启动一个 Mock API”“能说明卷为什么保留数据”“重建容器后验证数据仍在”。不同目标可分层：认识概念、能跟着示例做、能独立完成、能解释失败与取舍。求职材料通常需要后两层的证据，阅读文档本身只是准备。

闭卷回忆的流程很简单：合上笔记，用纸写出要点或口头讲解；再对照资料标出遗漏和错误；最后做一道应用练习。复查时不要只问“记得吗”，而是改变例子检验是否理解，例如将 RAG 主题换成政策文档，仍能定位故障阶段。若答错，记录具体问题，下次复习先尝试回忆再看答案。

## 周计划要考虑精力和现实限制

安排任务时估算每项所需时间，别把每天都填满。将最重要的一项放在精力较好的时段，留出缓冲处理临时事情；周中若落后，先调整优先级，而不是牺牲睡眠或休息。可以规定“最低完成版”：即使只有 20 分钟，也完成一次闭卷回忆或一个测试，而非因计划不完美就整周放弃。

每周复盘三个问题：哪项证据已经完成？什么阻碍了计划？下周只保留哪些最有价值的目标？对投递，关注岗位是否相关、材料是否展示证据、面试是否出现重复反馈；没有回音也不应自动推断个人能力不足，还要考虑岗位数量、时机与筛选条件。

## 作品迭代示例：每周交付一个小变化

第一周让 Mock API 可以从 README 启动；第二周添加超长输入测试；第三周记录 request ID 和安全错误类别；第四周写一份虚构评测集并展示失败分析。每次变更都用一条测试或复现步骤证明有效，并在 README 中写明当前限制。这样逐步形成可演示的项目，不必一次构建庞大的“企业级系统”。

申请记录可以用简单表格保存：岗位与链接、查看日期、核心匹配点、证据链接、简历版本、投递日期、下一步和反馈摘要。限制记录范围，不保存不必要的私人信息；面试反馈中不记录对方的敏感细节。每周安排固定复盘时段，避免每天不停刷新投递状态。

## 45 天之后的路线

选择一个与你目标岗位相连的作品主题，写清用户问题、最小范围、验收用例、风险和每周里程碑。先完成可以本地运行的版本，再增加鉴权、评估或容器化等能力。若发现岗位方向不合，可根据三份以上公开岗位共同职责调整，而非追逐单一职位的全部技术词。持续记录“做了什么、证据是什么、还有什么限制”，就是下一轮学习的起点。

把作品范围控制在能完成的大小：先为一个清楚的问题准备少量虚构数据，做出一条完整流程；再选一项风险或质量指标验证；最后写运行方式和限制。每次扩展前问“它能证明什么岗位能力、验收怎样判断完成”。如果答案不清楚，先不加新框架或功能。求职期间也应设定每周学习与投递的上限，保护休息时间，避免用忙碌感代替有效进展。

## 动手练习

1. **热身：**从错题/反馈中选出三个薄弱点。验收：每项都有事实依据，不是笼统的“基础差”。
2. **引导：**为每项写学习材料、闭卷练习、验收条件和复查日期。验收：别人能依据标准判断是否完成。
3. **独立：**安排未来一周的复习、作品迭代、岗位筛选和投递复盘。验收：计划与目标岗位相关、留有缓冲/休息；至少能展示一个可复现项目、一份诚实简历和持续改进记录。

## 全程复盘

回顾 45 天：选出最有用的 3 个练习、最需要补的 2 个主题，以及下一阶段要构建的一个作品。为作品写一个小范围验收目标和日期；若项目涉及 API 或 Agent，可分别参考 [Day 35：FastAPI 封装 Agent](Day35-FastAPI封装Agent.md) 与 [Day 38：仓库整理](Day38-GitHub仓库与README整理.md)。

## 复习与词汇

- **间隔复习：**隔一段时间主动回忆，以发现遗忘并巩固；**持续改进记录：**保存问题、行动、证据和复查结果。
- 目标不是一天学完所有内容，而是用可证明、可复现的进步逐步接近目标岗位。
