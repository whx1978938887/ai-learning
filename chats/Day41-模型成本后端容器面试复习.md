# Day 41：面试复习——模型选型、成本、后端与部署

**今天的目标：**从质量、费用、延迟、隐私、可靠性和复杂度共同解释方案，而不是只说“选最强模型”。

## 模型选型要先定义任务

固定一组代表性问题和评分规则，比较候选模型的质量、延迟、费用、隐私要求、可用性和易维护性。基准（benchmark）是用于比较的一组任务和测量规则；没有与你真实需求相近的基准，排行榜名次也不一定适用。

先试低成本、能力够用的选项。失败问题可按需升级到更强模型；但要注意路由和重试本身也增加复杂度。API、模型版本和价格会变化，估算报告应注明日期与假设。

## 一个透明的成本估算

模型费用通常取决于输入和输出 token 数量、模型单价、缓存策略及重试次数。下面单价完全是假设，仅用于练习：

```text
每次平均输入 1,000 tokens，输出 200 tokens
每天 1,000 次；假设输入 $1/百万 tokens，输出 $2/百万 tokens
输入费 = 1,000 × 1,000 × $1 / 1,000,000 = $1/天
输出费 = 1,000 × 200 × $2 / 1,000,000 = $0.40/天
估算合计 = $1.40/天（尚未计入重试、缓存和其他服务）
```

面试中说清调用量、均值/峰值、输入输出 token、使用的价格和预留余量。不要把示例价格当真实当前价格。

## 后端可靠性与错误分类

API 后端需要输入校验、身份/权限、超时、限流、错误分类、请求 ID 和成本监控。能不能重试取决于错误和操作类型：429 可有限等待重试；供应商暂时 5xx 可退避重试；认证错误（401/403）应修配置或权限，不盲目重试；无效输入应修请求；非幂等写入超时要先查状态。

降级（fallback）可以是返回缓存/只读结果、切到经过验证的轻量模型，或明确告知暂不可用。不能降级到无证据猜测或忽略权限。

## Docker 与 Kubernetes 的角色

Docker 镜像把应用及依赖打包，容器是运行实例；health check 检查服务响应。Kubernetes（常称 K8s）用于管理一组机器上的容器、调度和扩缩容。K8s readiness（就绪探针）判断实例是否该接流量；liveness（存活探针）判断是否需要重启。具体语义取决于探针配置。

小型单机项目可以先用 Docker/Compose；团队确实需要多机调度、自愈和扩缩容时再评估 K8s，因为它也带来配置、安全和运维成本。选择工具要匹配规模，而非履历关键词。

## 常见错误

- 把理论 token 估算当精确账单，忽略长尾输入、并发峰值、重试与价格变化。
- 只根据模型排行榜选型，不在目标任务上验证。
- 成本估算没有调用量/价格假设，或漏算输出 token 与重试。
- 所有 HTTP 错误都重试，包括 401、403 和非法请求。
- 小项目先上 Kubernetes，却没有维护能力或扩容需求。
- 认为健康探针能验证回答质量、数据备份或模型安全。

## 深入理解：把模型方案变成选择表

先列任务必须满足的要求，例如回答必须有政策引用、P95 小于 3 秒、单日支出不超过某预算、敏感资料不能离开指定环境。然后为候选方案用同一套测试问题和评分规则收集质量、延迟、费用、可用性和运维复杂度。不能用一个“综合分”掩盖硬约束：若隐私要求不满足，再便宜也不能选；若安全用例失败，平均正确率高也不够。

质量测试要有代表性案例，包括正常问题、边界条件、无资料问题和恶意/越权请求。模型版本、系统提示、温度等参数要记录。线上模型可能改变版本、容量和价格，所以应有定期回归测试、限额和供应商替代计划；切换供应商前确认数据处理约定与输出差异。

## 成本估算的敏感性分析

输入中可能包含系统提示、历史对话和检索片段，因此用户问题短也不一定 token 少。输出长度和重试会让费用增加。用“平均请求”估算后，再计算高峰或长上下文情境，并留出预算余量。例如把平均 token 数翻倍、失败请求重试一次，看看费用是否仍可接受。若计价单位为百万 token，公式为：

```text
月费用 ≈ 每日请求数 × 30 ×
  (平均输入 token × 输入单价 + 平均输出 token × 输出单价)
  / 1,000,000
```

输入/输出单价要分别使用并注明币种和查看日期；还要记缓存折扣、工具成本、日志/存储费用是否纳入。估算值是规划，不是账单保证。上线后对照实际使用，设置硬性配额和高额支出告警。

## 错误分类与重试决策

客户端输入不合法，修正请求后再发；401/403 修复身份或权限，不重复请求；429 可根据等待提示进入队列或限次退避；外部 5xx 对幂等只读请求可有限重试；超时要区分请求是否可能已执行。每次重试都应计入总时限和费用预算，并设置最大次数。返回用户的错误信息要给可操作下一步，例如稍后重试、联系管理员或检查输入，而不是暴露上游堆栈。

## 从容器到集群的判断

单实例 Docker 可解决依赖一致和部署打包；Compose 可让本地多个服务一起启动。Kubernetes 增加调度、滚动发布、健康探针和扩缩能力，但也需要集群权限、网络、存储、监控、升级和故障排查。若一个团队还没有明确的多实例需求、值班和运维能力，先保持简单通常更稳。容器 health check 检查进程/服务端点；K8s readiness 控制该实例是否接新流量，liveness 失败可能触发重启。探针设计过于严格可能导致服务反复重启或所有实例被摘除。

## 动手练习

1. **热身：**列出模型选型的六项维度。验收：包含质量、成本、延迟、隐私、可用性、维护复杂度。
2. **引导：**用上面的公式为 100 次/天和 10,000 次/天各估算一次。验收：列出输入/输出 assumptions、价格来源日期和未计成本。
3. **独立：**为低成本客服设计一次有限重试和降级流程，再解释 Docker health check 与 K8s readiness/liveness 的不同。验收：认证错误不重试；服务故障不伪造答案；部署复杂度与规模相称。

## 复习与词汇

- **复习：**429 时可在有等待时间且有上限时重试；队列适合突发流量；降级适合已准备好安全替代方案的情境。
- **token：**模型处理文本的单位，不完全等同于单词；**限流：**控制单位时间请求数；**readiness/liveness：**分别表示可否接流量/进程是否需重启。
