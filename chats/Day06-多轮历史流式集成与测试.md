# Day 6：多轮历史、流式集成与测试

**今天的目标：**把历史管理接入 CLI，组合流式响应，并为异常路径编写离线测试。

## 知识点

多轮聊天必须把必要历史随请求显式传递。历史太长时制定裁剪规则，保留系统约束和最近相关消息；不能让不同用户共享同一历史。流式解析需要缓存跨块数据、识别事件、处理结束标记和结束时残留内容。可测试性来自可替换模型、假时钟和 Mock，而不是实际等待或付费请求。

### 离线流解析练习规格

可以把解析器设计为 `feed(data: bytes) -> list[event]` 加 `close() -> list[event]`：

- 支持一个输入块包含多条事件，也支持一条事件跨多个输入块。
- 增量 UTF-8 解码；SSE 空行结束事件；多条 `data:` 行按协议拼接。
- `[DONE]` 按服务商约定结束；事件 JSON 错误、UTF-8 错误及连接关闭时残留数据应清楚区分。
- 收集器拼接 `delta.content`，处理缺失 choices 的事件；保存最后一个有效 `finish_reason` 和 usage。
- 若 `finish_reason="length"`，结果须标记可能截断；不要把部分回答默认当完整成功。

生成器只创建一次并可多次 `next()`；调用 generator 函数本身不会立即执行函数体，迭代才会运行到 `yield` 并暂停。测试这一点时，把生成器次数、SSE 事件数和网络读取块数分开统计。

## 两个容易混淆的概念：历史与生成器

模型服务通常不会自动知道你上一次问了什么。一次请求就是一次请求；如果要它参考先前对话，应用需要把必要的旧消息也放进本次 `messages`。可以把它想成每次去新窗口办事都要重新出示需要的材料。历史越长，请求通常越大；用户隐私和不同会话隔离也要考虑。

```text
第一轮：user("我叫小林") → assistant("你好，小林")
第二轮请求需要带上：
  user("我叫小林")
  assistant("你好，小林")
  user("你怎么称呼我？")
```

历史管理要明确：哪些消息保留、最多多少轮或多少 token、怎样裁剪、会话之间是否隔离、是否写入磁盘以及怎样删除。不能把所有人的聊天放在同一个全局列表里，否则会话串线。

Python 生成器（generator）是“可以逐个交付结果、交一个暂停一下”的函数，常用 `yield` 暂停并交出一个值。调用 `yield` 函数时，通常先得到一个生成器对象；开始 `for` 或 `next()` 迭代后，函数体才一步步运行。

```python
def chunks(text: str, size: int):
    if size <= 0:
        raise ValueError("size 必须是正整数")
    for start in range(0, len(text), size):
        yield text[start : start + size]


stream = chunks("你好，AI", 2)  # 这里只创建生成器，尚未交出分块
print(list(stream))            # ['你好', '，A', 'I']
```

这个示例按 Python 字符切片，不是网络字节/SSE 解析器，也不一定等于模型 token。测试时要区分函数被调用、生成器开始迭代、`yield` 交付次数、SSE 事件数和网络读取块数。

### 测试失败路径，不只测成功

单元测试是给程序一组固定输入，检查输出是否符合约定。Mock 模型/响应、假时钟和假 `sleep` 让测试更快、更可重复。先列出“输入—预期”表再写代码：

| 情况 | 预期 |
| --- | --- |
| 完整合法事件 | 提取增量文字 |
| JSON 只到一半 | 暂存，不提前输出 |
| UTF-8 多字节字符被拆开 | 等更多字节后再解码 |
| 遇到结束标记 | 标记完成，不把它当正文 |
| 连接结束但事件不完整 | 明确标记/报错，不伪装完整回答 |

流式时，答案可能已显示一部分才断线。界面需要区分“完整回答”和“中断的部分回答”；若应用选择重试，也要避免把两次内容无提示地拼在一起。

## 分层练习（由易到难）

1. **热身：**运行 `chunks("你好，AI", 2)`，改变 `size` 和输入为空的情况。自测：输出顺序和原文一致；`size=0` 会清楚报错。
2. **跟做：**写两轮 Mock 对话。第二轮检查传给模型的消息包含必要的前文。自测：两个不同 session 的历史不互相出现。
3. **独立挑战：**用 `feed(bytes)` 测试同一块含两条事件、单条事件跨两块、结束时不完整。自测：只在空行后发出 SSE 事件，坏 JSON/坏 UTF-8/未完成事件能分别定位。
4. **故障测试：**分别模拟 401、超时和流断开。自测：401 不重试；超时有明确错误；流断开不被保存为完整成功。

常见错误：只测正常响应；以为调用生成器函数就已经跑完；把 token 数等同 `yield` 次数；流中断仍把部分内容保存成完整 assistant 消息；忘记隔离不同用户的历史。

## 动手练习

1. 实现 `chunk_text(text, chunk_size)` 生成器：正整数校验、保序分块、空输入、中文与非法长度测试；验证创建迭代器时函数体未执行，`next()` 才继续到 `yield`。
2. 用假模型完成两轮对话，验证第二轮包含必要历史。
3. 当历史超过设定上限时，保留系统规则和最近一轮交互，记录被裁剪内容。
4. Mock 成功事件流、401、超时和半截事件；分别断言结果或明确异常。
5. 测试同一 `feed()` 含两条事件、JSON 跨 `feed()`、UTF-8 中文字符跨字节、`[DONE]`、最后 chunk usage 与 `finish_reason="length"`。
6. 对流中断规定策略：不得将未完成答案伪装成完整成功；重试/回退前考虑是否已向用户显示部分内容。

先完成 Day 2 的流式和错误概念，再按本节规格编写离线解析器与集成测试。`feed()` 返回已完整结束的事件；JSON 错误、UTF-8 解码错误和 `close()` 时发现的未完成事件应有清楚且可区分的处理。

## 今日验收

- 错误响应不会被记录成完整的 assistant 回答。
- 每个测试运行不需要网络、密钥或真实 sleep。
- 历史按 session 隔离，裁剪规则可解释且测试覆盖。
- JSON 解析异常和 UTF-8 解码异常不会被静默吞掉。
