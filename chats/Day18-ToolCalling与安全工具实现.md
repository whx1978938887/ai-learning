# Day 18：Tool Calling 与安全工具实现

**今天的目标：**理解模型提出工具调用、应用验证并实际执行的往返过程；实现一个只允许调用白名单函数的本地示例。

## 1. Tool Calling 不是模型直接执行代码

Tool Calling（工具调用）是模型以结构化形式提出“希望调用某个工具”和参数的机制。模型**提出请求**，应用才是执行者：

```text
用户问题 → 模型提出 {工具名, 参数}
         → 应用检查白名单、参数、权限和风险
         → 应用执行受控函数并返回结果
         → 模型根据结果继续回答（或结束）
```

模型提出 `add(a=2,b=3)` 不代表它真的执行了函数，也不意味着参数可信。应用必须解析和验证。绝不能把模型输出直接交给 `eval`、任意 Python、SQL 或 Shell 执行。

Tool schema（工具参数结构说明）能帮助模型按格式提出请求，但 schema 只是输入提示/格式约束，不是授权边界。工具名必须在白名单里，参数必须再由程序校验，用户权限也必须由应用确认。

## 2. 用纯 Python 建立安全边界

下面示例实现只读加法工具。它不依赖模型服务，可以本地运行：

```python
def add(a: int, b: int) -> int:
    return a + b

TOOLS = {"add": add}  # 明确的白名单

def dispatch(name: str, arguments: dict) -> int:
    if name not in TOOLS:
        raise ValueError("未知工具")
    if set(arguments) != {"a", "b"}:
        raise ValueError("参数必须且只能包含 a、b")
    a, b = arguments["a"], arguments["b"]
    # bool 是 int 的子类，故用 type(...) 精确检查。
    if type(a) is not int or type(b) is not int:
        raise ValueError("a 和 b 必须是整数")
    return TOOLS[name](a, b)

print(dispatch("add", {"a": 2, "b": 3}))
```

输出：`5`。未知工具、缺参、多余参数、字符串或小数都应在执行前被拒绝。真实工具可能还要做授权、输入范围限制、超时和审计。

验证“错误输入没有真的执行”时，可用计数器或假工具记录调用次数。将白名单里的 `add` 暂时换成会把调用次数加一的函数；提交字符串或缺参后，检查函数调用次数仍为 0；再提交 `2` 和 `3`，检查结果为 5 且调用次数变成 1。这个检查能证明参数校验发生在执行之前，而不只是程序显示了错误文字。

Schema 可以声明参数类型，但执行函数仍须验证，因为请求也可能来自测试、旧客户端或其他代码路径。若业务只允许正整数，要明确写出范围检查；不要默默把 `"3"` 转成数字后执行，否则调用方不一定知道输入被改变。拒绝不合法输入通常比猜测用户意图更可预测。

## 3. 工具权限与失败处理

**最小权限**意味着工具只获得完成任务所需的最少能力。例如天气工具只读取城市名，不该同时拥有邮箱访问权。区分只读、可逆写入、不可逆/高影响操作。高影响动作（发邮件、删除文件、付款）应在执行前展示具体目标与参数，并等待用户明确确认。

给工具设置有限超时；处理服务不可用、限流、无权限等失败。向用户给出简洁错误，不暴露密钥、内部路径或完整堆栈。对可能重试的写操作考虑幂等性（重复提交不产生重复副作用），例如要求请求 ID。

检索到的文字和工具返回值也都是不可信数据：它们可能含错误、恶意指令或伪造内容。应用不能因为文本写着“授权通过”就跳过权限检查。

错误可分为内部诊断和用户提示两层。内部记录稳定错误码（如 `WEATHER_TIMEOUT`）便于测试；用户只看到“天气查询超时，请稍后重试”。不要把完整异常或密钥返回给模型，让模型自行解释。可以将经过筛选的错误状态交回流程，让助手诚实说明工具暂不可用，而不是伪造天气结果。

如果工具有副作用，最好先把“准备请求”与“提交执行”分成两个函数。比如 `draft_email()` 只返回收件人、主题和正文；`send_email()` 才实际发送。人工确认发生在两者之间，且确认时显示的内容必须与最后执行的参数一致。只读计算器没有这类风险，但同样应限制数字范围，避免输入过大导致无意的资源消耗。

## 4. 用 FakeWeather 验证超时与错误分支

本地天气工具可以不连网络，直接用固定字典模拟：

```python
def fake_weather(city: str) -> dict:
    known = {"Taipei": "rain", "Oslo": "sun"}
    if city not in known:
        return {"ok": False, "error": "UNKNOWN_CITY"}
    return {"ok": True, "forecast": known[city]}

print(fake_weather("Taipei"))
print(fake_weather("Nowhere"))
```

第一条返回成功状态和固定天气，第二条返回明确错误码。真实网络请求的超时通常要在 HTTP 客户端中设置；这个假工具不模拟真实计时，只用于确认应用遇到 `ok=False` 时不会捏造结果。可以再设计一个返回 `TIMEOUT` 的固定分支，并验证最终回答如实提示“查询暂不可用”。

## 5. 权限由调用上下文决定

假设工具是 `read_note(note_id)`，即使模型提供了合法的 `note_id`，应用仍需检查当前用户是否有权读这条笔记。授权输入应来自服务端已经验证的用户上下文，而不是让模型在参数里自行写一个 `owner="alice"`。只有“用户身份 + 文档权限”校验通过后才执行读取，之后返回给模型的内容仍应是最少所需部分。

每个工具调用都可记录工具名、校验是否通过、执行状态和耗时，不记录秘密参数或整段敏感内容。出现未知工具、无权限、参数错误和工具失败时，分别返回可辨认的状态；这样测试能检查失败发生在哪一步，也不会将安全拒绝误认为普通空结果。

一个完整校验顺序可写成：解析请求 → 检查工具名是否在白名单 → 检查参数字段和类型 → 检查业务范围 → 检查当前用户权限 → 执行函数 → 将结果缩减为下游所需信息。顺序很重要：若先执行再校验，错误参数可能已造成副作用；若先信任模型提供的用户标识，授权检查就没有意义。对只读 `add` 可省略用户资源授权，但用于真实数据的读取工具不能省略。

还要思考空值和边界值：空城市名应被拒绝；城市字符串过长可限制长度；计算器参数若要求整数，就说明是否允许负数和极大整数。安全并不等于“拒绝一切”，而是将允许范围说清并用测试验证。对合法范围内请求返回成功，对范围外请求拒绝且工具调用次数为零。

## 常见初学错误

- 把模型返回的代码或 SQL 直接执行。
- 只给模型 schema，却不在应用里复核参数。
- 用模型生成的 `user_id` 或租户名作为权限凭据。
- 无限制重试写操作，造成重复邮件或重复订单。
- 把完整异常堆栈和秘密内容显示给用户。

## 今日验收与复习

- 工具名来自应用白名单，参数先校验再执行。
- 能区分模型“提议”与应用“执行”的责任。
- 工具权限最小、超时有限、错误信息不泄密。

**复习卡片：**为什么仅仅把工具 schema 提供给模型，还不能构成安全边界？

**小词典：**Tool Calling＝模型提出结构化工具请求；Schema＝参数格式约束；白名单＝明确允许的工具集合；最小权限＝只给予任务必要能力；幂等＝重复执行结果不会重复产生副作用。
