# Day 26：Web 界面、文档与 GitHub

**今天的目标：**让第一次接触项目的人看得懂、用得起来，也不会因为界面或仓库泄露数据。

## 从用户看到的流程开始

知识库问答不是“按一下按钮就结束”。用户上传文件后，系统通常要经历**上传 → 校验 → 处理 → 建索引 → 完成/失败**。索引是让系统之后能快速查找文本的目录。文件多或处理慢时，界面要展示目前阶段，而不是一直转圈或看起来像死机。

可以先用下面的**状态机**（把流程划分为有限状态，并规定状态间允许的转换）描述界面：

```text
等待上传 -> 校验中 -> 处理中 -> 已完成
                   \-> 失败 -> 用户重试/联系维护者
处理中 -> 用户取消 -> 已取消
```

每个状态都告诉用户“发生了什么、下一步能做什么”。例如校验失败时提示“仅支持 PDF、TXT；请换文件”，而不是暴露服务器路径或 Python 堆栈。Streamlit、Gradio 适合快速做原型；原型界面并不自动提供身份认证或数据隔离。

## 权限不等于按钮是否可见

**身份验证**回答“你是谁”；**授权**回答“你能对哪份数据做什么”。隐藏上传或删除按钮只是视觉处理，用户仍可能直接构造 HTTP 请求。服务端必须在每次读取、上传、删除、检索时验证当前用户和文档权限。检索结果也要在服务端按权限过滤，不能先把别人的片段交给模型再期待模型不引用。

问答结果应展示可核查的引用；没有证据时应允许系统明确说“资料不足”。遇到可恢复错误（例如文件格式不支持），给出下一步；遇到内部故障，只显示安全的错误编号，并将细节记入脱敏后的维护日志。

## 文档与仓库

README 是陌生开发者的操作指南，至少写：项目用途、架构/数据流、环境要求、安装、配置变量名（不要填真实值）、启动、测试、Mock 模式、数据存放位置、限制和清理方法。**干净环境验证**是指不依赖作者电脑上的私有文件或已设置变量，按 README 从头执行一次。

提交前检查当前文件、Git 暂存区、提交历史、日志、样例数据和截图。`.env` 应忽略并提供无秘密的 `.env.example`。如果凭据曾提交，即使后来删除仍应立即撤销/轮换；Git 历史仍可能保留旧内容。

## 一个小型界面状态示例

```python
def upload_message(status: str) -> str:
    messages = {
        "processing": "正在提取文本并建立索引，请稍候。",
        "done": "处理完成，可以开始提问。",
        "failed": "处理失败。请检查文件格式后重试。",
    }
    return messages.get(status, "状态未知，请联系维护者并提供任务编号。")

print(upload_message("processing"))
# 正在提取文本并建立索引，请稍候。
```

真实界面还应由服务端提供任务状态；不能只在浏览器里自行假设任务已经成功。

## 动手练习

1. **热身：**给“处理中、完成、格式不支持、服务器暂时不可用”各写一条用户提示。验收：每条都说明现状和下一步，且不含堆栈、路径或秘密。
2. **引导：**画上传状态图，标出取消和重试。验收：失败不会伪装成完成；重试会产生可追踪的新任务。
3. **独立：**为一个 Mock 知识库写 README 并从空目录按步骤复现。验收：他人无需私有配置就能运行测试；检查 Git 历史、截图和样例中无凭据/个人信息。

## 常见误区

- 上传进度条只反映浏览器传文件的进度，并不代表后端已经完成解析、向量化和索引。
- 只做漂亮界面，不做服务端鉴权和权限过滤。
- 把用户原文、令牌或个人信息写入日志，或把错误堆栈直接展示给用户。
- “README 写了命令”就认为可复现；还要实际在干净环境照做。
- 秘密文件已删除就认为安全；已公开的凭据必须轮换。

## 深入理解：一次上传怎样安全地走完

可以把上传任务想成餐厅取号：用户提交文件后立即拿到任务编号，厨房（后台工作进程）继续做较慢的准备工作，前台用编号查状态。这样网页不必保持一个连接直到文档全处理完，也不会因为浏览器刷新而忘记任务。任务记录可包含 `task_id`、提交用户、状态、阶段和安全的错误类别；不要在可被猜测的编号中放用户资料。每次查询任务都要检查提交者身份，或确认该用户有权访问所属空间。

例如上传后的响应可以是 `{"task_id":"t-123","status":"queued"}`。之后的状态查询依次返回 `validating`、`extracting`、`indexing`、`done`。页面据此展示“正在检查格式”“正在提取文本”“正在建立检索索引”等消息。若失败，接口可给 `error_code: "unsupported_file"`；界面将它映射成“当前仅支持 PDF 和 TXT，请换一个文件”。真实的库异常和服务器路径留在有访问控制的运维日志中，并以请求编号串联。

权限检查要覆盖整条数据链：上传时确认用户可写入目标知识库；后台任务执行时保存并再次核对所有者；提问时先按用户可见范围筛选文档，再检索；删除时检查文档所有权并确认索引中的副本也被移除。只在 UI 隐藏按钮，既挡不住直接 HTTP 请求，也挡不住共享链接或旧任务 ID 被他人访问。对答复显示引用标题、段落或页码，方便用户核对；若检索结果为空或分数不足，应说“资料不足”，而不是把猜测包装成事实。

## README 的干净环境复现方法

把“干净环境”具体化，可以用新建目录和新的虚拟环境，或者临时创建一个全新容器，而不是清空开发者平时使用的环境。验证者按说明从克隆开始，逐条执行依赖安装、配置复制、Mock 模式启动、健康检查和测试命令。每条命令都说明在哪个目录运行、预期看到什么、失败后检查哪里。若 API Key 可选，明确 Mock 模式不需要密钥；若必填，解释去哪里创建以及如何只在本地设置，绝不在文档示例里放真实值。

检查截图和示例也要看背景窗口、浏览器地址栏、终端提示符与日志内容，它们可能无意中显示用户名、内部主机名或令牌。把日志样例改成虚构值，样例数据明确写“虚构”。仓库的 `.gitignore` 只影响之后未跟踪的文件；对已经提交过的秘密，正确做法是先撤销/轮换，再评估历史和访问记录。

## 复习与词汇

- **复习：**为什么隐藏一个按钮不能代替服务端授权？因为请求可以绕过界面，服务端必须逐次判断身份和资源权限。
- **状态机：**用状态与合法转换表达流程；**Mock：**用本地假数据模拟真实依赖；**脱敏：**移除或替换可识别个人/秘密的信息。
