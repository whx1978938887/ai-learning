# Day 24：项目混合检索与权限过滤

**今天的目标：**在项目样例中合并关键词和语义检索结果，同时保证用户无权访问的片段不会进入模型上下文。

## 1. 混合检索复习与流程

关键词检索适合编号、术语和精确表达；向量检索可以补充同义问法。Hybrid search（混合检索）将两路候选/排名融合，具体使用排名融合、归一化或其他方法要通过固定问题集比较。Reranker（重排器）可以对已召回候选再次排序，但找不到两路都没返回的资料。Day 15 介绍了排名融合和 Recall@k。

可见的调试流程：

1. 记录输入问题及当前检索策略。
2. 分别查看关键词候选、向量候选。
3. 查看合并和重排后的顺序。
4. 按可信权限过滤，排除无权记录。
5. 仅把允许的证据与来源组装到模型上下文。

对问题、候选 ID、排序和过滤结果做必要日志有助排错；不要在日志中无必要地保存完整敏感内容。

## 2. 权限过滤：先确认，再给模型看

权限（authorization）决定一个用户能访问哪些文档。过滤条件必须由服务器根据当前登录身份、文档 ACL（访问控制列表）或租户策略计算，不能采用用户问题、Prompt 或模型生成的租户 ID。

过滤发生得越晚，泄露风险越大：如果无权片段已经被发送到模型，即使最终答案没提到它，内容也已越过边界；若先返回给用户再隐藏文字，更是太晚。权限过滤应在上下文组装和模型调用之前实施。缓存、引用、调试输出也应遵循同一访问规则。

过滤实现要针对实际检索库验证。有的数据库可在检索查询中加入可信 metadata 条件；有的设计需要检索后由服务端过滤。选择哪种策略时，确保无权内容不会进入不受信任的下游，并考虑候选数量、性能和侧信道信息。不能假设一个 API 参数就自动满足所有安全要求。

## 3. 本地安全测试思路

准备 Alice 和 Bob 两篇虚构文档，各自带 owner metadata。调用检索流程时将已认证用户身份从测试夹具传入；服务端过滤只保留该用户可读记录。检查最终上下文，不只是检查 UI 上看不见文字。

```python
docs = [
    {"id": "a1", "owner": "alice", "text": "Alice 项目代号是 Maple。"},
    {"id": "b1", "owner": "bob", "text": "Bob 项目代号是 Cedar。"},
]

def authorized_context(authenticated_user: str) -> list[dict[str, str]]:
    return [d for d in docs if d["owner"] == authenticated_user]

print([d["id"] for d in authorized_context("alice")])
```

输出：`['a1']`。此代码只演示过滤逻辑；实际系统不能把客户端传入的任意字符串当作已认证身份，应由可信认证层提供用户身份，并支持更复杂的 ACL。

注意示例把全部文档先放进 Python 列表，再按 owner 过滤，适合展示概念，不代表所有向量库都必须这么实现。若数据库支持可信 metadata 条件，可在检索请求中限定访问范围；若采用“先检索、后过滤”，要避免无权内容进入模型、缓存、日志或用户可观察的结果，并评估候选截断造成的召回偏差。无论哪种做法，都要以认证服务提供的身份和服务端策略为依据。

权限条件必须在每次查询时应用，而不能只在文档写入时设置一次。用户可能后来失去某文档访问权，文档 ACL 也可能变化。缓存检索结果时，应将用户/权限范围纳入缓存隔离，或在返回缓存前重新检查权限；否则前一个用户的合法结果可能被下一个用户复用。

## 4. 追踪一条结果的安全路径

假设向量候选排序为 `[b1, a1, b2]`，其中 `a1` 属于 Alice，`b1` 和 `b2` 属于 Bob。Alice 发起问题后，服务端只保留 `a1`，之后才把它转成模型上下文和引用。测试时分别检查：过滤前有哪些候选（仅在受保护的内部测试日志中）、过滤后有哪些 ID、模型输入中出现了什么文本、返回引用指向哪里。用户界面上“看起来没显示 Bob 的内容”不足以证明模型未收到它。

过滤候选还会影响召回率：如果当前用户实际上有权访问的片段没有被保留，答案可能缺证据。应使用多用户的固定测试集同时验证两件事：无权片段绝不泄露；有权的正确片段仍能进入候选。安全和相关性要分别检查，不能为了其中一项而忽略另一项。

例如 Alice 有权访问 A 文档和共享文档 S，但无权访问 Bob 的 B 文档。对同一查询，测试应检查 A 和 S 的相关片段仍可召回，B 不会进入模型输入；仅仅让答案“不提到 B”不够，因为模型可能已看到 B 的文字。把候选 ID 和最终上下文 ID 分开记录，能看出过滤是否确实发生在模型之前。

若有多个检索分支，统一封装一个可信过滤步骤或让每路都使用同一服务端授权规则，并测试最终融合结果。否则关键词分支可能已过滤，向量分支却漏掉条件；融合阶段又把无权 B 带回来。引用生成也只能从最终允许的证据集合取来源，不能使用未经授权的候选。

排名融合也要在理解权限条件后评估。若某条文档因无权访问而被过滤，它不应通过另一检索分支、Reranker 或引用缓存重新出现。最终传给模型的证据列表是安全边界前最后一个关键检查点。

## 5. 为排错保留安全的观测信息

开发阶段可记录查询的匿名编号、每一路候选 ID、文档权限决策（允许/拒绝）和最终传给模型的 chunk ID。这样可以复现“为什么 Alice 没找到共享资料”或“为何过滤掉 Bob 的片段”。普通日志尽量不写片段全文、用户原始敏感问题或密钥；必要的全文检查放在本地测试夹具中。

## 6. 召回不够时仍不能放宽权限

当混合检索结果少于 Top-k，不要为了凑足数量放宽权限条件；少返回一些授权内候选是安全的，泄露无权资料不是合理的召回优化。应另行检查授权内索引、过滤实现和候选上限。把安全决定和相关性决定分开记录，能让后续调参不误改访问控制。

负向测试可以让 Bob 的文档对 Alice 的查询拥有完全匹配的关键词，确保检索系统有机会召回它，再检查授权步骤将其排除。正向测试则确保 Alice 自己的相近文档仍然保留。每次调整检索融合或 metadata 过滤后重跑这两类用例，避免修复一项时破坏另一项。

## 常见初学错误

- 把模型的 `tenant_id` 或用户提供的过滤条件当成可信授权。
- 先召回并发送全部结果给模型，再试图隐藏越权答案。
- 将关键词与向量原始分数直接相加但不检查尺度。
- 仅在 UI 层隐藏结果，日志或缓存仍泄漏内容。
- 不检查“没有权限”时是否通过结果数量等信息暴露资料存在。

## 练习（由浅入深）

1. **热身：识别精确与语义问题。**准备一个编号查询和一个自然语言查询。验收：说明分别为什么可能更依赖关键词或向量，不宣称某方法必然成功。
2. **跟做：观察候选融合。**对每种查询手工写关键词、向量两路排名，并做简单排名融合。验收：同一文档能整合两路排名；明确重排不能创造未召回文档。
3. **独立完成：跨用户权限测试。**加入 Alice、Bob 的虚构文档，模拟 Alice 查询一个语义上匹配 Bob 内容的问题。验收：Bob 的 ID 和文本都不出现在最终上下文、引用或用户可见结果；身份来自可信测试夹具；同时记录过滤前后计数，不记录无必要的正文。
