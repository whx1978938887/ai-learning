# 掌握 CoT、零样本/少样本学习与 Negative Prompting

这三种方法都能影响模型输出，但作用并不相同：**零样本和少样本学习决定是否用示例；CoT 引导模型分步骤处理复杂任务；Negative Prompting 明确哪些内容或行为不希望出现。**它们可以组合使用，但都不能代替清晰的任务定义和结果验证。

本文用“分析用户反馈”作为贯穿案例，学习如何写提示词、判断方法是否适用，并通过小实验验证效果。

## 一、先区分三类方法

| 方法 | 核心问题 | 常见写法 | 适合解决 |
| --- | --- | --- | --- |
| Zero-shot（零样本） | 不给示例，模型能否按规则完成任务？ | 直接描述任务、规则和输出格式 | 常见任务、规则直观、希望节省上下文 |
| Few-shot（少样本） | 给少量示例，能否让模型更好地理解规则？ | 提供若干输入与目标输出 | 标签边界难描述、格式或风格需要示范 |
| CoT（Chain of Thought，思维链） | 复杂任务如何分解并检查？ | 要求先识别条件、逐步处理，再给结论 | 多条件判断、计算、规划、复杂问答 |
| Negative Prompting（负向提示） | 哪些输出或行为要避免？ | 明确禁止项及其替代行为 | 控制范围、风格、臆测、冗余或不需要的内容 |

前三种并非互斥选项。例如可以在 Few-shot 示例基础上，要求模型按步骤检查分类条件，并禁止猜测输入中没有的信息。是否有效仍要用固定样例测试。

> **术语提醒：**CoT 常被译为“思维链”。实际应用中，更稳妥的目标通常是让模型执行可检查的步骤，并给出简短依据或验证结果，而不是要求输出冗长的内部推理全文。对用户交付的内容，应只包含完成任务所需的说明。

## 二、Zero-shot：不提供示例，先把规则说完整

Zero-shot（零样本提示）指的是：**提示词里不提供任务示例**。它不等于只写一句话，也不等于模型完全没有预训练知识；它只表示本次提示没有给输入—输出演示。

### 一个零样本例子

```text
你是产品反馈分类员。阅读用户反馈，只依据原文明确表达的信息，选择一个主要类别：性能、易用性、价格、功能、其他。

规则：
- 多个问题同时出现时，选择用户最主要或描述最具体的问题。
- 证据不足以归类时选择“其他”，不要推测原因。
- 只输出以下两行，不附加建议：
类别：<一个允许的类别>
依据：<不超过 30 字，指出原文中的直接证据>

待分析反馈：
“新版本里找不到导出按钮，之前保存的文件也打不开。”
```

这里没有任何示例，但任务、标签范围、冲突处理、未知情况和输出结构都写明了。Zero-shot 的质量关键不是“提示词短”，而是**规则足够明确，且任务与模型已有能力相匹配**。

### 何时先试 Zero-shot

- 类别定义直观，或者任务本身是常见问答、改写、摘要。
- 你还没有可靠示例，或不希望示例偏置模型。
- 上下文长度或调用成本比较敏感。
- 希望先建立简单基线，知道不加示例时模型会在哪里出错。

### 常见问题

如果同一句反馈有多种合理分类，单纯加“请准确分类”通常无效。应定义“主要类别”的选择规则、标签的边界，以及不确定时的处理方式。必要时再用少量示例展示这些边界。

## 三、Few-shot：用少量示例展示规则边界

Few-shot（少样本提示）是在当前提示中提供少量**输入—理想输出**示例。模型据此从上下文学习本次任务的标签用法、输出样式或判断边界，不代表模型参数被永久训练或更新。

### 将示例加入同一个任务

```text
你是产品反馈分类员。只依据原文，选择一个主要类别：性能、易用性、价格、功能、其他。
多问题同时出现时，选择用户描述最具体的问题；不要推测原因。只输出“类别”和“依据”。

示例 1
反馈：搜索结果要等很久才出现。
输出：
类别：性能
依据：搜索结果出现很慢

示例 2
反馈：我想把报告发给同事，但页面里没有分享入口。
输出：
类别：功能
依据：没有分享入口

示例 3
反馈：按钮太多，我不知道下一步该点哪里。
输出：
类别：易用性
依据：用户不知道下一步如何操作

现在分析：
反馈：新版本里找不到导出按钮，之前保存的文件也打不开。
```

这个例子把功能缺失、使用困惑和性能问题区分开了。对实际任务，示例应该反映真实输入，而不是为了凑数量随意编造。

### 选择示例的原则

- **有代表性：**接近实际输入的长度、措辞和噪声水平。
- **有区分度：**优先加入容易混淆的标签、边界情况和反例。
- **前后一致：**示例输出必须遵循同一套规则和格式。
- **数量克制：**从少量高价值示例开始；冗长或重复的例子会增加成本，也可能干扰判断。
- **避免标签泄漏：**不要把目标输入的答案或与答案强相关的无关线索带进示例。

如果示例数量增加后结果变差，先检查是否有示例互相冲突、示例与规则不一致，或示例分布过于单一。Few-shot 不是“例子越多越好”。

### Zero-shot 与 Few-shot 的选择

先用 Zero-shot 作为基线。如果错误主要来自规则理解或标签边界，再补充少量针对性示例；如果错误是事实知识、上下文缺失或任务本身含糊，增加示例不一定能解决。

## 四、CoT：把复杂任务拆成可检查的步骤

CoT 是“思维链”提示方式的简称，通常指引导模型在得出答案前组织中间步骤。它可以帮助模型处理需要多步判断的问题，但并不保证结论正确；步骤写得越长，也不必然越可靠。

### 适合分步骤处理的任务

- 有多个明确条件要同时核对。
- 需要计算、比较或按顺序执行规则。
- 结论需要能追溯到输入中的证据。
- 需要在作答前检查遗漏或内部矛盾。

简单的单标签映射通常不需要 CoT。对复杂分类，可用**任务步骤**代替宽泛的“展示完整思维链”：

```text
请按以下流程处理，但只输出规定结果和简短依据：
1. 从原文提取明确提到的问题，不推断原因。
2. 将每个问题对应到允许的类别。
3. 如果有多个问题，按“用户最主要或描述最具体的问题”选择一个。
4. 检查所选类别是否有原文证据；没有就选择“其他”。
5. 输出类别和不超过 30 字的证据摘要。
```

这里的步骤是**可观察、可评估的任务流程**，最终的“依据”是供用户核验的简短证据，而不是要求模型展示所有内部思考。

### 结构化推理提示模板

```text
任务：<要解决的问题>

处理步骤：
1. <提取输入中明确的信息>
2. <按给定规则比较或计算>
3. <核对边界条件和不确定信息>

约束：<不得推测的内容、适用范围>

最终输出：<答案格式，以及是否需要简短依据>
```

把步骤写成领域规则，比只说“仔细思考”“一步一步想”更容易测试。例如，日期计算应明确时区、起始日是否计入；分类任务应明确多标签冲突如何处理。

### CoT 的边界与验证

- **步骤不等于证据：**模型可能给出看似连贯但错误的过程。对事实、数字和关键结论要独立校验。
- **简单任务不必强加步骤：**步骤可能增加延迟、成本和冗余，还可能引入新的错误。
- **要求可检查的交付物：**例如中间计算值、引用的输入片段、规则检查结果，而不是没有必要的长篇推理。
- **敏感或高风险任务加强外部验证：**医学、法律、财务或安全相关结果不能仅凭模型自述的推理确认。

如果 API 或产品提供结构化推理、工具调用或校验能力，应结合相应文档使用。提示词本身不能保证内部推理过程完整、忠实或正确。

## 五、Negative Prompting：明确不想要什么，也说明应该怎么做

Negative Prompting（负向提示）是明确告诉模型要避免的内容或行为。它可以减少跑题、臆测、冗余和不合格式，但**只列禁止事项往往不够**：最好同时写出正确的替代行为。

### 负向约束的写法

```text
不允许：
- 不要推测用户没有提到的技术原因。
- 不要把未确认的信息写成事实。
- 不要提出解决方案。
- 不要输出给定标签以外的类别。

遇到信息不足时：选择“其他”，并在依据中写“信息不足”。
```

“不要瞎编”是方向，但不是完整的处理规则。补上“信息不足时选择什么、如何标注”，模型才有可执行的替代路径。

### 不够好与更可执行的写法

| 不够明确 | 更可执行 |
| --- | --- |
| 不要啰嗦 | 只输出类别和一条不超过 30 字的依据，不写开场白或建议 |
| 不要猜 | 只使用输入中明确出现的信息；缺少依据时输出“无法判断” |
| 不要分错类 | 类别只能从给定列表选择；多问题时按指定规则选一个主要类别 |
| 不要用专业术语 | 面向普通用户表达；首次出现的必要术语用一句话解释 |

负向指令有时会和正向要求冲突。例如“解释清楚”与“只输出一个标签”不能同时满足。应明确优先级，或把结果拆为标签与限定长度的依据。

### 文本任务与图像生成中的术语

在文本任务里，Negative Prompting 通常是提示词中的禁止项和边界条件。在部分图像生成工具里，“negative prompt”也可能是单独的负向提示输入框，用于描述不希望生成的视觉元素，例如“文字、水印、模糊”。不同模型对该字段的支持和含义不同，应以工具文档为准；图像生成的负向提示不一定能原样迁移到聊天模型。

## 六、组合使用：从清晰规则到针对性增强

下面是一个把 Zero-shot、Few-shot、步骤检查和负向约束组合起来的模板。按任务需要取舍，不要把每个模块都机械地塞进去。

```text
角色：你是产品反馈分类员，只做基于文本证据的分类。

任务：从“性能、易用性、价格、功能、其他”中选择一个主要类别。

判定规则：
- 只依据反馈中明确表达的内容。
- 多个问题同时出现时，选择用户最主要或描述最具体的问题。
- 无法从原文判断时选择“其他”。

处理步骤：
1. 找出原文明确描述的问题。
2. 根据判定规则选择一个类别。
3. 检查是否有直接证据支持该类别。

不要做的事：
- 不要推断技术原因或用户未表达的意图。
- 不要提出解决方案。
- 不要输出列表以外的类别。

示例：
反馈：切换页面时总要等五秒。
输出：
类别：性能
依据：切换页面需要等待五秒

输出格式：
类别：<一个允许的类别>
依据：<不超过 30 字的直接证据；信息不足时写“信息不足”>

待分析反馈：
{{feedback}}
```

使用前确认：示例是否必要？任务是否真的需要步骤？禁止项是否配有明确的替代行为？输出字段是否与最终用户需要的一致？删掉不需要的部分，往往更易维护。

## 七、怎样验证有没有改善

不要只凭某一次输出“看起来更好”就判断提示词有效。用同一组输入比较不同提示词，并分别检查正确性、格式和成本。

### 一个小型对照实验

准备至少 12 条固定反馈，覆盖清晰样例、易混淆样例、多问题、信息不足和口语表达。请人工先标注参考答案，再比较：

| 版本 | 提示词设置 |
| --- | --- |
| A | Zero-shot：任务、判定规则、输出格式 |
| B | A + 3 至 5 个有区分度的 Few-shot 示例 |
| C | A + 可检查的处理步骤 |
| D | B + 处理步骤 + 必要的负向约束 |

记录以下指标：

- **分类正确率：**类别正确的样本数 ÷ 总样本数。
- **格式合规率：**符合字段、值域和长度要求的样本数 ÷ 总样本数。
- **臆测率：**依据中包含输入没有支持的信息的样本数 ÷ 总样本数。
- **成本与延迟：**记录实际调用的模型、参数、输入/输出 Token（若可获取）和耗时。

每轮只改变一种主要因素，使用相同模型、参数和样本。如果模型输出存在随机性，可对每个版本重复运行，并记录设置。样本数量较少时，结果只用于发现问题，不足以证明方法对所有任务都有效。

### 结果如何解释

- B 比 A 好：示例可能帮助厘清标签或格式；检查改善是否集中在边界样例。
- C 比 A 好：显式步骤可能有帮助；确认没有让简单样例变差或增加不必要输出。
- D 的格式更整齐但正确率没变：约束改善了可控性，不代表判断质量提升。
- 指标都没改善：检查标签定义、测试集、模型能力和输入质量，不要只继续增加指令。

## 八、常见失误与排查

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| Zero-shot 分类摇摆 | 标签边界、冲突规则或未知值没有定义 | 补充定义和冲突处理规则 |
| Few-shot 越加越差 | 示例冲突、过度单一或与真实输入差异大 | 删除低价值示例，保留边界对照 |
| CoT 输出很长但答案仍错 | 要求展示过程，却没有可验证的规则或计算校验 | 改成短步骤、明确核验点，并独立验证结果 |
| Negative Prompting 没效果 | 禁止项太抽象，或没有说明遇到该情况怎么办 | 写出可观察的禁项和替代输出 |
| 结果守格式但内容错误 | 把格式合规误当成事实正确 | 分别评估内容正确率与格式合规率 |
| 每次修改都无法判断效果 | 同时改了多个变量，或每轮输入不同 | 固定测试集，每轮只改一个主要因素 |

## 九、练习

### 练习 1：建立 Zero-shot 基线

为下面任务写一条不含示例的提示词：将客服消息分类为“退款、物流、商品质量、账户、其他”。定义多问题时的选择规则、证据要求和无法判断时的输出。准备至少 8 条输入，人工标注预期分类并记录模型错误。

### 练习 2：为边界情况添加 Few-shot

从练习 1 中挑出最容易混淆的两个类别，为它们编写成对示例：输入相似，但正确标签不同。将示例加入提示词后重跑同一组输入，比较分类正确率，而不是只挑新版本答对的案例展示。

### 练习 3：写可检查的 CoT 步骤

设计一个多条件任务，例如判断活动通知是否包含报名所需的全部信息。列出模型必须核对的字段，规定缺少字段时的结果，并让最终输出包含“是否完整”和“缺少项”。不要要求无关的长篇过程。

### 练习 4：改进 Negative Prompting

把“不要瞎编、不要啰嗦、不要答非所问”改成至少三条可检查的规则。每条规则都写清楚：禁止什么、依照什么证据、无法完成时如何输出。

### 练习 5：做四组对照

使用本节对照实验的 A、B、C、D 四种设置跑同一组测试输入。记录正确率、格式合规率、臆测率和成本/延迟，写下最有效的一项变化及其适用边界。

## 十、完成后的自我检查

- 我能区分“不提供示例”“提供少量示例”“分步骤处理”和“禁止某类输出”吗？
- 我是否先建立了 Zero-shot 基线，而不是默认示例越多越好？
- Few-shot 示例是否代表真实输入，并覆盖容易混淆的边界？
- CoT 步骤是否对应任务规则，且最终答案有独立核验方式？
- Negative Prompting 是否给出了信息不足时的替代行为？
- 我是否分别检查了内容正确、格式合规、臆测和成本？
- 每轮实验是否使用同一组输入，并只改变一个主要因素？
