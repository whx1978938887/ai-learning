# Day 15：混合检索与 RAG 评估基线

**今天的目标：**认识关键词检索与语义检索的互补之处，建立“改进之前”的可复现基线。

## 1. 两类检索解决不同问题

**关键词检索**查找字面词项匹配。BM25 是常见的相关性排序方法，会考虑查询词与文档中的匹配情况及词频等因素。它通常适合型号、编号、专有名词和精确短语，但不一定理解同义表达。

**向量检索**比较查询与文档的 embedding 向量，适合含义相近但用词不同的表达；它可能把语义接近却细节不对的内容排前面，也可能漏掉精确编号。

举例：查询 `AB-204` 可能更适合关键词检索；查询“如何取消尚未发货的购买”可能从语义匹配中受益。实际结果受语料、分词、embedding 模型和参数影响，必须用本地样例验证。

## 2. 混合检索：合并候选或排名

混合检索（hybrid search）把关键词和向量两路结果结合。不能默认直接相加原始分数，因为不同方法的分数尺度可能完全不同。较直观的方法是排名融合：分别排序后，对某条记录的名次贡献分数，再合计。

一种常见思路是 Reciprocal Rank Fusion（RRF，倒数排名融合）：

```text
融合分数 = 对每一路结果求和：1 / (常数 + 该路排名)
```

常数用于避免第一名分数过大。理解概念即可；具体常数、候选数和实现方式都应以评测结果为准。融合不会创造新文档，只能整合两路已经召回的候选。

Reranker（重排器）再用另一种相关性判断，对有限候选重新排序。它能改变顺序，但无法找回初始两路都没召回的文档。HyDE（假设文档嵌入）会先生成一段假设性答案/文档再用于检索，可能帮助召回，也可能引入生成成本和错误；初学阶段把它视作可选实验，不是默认必备步骤。

## 3. RAG 评估基线

在优化前保存一份基线（baseline，当前系统表现的参考点），至少评估：

- **检索：**Recall@k（Day 14）、MRR（Mean Reciprocal Rank，平均倒数排名：第一条相关结果排名越前，分数越高）。
- **答案：**是否回答正确、是否忠实于给出的资料（groundedness/faithfulness）。
- **引用：**引用是否存在，是否真的支持对应陈述。
- **拒答：**资料不足时是否避免猜测。
- **运行：**延迟、调用次数等（即使使用 mock，也记录哪些指标尚未测量）。

10 条问题适合做课堂小基线，但结论只能用于初步比较。评估可以人工完成，也可以使用本地脚本；某个评估框架不是建立评估的前提。

## 4. 手算一个简单排名和指标

假设一题只有一个相关文档，系统把它排在第 2 位。此题的 reciprocal rank（倒数排名）是 `1/2=0.5`；若排第 1 位则是 `1/1=1`，排第 4 位则是 `1/4=0.25`。MRR 是多个问题各自“第一条相关结果排名倒数”的平均值。两题的第一条相关结果分别排第 1、第 4，MRR 就是 `(1 + 0.25) / 2 = 0.625`。若某题没有相关结果，通常记为 0；记录评估时要写明规则。

Recall@3 只看相关来源是否出现在前三位；第一名与第三名都算命中。因此 MRR 与 Recall@k 补充不同信息：前者关注相关结果靠不靠前，后者关注是否进入指定候选范围。

## 5. 建立可复现的 baseline 表

基线表不必复杂，但要让未来的自己能重复实验。至少记录语料版本、问题集版本、检索方法、Top-k、相关来源标注、检索命中、回答、引用核验和拒答结果。真实服务才记录实际延迟或调用成本；本地 mock 没测过就写“未测”，不要编数字。

| 题目 | 类别 | 关键词 Top-3 | 向量 Top-3 | 混合 Top-3 | 答案/引用检查 |
|---|---|---|---|---|---|
| AB-204 是什么？ | 编号 | … | … | … | 待检查 |
| 怎么重新开通账号？ | 自然语言 | … | … | … | 待检查 |
| 周日是否营业？（资料无记载） | 不可回答 | … | … | … | 应拒答 |

比较时保持语料和问题集不变；若更改 embedding 模型或索引内容，要记录为新条件。小基线用于发现明显差异和指导下一轮，不代表所有业务问题上都会得到同样效果。

一个直观的双查询演示：准备两篇虚构文档，一篇含“设备型号 AB-204 的重置步骤”，另一篇写“忘记密码后如何恢复账户”。先查精确编号 `AB-204`，记录关键词和向量各自的 Top-3；再查自然语言问题“我无法登录，怎么重新获得账号访问？”。这些只是待验证的假设，不是对某个检索器的保证，要以实际候选为准，再判断哪一路补上了另一条遗漏。

若某条文档只出现在关键词结果中，混合流程要保留它；只出现在向量结果中也一样。融合后还要检查 Top-k 截断是否把有用候选挤掉。记录文档 ID 而不是只抄文字，能在去重时确认两个结果是不是同一来源。

答案评价也可用简单人工核对表：事实是否正确、能否从给定片段推出、引用是否指向该片段、不可回答时是否拒答。评测者应同时看到证据和答案，否则“听起来对”可能被误判为忠实于资料。若不同人对样例判定不一致，保留讨论并修订标注，不要悄悄删除失败题。

## 6. 让混合检索比较公平

关键词检索和向量检索可能分别返回同一文档。融合前先按稳定文档 ID 去重，并为每一路记录名次；融合后查看每个 ID 来自哪几路。只记录最终文本会隐藏候选重复或来源不同的问题。若使用 RRF，某份文件在两路都排名靠前时通常会得到较高融合排名，但具体排序仍应实测。

比较时保持文档集合、问题文本和候选数量一致。不要给关键词检索 Top-5，却给向量检索 Top-50 后直接说混合方法更好；更多候选自然更容易覆盖答案，但也可能带来噪声。若确实要测不同候选数，单独作为一个因素记录。

## 7. 评估结论应该回答什么

好的基线小结不只是报一个分数，而是回答：哪些问题命中、哪些漏了？精确编号查询和自然语言查询分别表现如何？不可回答问题有没有被错误回答？引用是否支持答案？目前最大的未知是什么？比如 mock 没有测真实延迟，就明确写“尚未测量”。小样本的价值是发现下一步假设，不是证明系统已适合上线。

练习结束后保存一次基线，不要覆盖旧记录。下一天优化时用同一问题集再测，才能看出改动带来的影响。

## 常见初学错误

- 认为向量检索一定比关键词好，或关键词一定更准确。
- 把不同检索分数直接相加，没确认它们是否在同一尺度。
- 指望 Reranker 找回最初候选集合里没有的文档。
- 混淆“答案看起来合理”和“答案被证据支持”。
- 先改参数再建基线，无法知道新配置是否真的更好。

## 练习（由浅入深）

1. **热身：选择检索方式。**为 `错误码 E-17` 和“账号怎么重新开通”各选关键词、向量或两者并用，并说明理由。验收：精确代码优先考虑关键词；自然语言同义问法考虑语义搜索，但用测试确认。
2. **跟做：手算 RRF。**某条文档在关键词排名第 1、向量排名第 3，使用教学常数 `60`。验收：写出 `1/61 + 1/63`；说明这是排名融合示意，不是把两个原始相关性分数直接相加。
3. **独立完成：建立基线。**整理 10 个问题，包含编号、自然语言、不可回答问题；对关键词、向量、混合方法记录 Top-3。验收：算 Recall@3（写出分母）、抽查 3 个回答的证据/引用；记录方法版本和设置，不先调参数。
