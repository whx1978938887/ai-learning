# Day 36：简历定位与项目证据

**今天的目标：**把真实经历映射到目标岗位，并让每条重要技能都能被项目、代码、测试或演示验证。

## 简历不是技术名词清单

简历要回答两个问题：你想做哪类工作？你有哪些证据证明自己能做其中一部分？“AI 工程师”可能意味着后端 API、RAG 应用、数据管道、模型训练或部署运维。先根据岗位职责确定方向，不要把调用模型 API 说成“训练大模型”，也不要把课堂 Demo 说成线上生产系统。

把经历拆成四层：

1. **问题与使用者：**谁遇到什么困难？
2. **本人贡献：**你亲手设计、实现或验证了什么？
3. **技术决策：**为什么用这种方案，而非另一个？
4. **证据与边界：**如何验证？在什么条件下有效？尚未完成什么？

## Worked example：从空话改成可信表述

原句：“我做了一个智能客服系统，使用大模型提高效率。”

若实际项目是课程里的本地原型，可改为：

> 在课程项目中独立实现一个本地知识库问答原型：负责 PDF 文本切分、向量检索和带来源引用的回答流程；用 20 条自建问题检查引用是否覆盖答案，并记录 4 个未召回案例。项目使用 Mock/本地数据，尚未接入真实用户或测量生产效率。

这段不夸大“效率提升”，交代了职责、方法、验证和限制。简历上的量化数字必须能回到实验记录；没有证据就写已完成的工作和下一步评估，而非编一个百分比。

## 建立证据矩阵

| 岗位要求 | 你的经历 | 可核验证据 | 还缺什么 |
|---|---|---|---|
| REST API | 完成 FastAPI 原型 | 请求 schema、自动测试、README | 认证/部署经验 |
| RAG | 完成小型检索 Demo | 数据流图、样例引用、评估表 | 大规模运行经验 |
| 容器 | 编写 Docker Compose | 可复现启动步骤 | 生产集群运维 |

“团队做了”不等于“我做了”。清楚写明你负责部分、协作部分与他人贡献，面试时也用同样边界解释。

## 求职材料检查清单

- 每个项目描述包含目标、本人动作、结果/证据和限制。
- 技术名词能被你用自己的话解释，能回答“为什么选它”。
- 链接能打开，仓库有运行说明，截图/日志已脱敏。
- 课程练习、个人原型、真实生产经验明确区分。
- 日期、角色、指标一致；每个数字有来源和测量方法。

## 常见错误

- 将所有参与过的技术都写成“熟练”，面试官自然会追问到无法解释的深度。
- 写“熟练掌握”但无法现场说明或展示证据。
- 把 API 调用、RAG 搭建和模型训练混称为训练大模型。
- 用团队整体成果暗示个人完成全部工作。
- 把本地小样本结果包装成生产用户收益。
- 为了匹配岗位而夸大行业经验或虚构指标。

## 深入理解：把岗位用词翻译成可验证工作

“熟悉 Python 后端”可能意味着能读写 API、处理请求校验、错误和测试，而不是只写过一个脚本。读职位要求时，先将抽象能力拆成可观察动作：比如“RAG 经验”可拆为能解析文档、构造索引、检查召回、展示引用、设计测试。然后给每个动作找证据；如果只有一部分，就写清范围，而不是把全部能力合并成一个夸张标签。

证据最好能让别人独立验证：代码链接定位到主要实现，测试命令能跑通，演示数据为虚构，README 说明环境。若作品依赖 API，提供 Mock 路径或录屏，避免审核者必须购买服务才能看到流程。若项目是小样本实验，附数据量、测试方式和失败案例，比“效果良好”更可信。

## Worked example：区分自己与团队贡献

想像团队四人做了一个内部知识库，团队成果接入 100 份文档并给 30 人使用；你本人只负责上传校验、文件元数据和两条权限测试。不能把“我构建了服务给 30 人使用”当作个人工作。可以写：“在四人团队的内部知识库项目中，我负责上传校验与文档元数据接口，补充格式错误和越权场景测试；团队系统接入 100 份文档并由约 30 人试用。检索和部署由其他成员负责。”若这些数字是团队数据，说明统计来源或标记为团队整体背景。

如果没有真实人数或业务指标，可以描述可复核的工程成果：“实现文件类型/大小校验，测试覆盖正常 PDF、空文件和不支持格式；失败时返回明确错误码。”这类结果虽不宏大，却比虚构增长百分比更有用。

## 项目描述的事实核对

逐句检查：动词是否准确（设计、实现、维护、参与）；主语是否清楚（我/团队）；指标有没有数据来源；“自动化”“实时”“安全”等词是否有具体定义；演示和生产是否区分；限制是否能诚实讲出。准备一条具体失败案例，说明如何定位、修复或决定不修复，这能证明你确实理解项目，而不是只会复述宣传语。

技能分级可以很朴素：接触过（能描述概念）、练习过（能完成小任务）、做过项目（能解释选择与边界）、生产负责过（能说明运行、故障与维护证据）。不要把课程视频看过写成独立实战。

## 从项目产物组织证据包

简历每个项目可以准备一个“证据包”：仓库链接、运行截图或短演示、最关键的测试、架构/数据流图、评估记录、已知限制。面试前确认链接不需要私人账号、仓库中的命令仍有效、展示数据是虚构或获准公开。若项目不适合公开，可做删敏的最小复现，或用口头解释架构并说明保密边界，而不是贴出内部代码。

证据包也能帮助你判断自己是否真的掌握一项能力。若简历写“实现权限过滤”，应能指出在哪个阶段过滤、测试如何验证不同用户看到不同资料、越权时如何失败；若只是在界面上隐藏按钮，就应把描述收窄为“实现界面入口控制”，并承认服务端授权尚未完成。把措辞与实现对应起来，既帮助面试官提问，也能暴露下一步学习目标。

## 根据不同岗位调整重点

同一个项目可以有不同但真实的讲法。后端岗位强调 API schema、错误处理、任务状态和自动测试；AI 应用岗位强调数据切块、检索、引用和评估；测试岗位强调边界案例、Mock 和可重复测试；部署岗位强调容器、日志、健康检查与回滚。调整的是展示顺序，不是捏造不同经历。每版简历都应保留相同事实和指标，便于追溯。

## 动手练习

1. **热身：**选一个岗位方向（后端、AI 应用、测试、部署或训练），列出三项核心职责。验收：不是只写技术名词。
2. **引导：**给两个项目填写上面的证据矩阵。验收：每个“已掌握”对应可打开的代码、测试、演示或文档；缺口诚实标注。
3. **独立：**将一个项目写成 2–3 条简历 bullet，并进行事实核对。验收：能讲清个人/团队边界、测试条件、限制；无无法证明的指标或生产化表述。

## 复习与词汇

- **复习：**“我做了智能客服”可改成说明本人负责部分、使用技术、验证证据和项目边界的一句话。
- **证据：**能让他人复核的产物或记录；**岗位匹配：**经历与职责之间可解释的对应，而不是关键词重合。
