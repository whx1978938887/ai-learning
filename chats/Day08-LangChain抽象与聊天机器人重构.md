# Day 8：LangChain 抽象与聊天机器人重构

**今天的目标：**从“一个函数包办所有事”逐步拆成职责清楚、可测试的组件；知道 LangChain 能帮什么、不能替你决定什么。

## 先建立直觉：框架不是模型

模型是负责根据输入生成内容的程序/服务；框架（framework，帮助你组织程序的工具集）是把提示、模型、检索和工具连接起来的代码。LangChain 属于后者。即使完全不使用框架，也能通过普通 Python 函数把这些步骤串起来。

想象一个问答工序：

```text
用户问题 → Prompt（整理输入）→ Model（生成）→ Parser（检查/转换）→ 用户看到的结果
                                  ↑
                      Retriever（可选：找资料）
```

每个组件有清晰的输入与输出，所以可以单独替换、测试：

| 组件 | 通俗说法 | 何时需要 |
|---|---|---|
| Prompt | 给模型的任务说明和输入格式 | 几乎所有模型调用 |
| Model | 生成文本的模型接口 | 需要模型回答时 |
| Parser | 把模型文本变成程序可用的数据，并检查格式 | 下游程序需要 JSON、分类值等 |
| Retriever | 从自己的资料中找候选片段 | 需要依据私有/本地文档回答时 |
| Tool | 应用允许模型请求执行的一个受控动作 | 需要查天气、算数等外部能力时 |

Retriever 和 Tool 并不是“模型自动拥有的能力”：它们是应用提供的组件。完整 Tool Calling 会在 Day 18 讲解；结构化 Prompt 和输出检查见 [Day 9](Day09-聊天重构PromptTemplate与Parser.md)。

## Runnable / LCEL 是什么

Runnable（可运行组件）是 LangChain 中一类可统一调用、可组合的组件；LCEL 是 LangChain Expression Language 的缩写，指用组合表达式把组件接成流程。它解决的是**如何组织和组合程序步骤**，不会自动让回答更准确、数据更安全，也不会替你选好分块或授权规则。

LangChain 的 API 随版本演进，旧教程中的 `Chain`、`Memory` 等接口不一定适用于当前安装版本。初学时先看清依赖版本，再读该版本的官方文档；不要把网上某段代码当作所有版本通用。

## 动手前的重构方法

把 CLI（命令行程序）的工作分开：

1. CLI 读取用户文字、显示回答。
2. 会话逻辑组织历史并调用模型接口。
3. Provider（模型服务提供方）的实现负责具体请求。
4. 测试用 FakeModel（假模型）返回固定内容，不需要网络、密钥或付费额度。

“分开”不是要求马上创建许多目录或类，而是先让数据流清楚。比如 CLI 收到 `"你好"` 后，先构造一条用户消息，再交给 `ask()`；`ask()` 不应该读取键盘或打印屏幕，它只处理输入并返回回答。这样测试可以直接调用 `ask()`，不用模拟键盘。若之后要换模型，只替换模型对象，不必重写用户输入逻辑。

下面是只用 Python 标准库的最小例子，可保存为 `chat_demo.py` 后运行：

```python
from typing import Protocol

class ChatModel(Protocol):
    def reply(self, messages: list[str]) -> str:
        """给定消息列表，返回一段文本。"""

class FakeModel:
    def reply(self, messages: list[str]) -> str:
        return f"收到 {len(messages)} 条消息：{messages[-1]}"

def ask(model: ChatModel, question: str) -> str:
    return model.reply([question])

if __name__ == "__main__":
    print(ask(FakeModel(), "你好"))
```

预期输出：

```text
收到 1 条消息：你好
```

`Protocol` 是接口约定：只要对象提供了 `reply` 方法，就能传入 `ask`。业务代码依赖“能做什么”，而不是绑死某个服务商 SDK。以后接真实模型时实现同样的方法即可；没有真实模型凭据也能先完成其余逻辑和测试。

初学者可以把这个接口想成插座：插座约定电压和形状，电器不必知道墙内电线如何布置。程序中的调用约定同样要明确，例如输入是消息列表，返回值是字符串；如果真实服务可能超时，它还要明确错误如何返回。接口约定不代表各种模型效果相同，真实实现仍需单独验证。

如果暂时不用类型提示，也可用最普通的函数实现同一想法：

```python
def fake_reply(messages):
    return "固定测试回答"

def ask_with(reply_function, question):
    return reply_function([question])

print(ask_with(fake_reply, "你好"))
```

预期输出是 `固定测试回答`。类或 `Protocol` 不是重点；重点是把“聊天流程需要一个可返回文本的调用者”与“这个调用者到底连向哪家模型”分开。

可以为这个最小接口写一个完全离线的断言：

```python
fake = FakeModel()
assert ask(fake, "你好") == "收到 1 条消息：你好"
print("通过：模型接口能被假实现替换")
```

`assert` 是断言：条件不成立时测试会报错，成立时程序继续。这比只看“程序没有崩溃”更有用，因为它检查了预期结果。后续真实模型版本也可用相同接口，但真实请求应单独做集成测试，并明确处理网络异常；单元测试不应该因为网络或 API 密钥不可用而失败。

在拆分组件时，可以用“谁拥有这条规则”来决定放在哪里：终端输入格式属于 CLI；对话是否保留最近几轮属于会话逻辑；怎样调用服务商接口属于 Provider；JSON 字段是否合规属于 Parser 或业务校验。不要让 Provider 直接读键盘，也不要让 Prompt 组件决定用户是否有权查看某篇文档。边界清晰后，排错时就能先问“哪个组件的输入/输出不符合约定？”

可以用一个简单边界测试来练习这个思路：给 `ask()` 传入空字符串时，决定这是 CLI 应提示重输，还是业务函数拒绝空问题；把决定写成规则并只在一个地方实现。然后用 FakeModel 断言空问题没有到达模型。测试隔离的不只是网络，也能确认程序不会把格式错误、未授权或空白输入误传给后续组件。若你的项目使用 LangChain，先确认所装版本的类和方法；这里的 Python 接口是教学示意，不依赖某个 LangChain 版本。

抽象的好处可以用替换实验观察：先让 FakeModel 固定返回 `"好的"`，再换成返回 `"暂时无法回答"`，检查 CLI 和会话逻辑是否需要跟着改。如果只需替换 FakeModel，边界就起到了作用；如果到处都要改，说明 provider 调用散落在多个地方。反过来，如果为了只运行一次的脚本创建了许多层接口，且没有替换或测试需求，也可以先简化。抽象的价值由真实变化点决定，而不是类的数量。

## 常见初学错误

- **把 LangChain 当成模型：**框架负责组织调用，回答仍由模型产生。
- **一开始就把每行代码包成组件：**抽象不是越多越好；当替换、复用或测试确实变困难时再抽象。
- **把模型文字直接当成可靠数据：**需要结构化结果时必须解析并校验。
- **照抄旧 API：**先检查锁定的包版本；小例子跑通后再扩展。
- **测试必须连网：**先以 FakeModel 测会话行为，网络集成单独测。

## 练习（由浅入深）

1. **热身：画组件图。**画出 Prompt、Model、Parser 的顺序，在每个箭头旁标注输入/输出类型。检查点：能指出哪一步是模型生成、哪一步是程序校验。
2. **跟做：替换假模型。**运行上面的代码，将 FakeModel 的固定回复改成 `"测试回答"`。再调用 `ask` 两次。预期每次均打印 `测试回答`，且无网络请求。
3. **独立完成：拆开现有 CLI。**将“读输入/打印”“会话逻辑”“模型实现”分成三处；写 FakeModel 的自动测试。验收：FakeModel 可替换真实实现、测试离线通过、同一问题可重复得到固定结果；记录项目实际 LangChain 版本（若使用）及其文档入口。

## 今日验收与复习

- 能用自己的话说清 Prompt、Model、Parser、Retriever、Tool 的职责。
- Runnable/LCEL 是组织步骤的方式，不是质量或安全保证。
- 你的业务流程能用假模型离线测试。

**复习卡片：**Runnable/LCEL 组合改变的是组件组织方式；它不会自动解决什么业务问题？

**小词典：**框架＝帮助组织程序的工具；Provider＝模型服务提供方；接口＝组件之间约定好的调用方式；Fake/Mock＝测试中用的可控替身；LCEL＝LangChain 的组件组合表达式。
