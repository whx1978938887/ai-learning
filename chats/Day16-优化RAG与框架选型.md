# Day 16：优化 RAG 与框架选型

**今天的目标：**依据 Day 15 的评测结果定位瓶颈，进行一次小而可验证的修改；再判断框架是否真的能解决当前需要。

## 1. 从失败结果反推问题阶段

RAG（检索增强生成）不是一个黑盒步骤。常见错误和可能位置：

| 观察到的问题 | 先检查什么 |
|---|---|
| 原文里有答案，但候选里完全没有 | 文件是否成功解析、分块是否切断、检索设置/方法 |
| 候选里有正确资料，但排在很后面 | 排序、关键词/向量结果融合、是否需要评估重排 |
| 候选内容相互矛盾或太多 | 来源质量、过滤条件、Top-k、去重 |
| 候选有清楚证据，回答仍答错 | Prompt 是否要求依据证据、上下文组装、模型误读 |
| 引用不存在或不支持句子 | 引用映射、回答与证据对照 |

定位时从文档到回答逐步检查：源文件 → 提取文本 → chunk → 检索候选 → 过滤/重排 → Prompt 上下文 → 回答。增加更多 Prompt 文字不能修复正确文档从未召回的问题。

## 2. 小步优化与回归

一次改一个因素，比如只调 Top-k 或只调整 chunk size。重新跑**完整固定评测集**，不是只测原来失败的那一道题。记录目标样例变化、整体指标变化、误召回/延迟等副作用，以及是否接受改动。

自动分数是信号，不是最终真相。对典型失败、边界样例和不可回答问题进行人工抽查。若分数上升但引用变差，应按实际产品目标判断，不能只追一个数字。

一次实验可以按以下顺序执行：

1. **冻结基线：**保存问题、相关来源、当前参数和每题候选；先不要改代码。
2. **选一个可检验假设：**例如“Q2 的答案跨越分块边界，适度增大 chunk 可能让来源进入 Top-3”。
3. **只改变一个因素：**保留同一语料、embedding、查询与评估规则，只调整 chunk size。
4. **重跑所有用例：**不仅看 Q2，也检查其他题的召回、候选长度和引用。
5. **做决定：**若目标改善但其他指标退步，写明取舍；没有明确收益就恢复旧配置。

这套过程类似对照实验，能减少“改了很多东西、偶然变好”的错觉。即使用手工表格、固定候选和 mock 回答，也能练习严谨的定位；不必先接云模型或购买评估服务。

一个具体诊断例子：问题是“退款申请期限？”原文有“购买后七天内”，解析文本也完整，但当前 Top-3 全是账户设置说明。这表示生成阶段根本没见到退款资料，应先检查索引中是否有对应 chunk、查询是否查对集合、过滤条件是否排除了它。把 Prompt 改得更强烈，仍无法提供未进入上下文的那句话。

相反，如果退款片段已经出现在上下文里，而模型把“七天”答成“七个月”，才需要检查上下文组装和生成行为。改完后重跑整个固定问题集，确认没有把不可回答题也误答为有答案。将错误分类和验证结果写在一起，可以让他人复现你的判断。

可把排错记录写成一段短的“证据链”：

```text
问题：退款要在几天内申请？
原文：退货说明写七天内
解析/切块：完整，chunk=return-02
检索：Top-3 没有 return-02
结论：先查检索配置，不改生成 Prompt
```

当检索已含正确片段时，记录需要继续追踪到“Prompt 中实际拼入了哪几段”；候选列表有证据，并不能证明最终上下文也包含它。有些程序会在中间按长度截断上下文。每一步都可见，才能避免把问题归咎给模型。

## 3. 什么时候需要评估框架

评估工具可以帮助批量运行数据集、汇总分数或输出报告，但也可能带来新依赖、额外配置和对某种指标的误解。先把评估问题和人工判定规则说清楚，再决定是否需要工具。一个工具显示分数 `0.8`，如果你不知道它比较什么、样本如何标注，就不能据此判断系统是否满足需求。

## 4. 框架选型：解决问题优先

LangChain、LlamaIndex 或不用框架，都是实现选择，不等于质量保证。框架可能减少常见集成代码、提供组件接口；也可能带来依赖、版本更新和调试成本。小型本地笔记问答可以直接组合 Python 函数；当需要多种连接器、标准化组件或复杂流程时，再验证框架是否节省工作。

选型前列出具体需求：现有 Python 版本和依赖、文档加载方式、检索控制、调试可见性、团队熟悉度、升级与迁移成本。查安装版本的文档，用小原型验证关键路径，不要同时引入多个框架只为“以后可能用”。

如果团队目前只遇到一个检索错误，新增框架通常不是第一步；先用可见数据定位原因。若重复集成代码很多，再做框架原型并让它通过原有固定评测。框架价值应该体现为实际减少重复工作，或让流程更易维护，同时不牺牲权限、来源和测试可见性。决定引入时写清版本、使用范围、升级者和移除方案。

评估变更时也要考虑副作用：提升 Top-k 会把更多片段交给模型，可能增加无关上下文；增大 chunk 可能保留完整条件，也可能混入相邻主题。选择改动之前先预测“哪些测试会变化”，改完再核对预测。预测失败时先观察数据，不要事后修改假设来假装实验成功。

实验结果可以分成“支持假设、没有支持、无法判断”。例如假设调大 chunk 会找回被拆开的例外条件；若正确 chunk 进入 Top-3，算得到支持；若仍未进入，假设没有得到支持；若问题集里根本没有测试例外，则是无法判断，而非支持。写清楚这个区别，可以避免把偶然的一条成功样例当作证明。

优化前后也要检查相同的失败集合：固定语料、query、过滤权限和评测标注。若改了索引内容或删除了某份资料，就不能把差异归因到单个参数。为每轮保存小型结果表和配置，既能回退，也能让别人重复试验。调优是一项连续验证工作，不存在凭一次结果找到“永远最佳”的参数。

## 常见初学错误

- 看到答案错就立刻改 Prompt，不查看候选和原文。
- 一次改多个参数，结果无法归因。
- 只测失败题而不重跑全部固定用例，遗漏回归。
- 用单一自动分数判断最终质量。
- 认为使用更大的框架会自动增加准确度、安全性或可观测性。

## 练习（由浅入深）

1. **热身：分类故障。**若正确段落不在 Top-3，判断优先检查检索还是生成。验收：先检查解析、分块和召回；Prompt 不能凭空提供没送入上下文的证据。
2. **跟做：写一条故障记录。**从 Day 15 基线取一个失败题，填入“问题、预期来源、原文提取、chunk、候选排名、回答、最可能阶段”。验收：证据链完整，不以猜测代替观察。
3. **独立完成：一次优化实验。**只改变一个参数或一项流程，完整重跑小评测集。验收：对照表含新旧 Recall/答案和引用观察、目标案例及回归问题；决定接受或撤销并解释理由；若证据仍不足，系统输出拒答。

## 今日验收与复习

- 诊断基于流水线中实际观察到的失败位置。
- 每次修改有基线、有完整回归、有记录。
- 框架选择由需求和测试结果决定，能够选择暂时不用框架。

**复习卡片：**从“解析、分块、召回、生成”选一阶段，举例说明它会导致怎样的错误。

**小词典：**瓶颈＝限制整体效果的薄弱环节；回归＝以前能通过的情况在改动后变差；原型＝用于验证关键想法的小实现；迁移成本＝以后换实现需要投入的改动。
