# Day 12：向量数据库与 RAG 流水线

**今天的目标：**理解向量库保存什么、怎么查找，以及 RAG 如何把本地资料放进回答流程。先用小数据看清原理，再选择是否采用外部库。

## 1. 向量数据库是什么

向量数据库（vector database）是能保存向量并按相似度查找候选的存储系统。常见记录还包括原文片段、稳定文档 ID 和 metadata（元数据，例如来源、标题、租户标识）。它不是“知道答案”的数据库：它按请求规则返回候选。

常见操作：

- **写入/更新：**保存 ID、向量、文本和元数据。
- **相似度查询：**给查询向量，取 Top-k（排名前 k 个候选）。
- **过滤：**只在满足指定元数据条件的记录中查找。
- **删除/持久化：**移除记录，或将索引存到磁盘以便进程重启后继续使用。

FAISS 常用作向量相似检索库；Chroma 提供向量存储及相关管理功能。部署、过滤能力、持久化方式和 API 取决于具体版本。练习可以任选本地小库，也可以先用 Python 列表模拟记录结构；无需云服务或付费数据库。

## 2. RAG：检索后再生成

RAG 是 Retrieval-Augmented Generation 的缩写，常译为“检索增强生成”。直观来说：模型回答前，程序先去资料中找相关片段，再把片段和问题一起交给模型。检索让回答有机会依据自己的资料，但不会自动保证证据可信。

```text
离线：文件 → 提取文本 → 分块 → 向量化 → 建立索引
在线：问题 → 向量化 → 召回候选 → 权限/相关性检查 → 组装证据 → 生成回答+引用
```

“离线”指准备资料/索引时，不代表一定断网；“在线”指收到用户问题后的处理阶段。

一个小的 Python 伪实现帮助看懂组件衔接（这里用固定候选模拟检索，不是语义搜索，也没有调用模型）：

```python
documents = [
    {"id": "d1", "text": "退款需在购买后七天内申请。", "source": "退货说明.md"},
    {"id": "d2", "text": "订单可在账户页面查询。", "source": "账户帮助.md"},
]

def retrieve(question: str, k: int = 2) -> list[dict[str, str]]:
    # 教学用固定候选。真实项目应替换为关键词或向量检索。
    return documents[:k]

def make_context(question: str) -> str:
    hits = retrieve(question)
    return "\n".join(f"[{d['source']}] {d['text']}" for d in hits)

print(make_context("退款期限是多久？"))
```

输出包含两条带来源的候选。真实系统要检查实际检索结果，不能因为返回了 top-k 就把所有文字都当成证据。若资料没有依据，产品应定义拒答（明确说当前资料不足），而非猜测。

完整运行时，可以先把每条检索结果的 ID、来源和分数打印出来确认，而不是立刻调用模型。分数具体代表什么由检索方法决定，不同方法的分数不能随意比较。候选低相关、来源冲突或没有相关段落时，应进入“证据不足”分支。

给模型的 Prompt 可以要求“仅根据以下资料回答；资料未提到的内容请说明无法确认；每条事实标出来源”。这有助于明确任务，但不是安全边界，也不是正确性保证。应用还要保留原始候选记录并核验引用；模型自行编出的文件名不等于真实检索结果。

一次本地演练可用两个固定问题：`“退款期限是多少？”`（资料中有明确句子）以及 `“周日办公室是否营业？”`（资料没有记载）。先为第一个问题标出预期来源，第二个标为不可回答。验收重点不是生成很长的答案，而是第一个回答有证据、第二个不猜。若答案不对，先检查检索候选是否包含那条退款句子，再决定是检索还是生成阶段的问题。

## 3.1 从候选到上下文的手工检查

假设 Top-3 返回了 A、B、C 三条片段，但只有 A 的文字直接回答问题。组装上下文时可以只提供相关片段，或者给候选数设合理上限；不应因“数据库说它们相似”就把三条都当成事实。保留来源标签，例如 `[退货说明.md / 退款期限]`，让后续引用能够对应到确切证据。

把同一条记录从索引中删除后，再运行检索并检查候选，能验证删除操作是否真正生效。仅从 UI 隐藏它并不等于索引已删除。课程阶段可以用列表模拟这个检查，重点是理解数据流，而非安装完整数据库。

## 4. 小型索引的操作顺序

使用 Chroma、FAISS 或其他库时，先写 3 条虚构记录，不要一开始导入整批私人资料。记录 ID、文本、向量和 metadata 的对应关系；插入后立刻查询，再测试过滤、更新、删除和重新打开索引。不同库的持久化 API 与过滤能力可能不同，照当前版本文档操作，并将实际行为写进练习记录。

向量检索通常会返回 ID 和距离/相似分数，再由程序找回相应文本。不要仅保存这些分数：得分并非通用概率，`0.8` 不等于“80% 正确”。小样本实验中，把候选文本一并展示，自己判断它是否真的回答了问题。

## 5. 逐阶段排查问答

收到错误回答时，先重复相同查询并依序查看四项：①文档是否入库；②检索是否返回正确块；③过滤后该块是否还在；④组装给模型的上下文是否包含它。只有前面都正确而答案仍错误时，才优先检查生成 Prompt 或模型输出。把每一步保存为可读记录，也能让离线假模型测试完整流程。

删除也要端到端验证：记录被删后，重新查询旧内容；如果检索仍返回它，检查是否有重复 chunk、另一份旧文档或持久化数据没有刷新。数据库返回“删除成功”只说明某个调用执行了，不一定证明系统里所有副本都不存在。

## 3. 元数据过滤和安全边界

元数据过滤可以限制来源、日期或租户，但条件必须来自可信应用身份/权限，而不是模型自己生成。过滤应在片段进入 Prompt（发给模型的输入）之前执行。Prompt 中写“不得查看其他人的文件”不能代替真正过滤。

## 常见初学错误

- 把向量库误当成生成模型或事实数据库。
- 混淆“召回到了候选”和“候选能支持答案”。
- 只保存向量，不存原文、来源、ID，之后无法引用或删除。
- 忘记验证持久化、更新和删除行为。
- 把授权过滤留给模型判断，或在生成后才过滤答案。

## 练习（由浅入深）

1. **热身：辨认一条记录。**手写一条包含 `id`、`text`、`source`、`vector`、`owner` 的示例。验收：指出其中哪些是内容、哪些是检索/权限元数据。
2. **跟做：模拟 Top-2。**在列表中放 3 个有来源的记录，返回前 2 条，再按 `owner=="alice"` 筛选。验收：打印结果中最多两条，筛选后没有 Bob 的记录。明确这只是列表过滤演示，不能替代真实身份授权。
3. **独立完成：搭建微型 RAG 流程。**用 Day 10–11 的文档块作为候选，设计“资料有答案”和“资料无答案”两个问题。验收：保存问题、候选片段、来源和最终回答；答案有引用；无证据时按规则拒答；能分别检查检索和生成阶段。

## 今日验收与复习

- 重启后检查所选本地索引是否持久化；更新、删除结果明确。
- 能区分检索候选与最终回答，回答可追溯来源。
- 权限过滤在可信应用中执行，并早于模型上下文组装。

**复习卡片：**“向量库返回了结果”能证明什么、不能证明什么？

**小词典：**RAG＝先检索资料再生成回答；Top-k＝排名前 k 个候选；持久化＝进程关闭后数据仍保存；召回＝把可能相关内容找出来；权限过滤＝按当前用户可访问范围排除记录。
