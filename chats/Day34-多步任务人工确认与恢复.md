# Day 34：多步任务、人工确认与恢复

**今天的目标：**为多步 Agent 任务定义状态、审批、取消和超时恢复，防止高影响动作被误执行或重复执行。

## 为什么多步流程要显式设计

单次问答失败通常只是回答不好；多步任务可能已更改外部系统。以“草拟并发送邮件”为例，草稿、等待确认、发送中、已发送是不同状态。把它们混成一个“成功/失败”容易出现：用户尚未确认却发送；发送已经成功但响应超时，系统误以为失败又发一次。

**状态机**为每个状态规定可做的事和合法下一步；**幂等性**表示重复请求不会造成重复副作用。先把流程画清楚，再实现：

```text
起草 -> 展示收件人/主题/正文 -> 用户可修改或取消
                              -> 用户确认(绑定草稿版本) -> 发送中
                                                       -> 已发送
                                                       -> 结果未知/待核对
```

## 确认必须对应实际操作

确认要绑定“用户看见的内容”，而不只是一个模糊的“继续吗？”。系统可保存草稿版本号或摘要；用户编辑后版本改变，旧确认立即失效，需要展示新内容并重新确认。执行前再次校验用户权限、收件人和内容，确保实际参数与确认时一致。

**补偿动作**是无法简单撤销时，执行另一操作尽量恢复状态；例如已创建错误待办可删除，但已发送邮件通常无法收回。因此高影响动作更应在执行前确认，并清楚告知不可逆性。

设计确认体验时，确认界面应突出最关键、最容易出错的字段：收件人、金额、日期、目标对象和将产生的后果。长正文可折叠展示，但要提供完整预览；不能只显示模型生成的摘要，因为摘要可能漏掉用户在意的条件。用户确认后，界面应显示“已收到确认，正在执行”，而不是立即显示“已完成”。只有外部服务确认成功，状态才能进入完成。

## 超时不等于没成功

网络超时只表示客户端没及时收到结果，服务端可能已经完成。安全的恢复顺序：

1. 保存任务 ID、操作 ID 和当前状态。
2. 超时后先查询外部服务是否已完成，不能马上重复发送。
3. 若服务支持幂等键，用同一键重试，以便服务端识别重复请求。
4. 若不能确认结果，标为“结果待确认”，告知用户并安排核对，而非谎称成功或自动重复。

确认只对当前版本有效；取消应阻止尚未开始的动作，并尽力停止可中断的步骤。已进入外部系统的操作需查询状态并说明边界。

## 常见错误

- 把发送服务的连接超时当成发送动作失败；两者不是一回事。
- 把“用户确认发送邮件”实现成长期有效的通用授权。
- 用户修改正文后仍沿用旧确认。
- 把超时等同失败，无条件重试有副作用操作。
- 只保留模型对话，不记录任务 ID/状态，导致无法恢复。
- 页面显示“已取消”，但后台任务仍然会继续执行。

## 深入理解：确认到底确认了什么

让用户看到并确认的内容，应与最终实际执行的请求一致。可以把待执行操作规范化成“收件人、主题、正文、附件列表”，再计算版本号或摘要。确认记录至少有操作者、草稿版本、确认时间和一次性用途；执行时重新比对当前版本。如果任何字段改变，就撤销旧确认并展示新版本。摘要的目的只是检测内容是否改变，不应当作秘密或授权令牌。

确认文本要具体：“将邮件发给 `alex@example.test`，主题为‘周五会议’，正文如下。发送后无法保证撤回。”比“要继续吗？”更清楚。低风险编辑可允许用户修改；高风险支付或删除应展示金额、对象、账户等关键参数，并使用适合其风险的二次确认。确认还要有有效期，过期后重新展示和确认，避免数小时前的许可被意外重放。

## 状态记录怎样帮助恢复

为任务保存唯一任务号、操作号、当前状态、最后更新时间、用户/租户、草稿版本和外部服务返回的操作 ID。状态应能区分“尚未发送”“发送请求已发出，等待确认结果”“已确认发送”“需要人工核对”。用户刷新页面后可凭任务号读取授权范围内的状态；后台工作进程重启后也能继续处理，而不是重新从第一步发送。

任务状态的转换也需要服务端约束，例如 `draft -> awaiting_confirmation -> sending -> sent`。不能从 `draft` 直接跳到 `sent`；`cancelled` 状态也不能被后台悄悄覆盖成 `sending`。并发请求可能导致两个工作进程同时处理同一任务，因此数据库更新要使用锁、条件更新或其他并发控制，让同一操作只有一个执行者取得“发送中”资格。对初学原型，可先用一个明确的状态字段和单进程处理，再记录多进程下需要补充的保护。

若外部服务支持幂等键，可以把稳定的操作 ID 作为键。同一任务因为网络断开重试，服务端识别为重复请求并返回原有结果，而不是再执行一次。没有幂等支持时，超时后优先查询发送记录；查询也失败就保留“结果未知”，让用户或维护者核实。

## 取消与补偿的边界

取消不是所有动作的“撤销”。尚在队列中的任务可标记取消，工作进程开始执行前需再次读取状态；正在执行的操作要检查外部 API 是否支持取消。邮件已经发出时，后台将状态改为已发送，即便用户刚点取消，也应解释取消太晚。可以补发更正邮件，但那是新的副作用，需要再次确认，不应假装原邮件从未发出。

把恢复步骤按阶段设计：草稿失败可重新生成；等待确认可继续或取消；已送出请求但超时要查询结果；确定失败可在安全条件下重试；结果无法判定则人工处理。每条路径都需定义用户看到的文字，避免“失败”让用户重复提交。

## 失败场景桌面演练

假设邮件供应商收到请求并成功发送，但响应在网络中丢失。系统记录操作号后超时。测试时先让 Mock 供应商“写入已发送记录，再抛超时”，随后让任务恢复逻辑查询记录，预期状态应变为“已发送”且发送次数仍为 1。另一个用例模拟供应商没有接收请求，查询结果为不存在；这时才可按策略使用相同幂等键重试。测试要同时覆盖两种可能，不能只测“请求失败”一种。

## 动手练习

1. **热身：**画“起草→确认→发送”状态图。验收：包含取消、修改和不确定结果。
2. **引导：**为确认设计绑定草稿版本的流程。验收：任何收件人/主题/正文变更后，原确认无效。
3. **独立：**模拟发送超时：先假设邮件已成功，再假设未成功。验收：第一种不会重复发送；第二种只在核实或安全幂等重试后继续；用户能看到真实状态和下一步。

## 复习与词汇

- **复习：**外部服务超时不说明动作没发生；盲目重试可能重复发送，应该查询状态或用幂等键。
- **幂等键：**让重复请求被服务识别为同一操作的唯一标识；**结果未知：**请求已发出但暂时无法确认成败；**补偿：**用后续动作修正已完成操作。
