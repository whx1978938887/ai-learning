# Day 20：LangGraph 状态编排与记忆

**今天的目标：**用状态图把多步 Agent 流程画清楚，并区分会话历史与跨会话用户记忆。先掌握概念；如实际使用 LangGraph，要按安装版本查 API。

## 1. 状态图是什么

状态图（state graph）是把流程表示成节点和连接线的一种方式。它适合需要分支、循环、暂停或恢复的任务。

- **State（状态）：**流程运行到此刻保存的信息，例如问题、候选证据、当前尝试次数。
- **Node（节点）：**完成一个小步骤的函数，例如检索、核验证据、生成回答。
- **Edge（边）：**从一个节点到下一个节点的路径。
- **条件路由：**根据状态决定走哪条边，例如有证据则回答、无证据则拒答、可重试则再次检索。

例如“检索 → 核验 → 重检索/回答/拒答”。每条分支都要有终点；循环必须有最大次数或截止时间。否则流程可能无限运行。

可以先用普通 Python 表达逻辑，不依赖框架：

```python
def answer_flow(has_evidence: bool, attempts: int) -> str:
    if has_evidence:
        return "answer"
    if attempts < 2:
        return "retry_search"
    return "refuse"

print(answer_flow(False, 1))
```

输出：`retry_search`。这段代码显示分支意图；真实图框架可以帮助组织和保存执行状态，但不能自动保证判断正确。

把例子写成状态表更容易查漏：

| 当前步骤 | 条件 | 下一步 | 状态变化 |
|---|---|---|---|
| 检索 | 有可用证据 | 回答 | 保存候选来源 |
| 检索 | 无证据且尝试次数小于 2 | 再检索 | 尝试次数加一 |
| 检索 | 无证据且已达上限 | 拒答 | 记录停止原因 |
| 回答或拒答 | 已完成 | 结束 | 保存最终状态 |

要明确次数从何时开始计算。例如 `attempts=0` 表示尚未尝试，第一次检索前后应按同一约定更新；否则“最多两次”可能实际运行三次。超时也应在等待工具响应期间生效，不能只在循环开始时检查。状态表能帮助你先发现缺少终点的分支，再实现代码。

把例子写成手工状态表会更直观：

| 当前节点 | 条件 | 下一步 | 状态变化 |
|---|---|---|---|
| 检索 | 有可用证据 | 回答 | 保存候选来源 |
| 检索 | 无证据且尝试次数小于 2 | 再检索 | 尝试次数加一 |
| 检索 | 无证据且已达上限 | 拒答 | 记录停止原因 |
| 回答/拒答 | 已完成 | 结束 | 保存最终状态 |

注意次数从何时开始计数。例如 `attempts=0` 表示尚未尝试时，第一次检索前后要一致地加一；否则“最多两次”可能实际运行三次。流程图和代码都应使用同一个明确约定。超时也应在等待工具响应时生效，而不是只在循环开始检查。

## 2. Checkpoint：中途存档和恢复

Checkpoint（检查点）是运行时保存的状态快照，便于中断后恢复、排查或等待人工确认。恢复时要谨慎：只读检索通常可以重跑；发送邮件、删除文件等副作用如果重跑，可能重复发生。可使用操作 ID、执行状态记录和用户确认防止重复，但具体保证依赖存储与工具设计，不能仅靠框架名称推断。

例如，状态可以保存 `pending_action_id` 和 `action_status`。流程准备发送邮件时，先停在 `awaiting_confirmation`，将收件人、主题和正文摘要展示给用户；用户确认后再执行并记录结果。如果系统在邮件已发出、但 checkpoint 尚未更新时崩溃，恢复后不能盲目再发。应按操作 ID 核对执行结果；如果工具无法查询，就暂停交由人工复核，而不是假设系统能精确执行一次。

## 3. 短期历史与长期记忆

- **短期记忆/对话历史：**当前 session 中的最近消息，帮助理解“它”“刚才”等指代。通常需要限制长度，避免上下文无限变大。
- **长期记忆：**跨多个会话保存的用户偏好或资料。它应有明确用途、来源和保留期限，允许用户查看、更改和删除。

敏感对话不应默认永久保存。先问“这条记忆是否必要？用户是否知情/同意？谁能读取？何时过期？怎样删除？”不同会话仍要隔离，不要把 Alice 的历史放入 Bob 的上下文。

长期记忆可以设计成一条有出处、可管理的记录，而非模型看过的所有内容：

```json
{
  "user_id": "alice",
  "key": "preferred_language",
  "value": "中文",
  "source": "用户主动设置",
  "expires_at": "2026-12-31"
}
```

此例说明字段，不规定固定保存期限。写入前要有明确用途并遵循产品同意机制；读取时核对 `user_id`；删除时验证记录及相关缓存是否一并清理。敏感健康、财务信息尤其不应因“以后可能有用”就随意保存。

为了检查隔离，可在练习中构造 Alice、Bob 两份独立状态，分别保存不同问题和偏好，再交换调用顺序。预期 Alice 的流程只读到 Alice 的历史。若把状态保存在进程内字典，关闭程序后消失是正常现象；若保存到磁盘，则还要考虑用户身份校验、保留期限和删除。不要把“框架支持持久化”误当成已经设计好隐私策略。

实践中还应区分“对话状态”和“业务真相”：状态里保存 `todo_created=true` 是流程的记录，但待办存储才是确认待办是否真实存在的权威来源。恢复时不能只相信旧状态字段而重复创建，也不能仅因状态写入失败就假设外部操作没发生。涉及副作用时，要查询操作记录或停下来人工核对，并将结果同步回流程状态。

## 常见初学错误

- 把状态当成永久记忆；进程重启或 checkpoint 持久化策略可能不同。
- 画出循环却不设循环上限。
- 恢复时把已发送邮件的节点再执行一次。
- 默认把所有对话都写入长期用户画像。
- 只写删除入口，却不清理关联索引或备份策略。

## 练习（由浅入深）

1. **热身：辨认状态图元素。**为“检索—回答”流程写出 3 个状态字段、2 个节点和一个分支。验收：清楚指出哪项是数据、哪项是执行步骤。
2. **跟做：画核验流程。**画“检索 → 核验 → 重检索/回答/拒答”，设最多 2 次检索和 30 秒截止。验收：每条路径可到终点，超时和无证据均有明确出口。
3. **独立完成：设计安全记忆与恢复。**设计一条偏好记忆（来源、写入时机、过期、访问范围、查看/修改/删除）；再列 checkpoint 恢复后可重跑与需确认的节点。验收：跨 session 隔离；高影响操作不会自动重复；长期记忆有用户控制方式。

## 今日验收与复习

- 状态、节点、边和条件路由都能用自己的话解释。
- 所有分支有终点，循环有硬性上限。
- 长期记忆可查看、纠正、删除；恢复不会重复高影响动作。
