# Day 17：LlamaIndex 与 LangChain 选型

**今天的目标：**用具体需求比较 LlamaIndex、LangChain 和“暂时不用框架”，不把框架名称当成项目质量的证明。

## 1. 框架的作用和边界

LangChain 和 LlamaIndex 都提供了与模型、文档、检索或流程相关的组件，但侧重点、可用集成、API 和版本节奏会随版本变化。它们是开发工具，不是模型，也不保证答案正确、安全或更便宜。仅凭框架名字不能判断哪个“最好”。

框架可能有用的情况：项目要组合多个集成、希望使用约定好的组件接口、团队熟悉该生态。它也可能增加依赖、间接调用层和排查成本。一个小工具若只有“读取几篇 Markdown、搜索、显示引用”，普通函数可能更直观。

## 2. 用可验证的需求做比较

以“读取本地 Markdown 并带出处问答”为例，先写需求，再做比较：

| 维度 | 要问的问题 |
|---|---|
| 集成 | 需要的文件、embedding、向量存储是否支持？当前锁定版本可用吗？ |
| 检索控制 | 能否查看候选、metadata、过滤和来源映射？ |
| 调试性 | 出错时能否看到每个步骤的输入/输出？ |
| 依赖 | 安装后新增多少包，是否影响现有项目？ |
| 学习成本 | 自己和团队能否读懂关键代码？ |
| 迁移成本 | 更换库/模型时是否被绑定到特定对象或格式？ |

不要只依赖营销页或旧教程。记录精确包版本，阅读相应版本文档，并做一个本地小原型：加载一份笔记、检索一个问题、输出来源。

## 3. 版本管理与决策

锁定版本（例如在依赖文件中限定版本范围或锁文件中固定解析结果）能减少升级造成的意外差异。升级时查看变更说明并跑测试。框架 API 可能改变，之前有效的代码不代表新版本仍有效。Day 8 已讨论 LangChain 的 Runnable/LCEL 与旧教程差异；本日关注是否值得采用。

一个简单决策记录可以写：

```text
需求：本地 Markdown 问答，当前只有一种存储。
选择：先用普通 Python 函数。
原因：步骤少且容易测试；暂时没有需要框架解决的集成。
重新评估条件：需要多个文档连接器或流程控制时，做两个实现的原型对比。
```

## 4. 用同一项小任务做公平比较

不要用一个框架的“完整成品”和另一个框架的“空项目”比较。给三个候选方案同样的任务：读取两份虚构 Markdown、切分、按问题取回一条资料、打印文件标题和原文。先定义验收：

1. 正确资料能被找到；资料缺失时能显示未找到。
2. 每条命中都能回到来源文件和标题。
3. 能查看候选记录，排查为什么命中或漏掉。
4. 安装与运行在本地完成，不依赖外部账号。

然后为每种方案记录实现时间、代码中可见步骤、额外依赖、调试难度和升级文档。不能只比较代码行数：框架可能隐藏复杂度，也可能把常用流程封装得更短；关键是开发者能否理解和检查实际行为。未执行的比较就标“未知”，而非猜测。

## 5. 先做边界，再让框架承担重复工作

无论采用哪个库，都可让业务代码保留清楚的职责，例如 `load_documents()`、`retrieve(question)`、`format_answer(hits)`。框架对象不要无处不在地渗入业务规则。将来升级或替换时，可以先改适配层，再保留测试和用户行为。

这不是要求每个小项目都增加抽象层。如果只有一个很短的脚本，直接调用即可；当复制逻辑、替换实现或测试开始变困难时，再抽取公共接口。选型本身也要复查：新版本或新需求可能改变最初取舍。

做原型时，可用同一张验收表评估“可检查性”：我能否看到加载出的文本？能否看到检索的文档 ID？能否明确知道引用从哪里来？出错时能否定位到 loader、切块还是检索步骤？框架若隐藏关键中间数据，初学阶段可能不易调试；若能清晰暴露这些信息，可能提高效率。判断应来自实际小实验，而不是框架宣传。

依赖也不只是包的数量，还涉及间接依赖、安装体积、所需 Python 版本和升级频率。课程学习可先记录现状，不必为了比较而安装所有框架；先阅读当前版本文档，只对需要验证的功能建隔离原型。这样不会污染项目，也避免把旧教程 API 当成现行接口。

## 6. 一个可复用的选型决策模板

```text
项目目标：
必需能力（不满足就不能选）：
候选方案及验证版本：
实际跑过的样例和结果：
未验证/未知的项目：
依赖和调试方面的代价：
当前选择及理由：
重新评估的触发条件：
```

举例：若纯 Python 已通过“加载、按关键词查找、返回正确标题”的测试，而现阶段只有两份本地笔记，就可以先维持简单实现；当需要多种文档连接器、重试机制或统一可观测链路时，再用相同样例对比框架方案。这不是说框架只能在复杂项目使用，而是把引入成本与实际收益放在一起考虑。

还要区分“框架能提供某功能”和“项目已正确配置该功能”。比如框架提供 metadata 过滤组件，并不自动保证租户过滤条件可信。权限条件的来源和位置仍要在自己的应用测试中验证。版本升级后，也需重跑相同验收用例，而不能把旧版本的结果直接沿用。

决策时可区分“必须项”和“偏好项”。必须项例如本地运行、能返回来源、能执行权限过滤；任一候选不满足就不应被选。偏好项例如 API 风格熟悉、示例多、学习成本低，可在候选都满足必须项后比较。这样可以避免因为某个框架教程好看，就忽略它暂不支持项目关键需求。

对初学者尤其重要的是可观测性：运行一个问题后，能否看到加载了哪些文档、检索到哪些块、哪个过滤条件生效、最后给模型的文本是什么？先用虚构资料做端到端试跑，并保存输出。真正的框架比较应包括调试时你能否解释结果，而不只是“成功跑通了 hello world”。

## 常见初学错误

- 选最热门的框架，而不是最符合已知需求的方案。
- 同一个小项目同时引入两个框架，重复存储和抽象。
- 只看安装成功，不验证检索、来源和权限等关键路径。
- 忽略升级说明，照抄其他版本 API。
- 把“不用框架”误解为“永远不能使用框架”。

## 练习（由浅入深）

1. **热身：列出需求。**为本地笔记问答写 3 条必须具备的能力。验收：至少包含来源定位、检索结果可检查和本地运行。
2. **跟做：填比较表。**比较 LlamaIndex、LangChain、纯 Python 三种做法。若未实际验证某项，填“待验证”，不要凭空打分。验收：涉及当前版本的 API 时记录版本和文档来源。
3. **独立完成：做决策记录。**选一个方案并写明取舍、关键原型检查、何时重新评估。验收：别人能根据这份记录复现选择依据；“框架更先进”不能作为唯一理由。

## 今日验收与复习

- 选型理由对应当前需求，而不是流行度。
- 能说清数据从加载、检索到回答的流向。
- 能解释暂时不用框架也可能是合理的选择。

**复习卡片：**“用了某框架”能单独证明系统质量更好么？你的评估依据是什么？

**小词典：**生态＝框架可连接的工具与社区资源；依赖＝程序运行所需的额外软件包；锁定版本＝明确记录使用的软件版本；原型＝验证技术关键点的小程序。
