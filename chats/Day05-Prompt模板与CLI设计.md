# Day 5：Prompt 模板库与 CLI 设计

**今天的目标：**把一次性提示词变成可复用模板，并设计多轮聊天命令行程序。

## 知识点

Prompt 模板将稳定指令和变化输入分开，定义变量、适用范围、约束、输出、版本及回归样例。变量必须明确且不能让输入数据覆盖控制规则。CLI 则负责输入循环、退出、空输入和错误显示；模型调用应与界面代码分开。

一份可交接模板可以包含：名称/版本、用途与不适用范围、使用者、必填/可选输入、处理规则、输出契约、未知值策略、检查方式和已知限制。模板要“一份解决一个主要任务”。用 `<<< ... >>>` 或结构化消息隔开用户资料与指令；示例只覆盖有价值的边界，不要复制分叉出一堆未维护版本。

三类常见模板思路：

- **文案生成**：只用已确认的产品资料；指定受众、语气、长度和卖点数；缺信息时指出缺项，不编造认证或效果。
- **代码生成**：给出语言/框架、相关代码和接口；要求遵循现有风格、限制修改范围、补充测试；关键信息缺失时先说明缺口。
- **数据提取**：定义字段、类型、缺失值、原文顺序、输出 JSON 契约；解析/schema 失败要报告或人工处理。

模板示例需要覆盖正常、缺失、边界、歧义/冲突和含不可信指令的输入。变更规则后用固定案例回归，记录模型版本和参数；不要把客户资料或 Key 当模板示例。

可复用模板骨架：

```text
名称/版本：<任务名称> / v1
用途与不适用范围：<何时使用；哪些任务不要用>
必需输入：<变量、格式和含义>
任务与规则：<可检查动作、依据、优先级、缺失/冲突处理>
输出：<字段、类型、值域、长度、额外文字规则>
验收：<人工检查或程序校验>

待处理资料：
<<<
{input_data}
>>>
```

代码生成模板还应提供相关项目上下文、语言/版本、不可改动接口、测试要求和验证命令；信息不足时先说明缺口，不能臆造项目 API。产品文案模板只使用已确认资料，不编造认证、功能或效果。抽取模板对日期、金额和未知值给出明确类型与表示。模板库可按任务命名，记录负责人、验证日期、限制和版本变更；每次更新复跑回归样例。

消息历史不是模型自动拥有的记忆。应用需要明确保存哪些 user/assistant 消息，并注意上下文窗口有限。只保存进程内数据和持久化数据的隐私风险不同。

## 把一次性 Prompt 变成可维护的工具

模板就像一张可重复填写的表格：规则相对稳定，输入数据每次不同。比如固定问题“分析客服反馈”，每次替换 `{feedback}`。变量要有名字和含义；不要让数据本身取代任务规则。

```text
模板版本：feedback-v1
用途：从一条客服意见中提取主要问题。
输入：feedback（一段原始文本）
规则：只根据原文；无证据时输出“未知”；不猜原因。
输出：JSON 对象，包含 category、evidence、unknowns。
```

版本号的意义不是装饰：改动了分类规则、字段类型或未知值策略，旧测试结果可能不再适用，应记录版本变化并重新跑固定案例。模板库不必一开始就做复杂网页；一个按名称保存的文本文件，加上测试样例和更新日期，已经能帮助团队避免散落的复制粘贴版本。

### CLI 是程序的“文字菜单”

CLI（命令行界面）就是用户通过终端输入命令/文字、再从终端看结果的界面。把它想成前台接待：收问题、显示状态、提示退出；它不应该自己负责 HTTP、Prompt 拼接、历史裁剪和 JSON 解析所有事情。

```text
CLI 输入/显示
   ↓
会话历史管理 ──> Prompt/请求构造 ──> 模型适配器（真实服务或 Mock）
   ↑                                      ↓
   └──────────── 展示回答与明确错误 ──────┘
```

分开职责的好处是：以后换模型服务时，只改适配器；写测试时，用 Mock 模拟回答；改界面时，不影响 API 请求。`quit` 应退出，空白输入通常应提示或忽略但不发送请求，错误应告知用户可采取的动作。历史太长时要有明确策略；长期保存时还要解释存在哪里、谁能访问、怎么删除。

### 用 Mock 提前练习

Mock 是测试里可控的假对象，不会发网络请求。例如约定模型适配器有 `reply(messages)` 方法，测试时给它一个固定回答 `"测试回答"`。这样可以先验证 CLI 是否把用户输入交给适配器，以及是否显示回答，而不用准备 Key 或承担费用。

## 分层练习（由易到难）

1. **热身：**从一段提示词中标出固定规则和每次变化的变量。自测：变量列表里写出 `{feedback}` 的类型/含义，模板说明不能推测什么。
2. **跟做：**为反馈分类模板编写 3 条测试输入：正常、空文本、正负面混合。自测：每条都有预期类别/未知行为，且版本变更后能复跑。
3. **独立挑战：**写 CLI 伪代码，分别处理普通输入、空输入、`quit`、模型异常和历史过长。自测：只有普通有效输入调用模型；退出会结束循环；异常不会展示成模型成功回答。
4. **架构挑战：**把“用户输入、历史、Prompt 构造、Mock/真实模型、结果显示”画成数据流。自测：切换 Mock 不必改 CLI 主循环。

常见错误：把模板变量直接拼进指令而不标明数据边界；每个人复制一份 Prompt 导致规则不一致；用 CLI 主循环直接堆所有业务逻辑；把多轮历史误认为模型自动记得过去。

## 动手练习

1. 创建反馈分类模板，定义 `{feedback}`、输出字段、未知处理，并用正常、空文本、混合情绪三条样例做回归。
2. 画 CLI 数据流：输入 → 历史 → 模型适配器 → 输出；标记哪里处理错误、哪里保存会话。
3. 写伪代码规定 `quit`、空输入、API 错误及历史超长时的行为。
4. 把“看看这些客服意见，帮我总结主要问题”改写为一份团队可复用模板，写明用途、字段、缺失策略、冲突策略和至少 3 条测试输入。
5. 给模板加版本、验证日期、已知限制；定义什么变化需要更新版本。

## 今日验收

- 模板有用途、变量、输出格式和适用边界。
- 假模型可以替代真实调用，CLI 不依赖 API Key 才能测试。
- 说明历史保存在哪里、是否跨会话以及如何删除。
- 用户资料与模板指令边界清楚；模板测试集有固定预期检查项。
