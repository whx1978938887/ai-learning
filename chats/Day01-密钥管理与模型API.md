# Day 1：密钥管理与模型 API

**今天的目标：**安全地配置模型 API，并理解一次对话请求从程序发出到响应返回的基本结构。

## 知识点

### API Key 与密钥管理

API Key 是应用访问模型服务的秘密凭据。把它放在环境变量中读取；本地 `.env` 文件必须加入 `.gitignore`，生产环境使用部署平台的 Secret。密钥不能进入源码、日志、截图或公开仓库。若曾经提交，立即撤销并轮换；只删除文件不能消除 Git 历史里的泄漏。

本地项目可在仓库根目录放 `.env`，每行一个 `NAME=value`；读取方式取决于项目是否使用 `python-dotenv`、框架配置或 VS Code 的环境文件设置。不要把占位符写成看似真实的 Key，也不要把 `.env` 放在公开的静态资源目录。`pyproject.toml` 管理项目依赖，`.gitignore` 忽略 `.env`、虚拟环境和缓存文件。

### 一次模型对话请求

HTTP 请求由 URL、headers 和 JSON body 组成。常见消息角色有 `system`、`user`、`assistant`；服务会返回状态码、回答和用量等信息。应设置有限超时、先检查 HTTP 状态再解析响应。官方 SDK 封装传输细节，但不替应用决定错误处理和成本策略。

可把一个典型请求拆成：读取密钥 → 组装认证和内容类型 headers → 组装 model/messages/参数 JSON → 发送 POST 并设置连接/读取超时 → 检查状态码 → 解析返回文本、结束原因和 usage。SDK 与直接用 `requests` 的主要差别是封装层级；无论哪种方式，认证、超时、错误和费用仍须由应用正确处理。字段名称、模型名、URL 和消息角色支持情况以服务商文档为准。

## 从零理解：一次请求到底发生了什么

把模型 API 想成“给远方服务寄一张有格式的单子，再收回回执”。你的程序是寄件人，HTTP 是运输规则，API Key 是门禁卡，JSON 是单子的内容，模型服务是收件方。Key 只证明“你有权使用服务”，它不是 Prompt，也不应该出现在请求正文或程序输出里。

典型流程可以画成：

```text
环境变量里的 Key ──认证信息──┐
用户问题 ──messages(JSON)────┼─> HTTP POST ─> 服务端 ─> HTTP 状态码 + JSON 回答
超时设置 ────────────────────┘
```

常见 HTTP 名词：

| 名词 | 小白版解释 | 例子 |
| --- | --- | --- |
| URL | 请求要寄到哪里 | 服务商提供的 API 地址 |
| POST | 要提交一份内容，而不只是读取网页 | 发送聊天请求 |
| Header | 附在信封上的说明 | `Authorization`、`Content-Type` |
| Body | 信封里的内容 | 模型名、消息、参数组成的 JSON |
| 状态码 | 服务端处理结果的大类 | `200` 成功、`401` 未授权、`429` 太频繁 |
| 超时 | 最多等多久，超时后程序停止等待 | 连接超时和读取超时可分别设置 |

例如下面只是一个**示意请求**，实际 URL、认证格式和字段名必须查所用服务商文档：

```json
{
  "model": "服务商文档中的模型名",
  "messages": [
    {"role": "user", "content": "用一句话解释什么是 API"}
  ]
}
```

`messages` 是一段对话消息列表；`role` 标明消息来源。`user` 通常是用户，`assistant` 通常是模型，`system`（若该服务支持）通常用于应用的总体规则。角色名称和请求格式不是所有服务商都完全相同，别把示意 JSON 直接当成万能接口。

### 为什么密钥要和代码分开

代码通常会被复制、提交 Git、发到 GitHub 或分享给同学；Key 则相当于账户密码。把 Key 写成 `api_key = "..."` 会让它随着代码传播。环境变量是操作系统提供给程序读取的配置入口：代码只写变量名，真正的秘密由本机或部署平台保存。

```python
import os

api_key = os.getenv("AI_API_KEY")
if not api_key:
    raise RuntimeError(
        "缺少 AI_API_KEY。请按所用服务商说明设置环境变量；不要把 Key 写进代码。"
    )
```

这段代码只负责读取和检查，并没有连接网络。`.env` 是一种常见的本地配置文件格式，但 Python 不会自动读取它；项目必须显式使用 dotenv 工具或其他配置机制。不要因为文件名叫 `.env` 就以为自动生效。`.gitignore` 的作用是让 Git 忽略指定文件；它不负责加密，也不能从已经提交过的历史中抹除秘密。

### 收到响应后先判断，再使用

状态码应先检查。否则服务端在出错时可能返回一段错误 JSON，而你的程序却把其中的错误文字当成模型回答展示。举例来说，`401` 多半意味着 Key 或权限有问题；重复发送同一请求通常不会修好它。`429` 表示限流，不等于密码错误；稍后可能恢复，但重试要有上限。

请求失败至少分成三类来想：**服务明确拒绝**（HTTP 错误状态）、**无法确认服务是否收到请求**（网络超时/断开）、**收到了响应但内容不符合预期**（JSON/字段错误）。错误提示应告诉使用者下一步做什么，但不能打印 Key 或整个认证 Header。

## 分层练习（由易到难）

1. **热身：**不写代码，给“环境变量、API Key、HTTP 状态码、JSON Body”各写一句自己的解释。自测：能说明 Key 放在哪、用户问题放在哪。
2. **跟做：**用上面的 `os.getenv` 读取 `AI_API_KEY`。分别在变量缺失、变量有值的情况下运行；自测：缺失时出现设置提示，有值时程序只确认“已读取”，绝不打印 Key 本身。
3. **独立挑战：**做一个假的响应判断函数，让输入状态码 `200/401/429` 分别得到“解析成功/检查认证/稍后重试”的不同分支。自测：401 没有重试；错误分支没有将错误正文当作回答。
4. **安全检查：**在 `.gitignore` 加入 `.env` 后，查看 `git status`。自测：新建的本地 `.env` 不出现在待提交列表。若它过去已被提交，应撤销并轮换 Key，而不是只删除文件。

常见错误：误以为 `.gitignore` 会保护已提交文件；误以为所有 HTTP 错误都应无限重试；在调试信息中直接打印请求 headers；在没有安装/启用 dotenv 的情况下期待 `.env` 自动加载。

## 今日验收

- 能口头画出“读取配置 → 组装 HTTP 请求 → 检查状态 → 解析回答”的流程。
- 401 不自动重试；错误信息不暴露密钥；网络请求设有超时。
- 没有真实 Key 也能用 Mock 完成本日练习。
- 不把 `requests` 或官方 SDK 的差异误认为安全边界；两者都要设置超时并检查异常。
