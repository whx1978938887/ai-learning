# Day 42：岗位筛选与技能匹配

**今天的目标：**用真实公开职位判断方向是否合适，区分必需条件、加分项和可补齐缺口。

## 筛选岗位，而不是海投标题

职位名称相似，实际工作可能完全不同。读岗位描述时优先看日常职责，再看技能和条件；也考虑地区/时区、经验年限、工作方式、个人兴趣。**必需项**通常决定能否完成核心工作；**加分项**是有更好、没有也可能胜任；**可补齐项**是合理时间内可通过练习获得证据的缺口。

不要把招聘描述中的每个关键词都当硬门槛，也不要将加分项误当成已有经验。行业知识是加分时，清楚表达自己是初学者并说明学习计划，比包装成行业从业者更可信。

## 岗位匹配矩阵

| 要求 | 分类 | 我的证据 | 缺口/行动 |
|---|---|---|---|
| Python API 开发 | 必需 | FastAPI 原型和自动测试链接 | 加入身份验证练习 |
| 向量检索经验 | 加分 | 本地 RAG Demo 与评估表 | 补充失败分析 |
| 金融行业经历 | 加分/待确认 | 暂无 | 先读公开行业资料，不声称从业经验 |

把“已有技能”写成具体例子：哪个项目、你做了哪部分、如何验证。只有上过课不等于能独立负责生产系统，但课程练习可以作为学习证据。

## Worked example：是否投递

职位核心是维护 Python 服务、写测试和处理 API 集成；另要求“有云平台经验者优先”。如果你已有本地 FastAPI 项目、测试和 README，云经验是加分缺口而非必然淘汰理由。可以投递，同时安排一个无付费账号依赖的本地部署练习，并在简历中标注本地原型。若岗位核心是多年 Kubernetes 生产运维，而你完全没有相关经验，应评估是否符合级别，不要夸大经历。

## 投递跟踪

记录公司/岗位链接、发布日期、岗位版本、匹配点、材料版本、投递日期、下一步和结果。这样可以检查是否缺少某类证据，避免重复投递或忘记跟进。投递数量不是能力指标；适配度和反馈学习更有用。

## 常见错误

- 只因公司名气或技术热度投递，没有确认日常工作是否合适。
- 只看岗位标题，忽略职责与级别。
- 把“加分项”当作必需项而过早自我淘汰。
- 把必需经验缺口隐藏，或把课程 Demo 说成商业生产经验。
- 追逐所有技术热词，不形成清晰的求职方向。
- 只记录投递数，不记录材料版本、反馈和下一步。

## 深入理解：从招聘描述里找真正的工作

职位描述可能把不同信息混在一起：日常职责、必须能力、偏好条件、公司介绍和申请限制。先读职责，再读要求。重复出现、直接对应核心产出的内容往往更关键；诸如“加分”“优先”“熟悉者更佳”通常表达偏好，但仍需结合上下文判断。有的公司把清晰必需条件放在申请问答里，因此也要检查年限、地区、语言和工作许可等硬限制。

把每条要求标为三类：

- **已有证据：**你已经亲手完成并能展示，例如写过 API 测试。
- **可补齐缺口：**当前经验不足，但能在合理时间做出练习证据，例如为本地服务增加限流。
- **目前不匹配：**核心要求明显超出当前经验或受客观条件限制，例如岗位需要长期生产集群值班而你无此经验。

“不匹配”不代表永远不能申请，只是帮助你做现实选择：是否值得投递、是否需要先积累项目、是否应看更合适的级别。不要把每个缺口都变成一项课程，优先考虑最常见、最核心的要求。

## 示例：如何判断一个岗位

假设招聘岗位负责开发内部知识助手，要求 Python、API、检索评估；“有云服务经验优先”。你做过本地 Python API、使用虚构文档搭建 RAG，并有检索测试，但没部署云环境。可以把前几项列为已有证据，把云经验标为缺口/加分项，决定投递并在一周内做一个本地容器化演练。简历写“本地原型与评估”，不写“熟练云上生产部署”。面试可主动说明边界和补齐计划。

另一岗位要求独立维护数十个服务、承担生产事故值班和多年 Kubernetes 经验。如果你只有单机课程项目，这些属于核心职责缺口；可以暂缓投递，先找初级岗位或明确有带教的职位。这样不是自我否定，而是避免把时间花在明显不合级别的职位上。

## 证据匹配矩阵怎么填写

每条已有能力都附最小可验证证据：项目链接、文件/测试名、演示步骤和结果。仅有课程结业证书时，标注为“学过概念”，不要写成独立项目经验。缺口行动要具体到交付物，例如“给 FastAPI Mock 增加无效输入和越权测试”，而非“学习后端”。设定截止日期和完成标准后，才能回头判断它是否解决了缺口。

岗位信息会过时，记录查看日期和原文链接；不要凭转载摘要猜测。整理 3 个岗位时，找出共同的核心技能，比针对单一职位不断增加冷门工具更能帮助确定方向。

也可以用简单的匹配分级避免“打分看起来精确但其实主观”：每项标记“有可验证经历、只有练习、未接触”，并注明这项是否为岗位核心。若核心必需项有多个“未接触”，优先找更适合的级别或先完成作品；若只是加分项缺口，则可能边投递边补齐。最终决定要写理由，便于下周复盘实际反馈，而不是把一张矩阵当成自动筛人算法。

投递材料的版本也要对应岗位：例如 `resume-backend-v2.pdf`，记录投递时使用哪个版本。若面试邀请率低，可检查岗位级别、地区条件、简历是否清楚展示证据；若进入面试但反复卡在同一技术点，优先做针对性练习。单次无回复并不足以证明简历或能力有问题。

最后把每次申请当作一次假设检验：哪些证据让招聘者愿意进一步交流？哪些要求反复出现却没有项目支撑？记录事实，不对沉默过度解读。

## 动手练习

1. **热身：**从一则公开招聘信息中抽取三项职责与三项技能。验收：来源链接和查看日期完整。
2. **引导：**找 3 个公开职位，逐条标记必需/加分/可补齐，并填写匹配矩阵。验收：每项已有技能都有具体证据；行业经验不夸大。
3. **独立：**从中选一个目标岗位，制定一个可在一周内完成的缺口练习和投递决定。验收：说明岗位为何匹配、缺口如何补、何时复查；不以投递数量代替计划质量。

## 复习与词汇

- **复习：**查看职责中“必须负责/要求/需要”与“优先/加分/熟悉者优先”等措辞，再结合工作本身判断；不能只凭单个词机械分类。
- **证据链接：**能直接打开验证技能的代码、测试或说明；**技能缺口：**岗位要求与当前可证明能力的差距。
