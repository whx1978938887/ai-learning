# 练习模型输出 JSON 与 Markdown 表格

本练习通过几个小任务，学习如何要求模型生成可读、可检查、便于程序处理的结构化内容。重点练习两种常见格式：

- **JSON**：适合程序读取，要求语法合法、字段和数据类型明确。
- **Markdown 表格**：适合人阅读和比较，要求列名、行数和单元格内容清楚。

提示词可以提高模型遵守格式的概率，但不能代替校验。尤其是要把结果交给程序时，应实际解析 JSON 或检查表格结构。

## 一、先把格式要求写具体

只说“请用 JSON 输出”或“整理成表格”通常不够。写提示词时，至少明确以下事项：

| 要明确的内容 | JSON 示例 | Markdown 表格示例 |
| --- | --- | --- |
| 输出结构 | 一个对象，包含 `name`、`price`、`available` | 固定三列：名称、价格、是否有货 |
| 数据类型 | `price` 是数字，`available` 是布尔值 | 每个产品一行，价格使用相同单位 |
| 允许值 | 状态只能为 `available`、`sold_out`、`unknown` | 缺失信息统一填写“未提供” |
| 边界情况 | 没有价格时用 `null`，不要猜测 | 没有符合条件的记录时，在表格下说明 |
| 额外文本 | 只输出 JSON，不要代码围栏或解释 | 只输出表格，不要前言和结语 |

格式要求中也要避免自相矛盾。例如，“只输出合法 JSON”与“在 JSON 前写一句说明”不能同时满足。若确实需要多种内容，应明确分区，并说明各部分的格式。

## 二、练习 1：从文本提取为 JSON

### 任务

将下面的商品信息转成 JSON。只能使用原文中明确提供的信息；缺失信息不能推测。

```text
商品：无线键盘
价格：129 元
库存：有货
颜色：黑色、白色

商品：便携支架
价格：未说明
库存：暂时缺货
颜色：银色
```

### 先自己写提示词

请在提示词中明确：

1. 顶层结构是 JSON 数组。
2. 每个商品对象都有哪些字段，以及每个字段的数据类型。
3. 缺失的价格如何表示。
4. 库存状态只能使用哪些值。
5. 只输出 JSON，不要使用 Markdown 代码围栏或补充说明。

可以从下面的模板开始修改：

```text
任务：将商品资料转换为 JSON。

规则：
- 只提取原文明确提供的信息，不要推测。
- 输出一个 JSON 数组，每个商品对应一个对象。
- 每个对象必须包含：<列出字段及类型>
- <说明缺失值和库存状态的表示方式>
- 只输出合法 JSON，不要代码围栏或其他文字。

商品资料：
<粘贴上面的商品信息>
```

### 参考结构

完成后再对照下面的示例。这里展示的是**参考结果**，不是要把示例直接复制到提示词中的内容：

```json
[
  {
    "name": "无线键盘",
    "price": 129,
    "stock_status": "available",
    "colors": ["黑色", "白色"]
  },
  {
    "name": "便携支架",
    "price": null,
    "stock_status": "sold_out",
    "colors": ["银色"]
  }
]
```

检查价格为 `null`，而不是字符串 `"未说明"`；`129` 是数字，而不是字符串 `"129 元"`。如果你的提示词采用了另一种合理的字段设计，只要结构一致、类型明确、没有添加原文之外的事实，也可以接受。

## 三、练习 2：生成 Markdown 表格

### 任务

将下面的活动信息整理为表格。表格列为“活动、日期、地点、费用、备注”。缺失的信息写“未提供”，不要推测。

```text
读书会：11 月 8 日，线上举行，免费。需提前报名。
Python 入门分享：11 月 15 日，在 A 教室，费用 20 元。
项目交流：日期未定，地点未定，不收费。
```

### 先自己写提示词

提示词应规定：

- 必须恰好有五列，且列名和顺序固定。
- 每项活动占一行，不要合并不同活动。
- 缺失信息统一写“未提供”。
- 费用使用一致的写法；明确免费的活动写“免费”。
- 只输出 Markdown 表格，不要前言、结语或代码围栏。

### 参考结果

| 活动 | 日期 | 地点 | 费用 | 备注 |
| --- | --- | --- | --- | --- |
| 读书会 | 11 月 8 日 | 线上 | 免费 | 需提前报名 |
| Python 入门分享 | 11 月 15 日 | A 教室 | 20 元 | 未提供 |
| 项目交流 | 未提供 | 未提供 | 免费 | 未提供 |

检查表头、列顺序和行数是否符合要求。注意，“未说明”不等于“免费”；只有原文明示不收费时才填写“免费”。

## 四、练习 3：同一任务输出 JSON 和表格

有些场景既需要程序读取的数据，也需要给人阅读的摘要。此时不要只说“输出 JSON 和表格”，还要说明各自的范围和顺序，避免模型把 Markdown 说明混进 JSON。

### 任务

根据下面的会议记录，提取行动项，并制作人员统计表。

```text
会议记录：
- 林：周三前整理用户访谈问题。
- 陈：负责更新原型，截止日期未定。
- 林：周四前发送会议纪要。
- 赵：暂无分配任务。
```

### 提示词要求

自己写一个提示词，明确要求模型按以下顺序输出：

1. `行动项 JSON`：合法 JSON 数组；每项包含 `owner`、`task`、`due_date`；未知截止日期用 `null`。
2. `人员统计表`：Markdown 表格，列为“人员、行动项数量”；每人一行，没有任务的人也要出现。
3. 标题用指定标题标明两个区块；JSON 区块必须能单独复制并解析。
4. 只依据会议记录，不添加任务或截止日期。

### 参考结果

#### 行动项 JSON

```json
[
  {
    "owner": "林",
    "task": "整理用户访谈问题",
    "due_date": "周三前"
  },
  {
    "owner": "陈",
    "task": "更新原型",
    "due_date": null
  },
  {
    "owner": "林",
    "task": "发送会议纪要",
    "due_date": "周四前"
  }
]
```

#### 人员统计表

| 人员 | 行动项数量 |
| --- | ---: |
| 林 | 2 |
| 陈 | 1 |
| 赵 | 0 |

这里的 JSON 被代码围栏包围，是为了在教程中展示；如果是程序直接读取的场景，应在提示词中要求**实际输出不带代码围栏**，或使用接口提供的结构化输出功能。

## 五、让练习更有挑战

完成前三个练习后，可以加入边界情况，看看提示词是否仍能稳定工作：

- 输入中有一个商品没有颜色信息：应该用空数组 `[]`、`null`，还是省略字段？在提示词里选定一种。
- 活动日期只写“下周”：是否保留原文，还是要求转换成具体日期？如果没有当前日期，就不要要求模型猜具体日期。
- 会议记录中同一人有多项任务：统计数量时按行动项条目计数，而不是按任务中的子步骤计数。
- 输入没有任何记录：明确要求空数组、仅表头的表格，还是输出指定的“无记录”提示。
- 记录之间存在冲突：定义是保留冲突、标记待确认，还是按某条明确的优先规则处理。

这些选择没有适用于所有任务的唯一答案。重点是先定义规则，并让输出在不同输入下保持一致。

## 六、结果检查清单

### JSON 检查

- 能否被标准 JSON 解析器读取？JSON 不支持注释、尾随逗号或单引号字符串。
- 顶层类型是否正确，例如对象 `{}` 或数组 `[]`？
- 必需字段是否齐全？有没有多出未约定的字段？
- 字段值类型是否正确？例如数字没有被写成数字字符串，布尔值没有被写成 `"true"`。
- 缺失值是否按约定表示为 `null`、空数组或其他形式？
- 是否把 Markdown 代码围栏或解释文字误当成 JSON 内容？

### Markdown 表格检查

- 表头、列顺序和列数是否符合要求？
- 每一行的单元格数量是否一致？
- 每条记录是否恰好对应一行？有没有漏项、重复或合并？
- 缺失信息是否按约定标记？是否把未知值误写成推测值？
- 是否出现表格以外的前言或总结，违反了“只输出表格”的要求？

### 通用检查

- 内容是否忠于输入，而不只是格式看起来正确？
- 有歧义或信息不足时，模型是否按约定处理？
- 同一提示词多次运行时，关键字段和结构是否稳定？
- 是否用固定测试样例检查常见情况和边界情况？

## 七、关键实践

1. **给出可验证的约束**：写清字段、类型、允许值、列名、顺序和行数规则。
2. **定义未知值策略**：提前规定 `null`、空数组、“未提供”等标记的使用场景。
3. **分开内容正确性和格式正确性**：合法 JSON 仍可能包含错误事实；排版正确的表格也可能漏行。
4. **用程序校验机器输入**：JSON 可用解析器和 Schema 校验；表格可检查表头、列数和记录数。
5. **复杂输出明确分区**：同时输出多种格式时，说明每个区块的边界和额外文字规则。
6. **优先使用接口的结构化输出能力**：如果模型 API 支持 JSON Schema 或受约束生成，通常比只依赖提示词更可靠；仍需处理调用失败和业务规则校验。

## 八、给自己的小测验

不看参考答案，完成下面的提示词设计：

> 从一段反馈中提取产品名称、问题类别和用户原话。产品名称可能缺失；类别只能是“性能、价格、功能、其他”；输出必须是一个 JSON 对象，不得添加额外文字。若无法判断产品名称，使用 `null`。

提交前逐项确认：是否规定了三个字段及其类型？类别值域是否封闭？用户原话是否保持原样？是否明确禁止代码围栏和额外解释？然后用至少三条输入测试，包括一条缺少产品名称、另一条信息不足的反馈，并记录哪些规则需要补充。
