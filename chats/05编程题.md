# 编程练习题

下面的题目都围绕前四篇笔记设计。除题目特别说明外，要求使用 Python 3.11+，并且不调用真实模型 API；网络相关行为请用固定字符串、内存对象或 Mock 模拟。

建议顺序：先完成基础题，再完成综合题。每题都先写测试，再写实现。

## 一、基础题：生成器与 SSE 解析

### 题目 1：实现一个可暂停的分块生成器

实现 `chunk_text(text: str, chunk_size: int)`，返回一个生成器，把文本按指定字符数分块。

要求：

- `chunk_size` 必须是正整数，否则抛出 `ValueError`。
- 保留原始文本内容和顺序。
- 空字符串应返回空序列。
- 证明函数只创建一次，但可以通过多次 `next()` 逐块取得结果。

建议测试：普通文本、长度不能整除的文本、空字符串、中文文本和非法 `chunk_size`。

### 题目 2：解析不完整的 SSE 数据

实现 `SSEParser` 类，提供 `feed(data: bytes) -> list[dict]` 和 `close() -> list[dict]` 方法。输入是网络分块，而不是完整的 SSE 行。

输入示例：

```text
data: {"choices":[{"delta":{"content":"你"}}]}\n\n
data: {"choices":[{"delta":{"content":"好"}}]}\n\n
data: [DONE]\n\n
```

要求：

- 一个 JSON 可能被拆在多个 `feed()` 中，不能因为本次数据不完整就丢失内容。
- 支持一个网络分块中包含多条 SSE 事件。
- 忽略空行、未知字段和 `data: [DONE]`。
- `close()` 时如果还有未完成的非空数据，应抛出明确异常。
- JSON 解析失败和 UTF-8 解码失败要能被调用方区分。

进阶：支持 `event:`、`id:` 等 SSE 字段，并将一条事件的多行 `data:` 合并。

### 题目 3：从 SSE 响应中提取回答和元数据

实现 `collect_stream(events)`，从 SSE 事件中提取：

```python
{
    "content": "完整回答",
    "finish_reason": "stop",
    "usage": {"prompt_tokens": 10, "completion_tokens": 5},
}
```

要求：

- 正确拼接多个 `delta.content`。
- 兼容某些 chunk 没有 `choices` 或 `delta.content` 的情况。
- 记录最后一次出现的 `finish_reason`。
- 记录最后一个携带的 `usage`，没有 usage 时返回空字典。
- `finish_reason == "length"` 时，在结果中增加 `truncated: True`，提醒调用方内容可能不完整。

## 二、进阶题：重试策略与异常边界

### 题目 4：为重试函数补齐可测试性

改造 `retry_with_backoff`，使它支持注入 `sleep` 函数和随机数函数，例如 `sleep_fn`、`random_fn`，默认行为保持不变。

要求：

- 可重试状态码为 `429、500、502、503、504`。
- `401、403、400、422` 等不可重试异常必须立即抛出。
- `max_retries=3` 时，最多调用目标函数 4 次。
- 等待时间不能超过 `max_delay` 后再叠加抖动；请明确并测试你的设计。
- 通过假的 `sleep_fn` 记录等待时间，测试中不得真的等待。

测试场景：第一次成功、重试一次后成功、全部失败、不可重试异常、没有 `status_code` 的普通异常。

### 题目 5：解析 `Retry-After` 并选择等待时间

实现 `get_retry_delay(attempt, base_delay, max_delay, headers, random_value)`。

规则：

- 若响应头有合法的 `Retry-After` 秒数，优先使用它。
- 没有该响应头时使用 `min(base_delay * 2**attempt, max_delay)`。
- 将抖动加入最终等待时间，但最终结果不能超过 `max_delay`。
- 非法、负数或过大的 `Retry-After` 应回退到指数退避策略。

写出一张表，说明 `attempt=0、1、2` 时的基础等待时间，并用边界测试验证结果。

### 题目 6：实现一个简化熔断器

实现 `CircuitBreaker`，状态包括 `CLOSED`、`OPEN`、`HALF_OPEN`。

建议接口：

```python
breaker.call(func)
breaker.state
```

要求：

- 连续失败达到阈值后进入 `OPEN`。
- `OPEN` 状态在冷却时间内拒绝调用，不执行 `func`。
- 冷却时间结束后只允许一次探测调用，进入 `HALF_OPEN`。
- 探测成功回到 `CLOSED`，探测失败回到 `OPEN`。
- 使用注入的时钟函数测试时间流逝，不要在测试里真正等待。

## 三、应用题：参数校验与模型基准测试

### 题目 7：实现请求参数校验器

实现 `validate_chat_options(options)`，校验 `temperature`、`top_p`、`max_tokens` 和 `stream`。

要求：

- `temperature` 范围为 `0` 到 `2`。
- `top_p` 范围为 `0` 到 `1`。
- `max_tokens` 必须是正整数。
- `stream` 必须是布尔值。
- 返回一份不修改原对象的规范化配置。
- 错误信息要指出具体字段和原因，不能只返回“参数错误”。

进阶：对“同时把 temperature 和 top_p 调得很激进”的配置给出警告，但不要把警告当成异常。

### 题目 8：计算一次模型调用的指标

实现 `calculate_metrics(started, first_token_at, finished, usage, prices)`，计算：

- TTFT：首个内容 token 到达时间减请求开始时间。
- 总耗时：完成时间减请求开始时间。
- 输出速度：输出 token 数除以 `finished - first_token_at`。
- 估算成本：输入和输出 token 分别乘以每百万 token 单价。

要求：

- 没有内容 token 时，`ttft_seconds` 和输出速度返回 `None`。
- 没有 usage 时，成本按 0 计算，但保留完整的指标结构。
- 处理时间相同或时间倒序等非法输入。
- 同时兼容 `prompt_tokens/completion_tokens` 和 `input_tokens/output_tokens` 字段。

### 题目 9：离线模型基准测试汇总

给定多次实验结果，按模型和题型汇总 benchmark 报告。

输入字段至少包括：`model`、`case`、`quality_score`、`ttft_seconds`、`total_seconds`、`estimated_cost_usd`、`format_valid`。

要求：

- 每个模型每个题型计算质量平均分、格式合规率、TTFT 中位数、总耗时中位数和平均成本。
- 少于 3 次结果的组合标记为 `insufficient_samples`，不要假装它足够可靠。
- 质量不达标的模型不能进入最终推荐列表。
- 最终推荐逻辑必须显式传入质量、速度和成本权重，并校验权重之和为 1。
- 处理失败请求和缺失字段，不能让一条坏记录导致整份报告崩溃。

## 四、综合题：做一个离线流式客户端

### 题目 10：实现带降级的 ChatClient

在不发起真实网络请求的前提下，实现一个 `ChatClient`，组合前面的能力：参数校验、SSE 解析、重试和备用模型降级。

建议依赖注入：

```python
ChatClient(
    transport=mock_transport,
    sleep_fn=fake_sleep,
    clock=time.monotonic,
)
```

行为要求：

1. 校验请求参数。
2. 调用主模型并逐块解析流式响应。
3. 对 429 和 5xx 按退避策略重试。
4. 主模型重试耗尽后切换备用模型。
5. 遇到 401、403、400、422 时立即返回可读错误，不切换模型。
6. 流中断或 JSON 解析错误时，丢弃不完整结果并按约定执行降级。
7. 返回内容、使用量、完成原因、重试次数、最终模型和耗时指标。

至少编写以下端到端测试：

- 主模型一次成功并完整返回。
- 主模型 429 后重试成功。
- 主模型持续 503，备用模型成功。
- 主模型鉴权失败，不调用备用模型。
- SSE 内容跨网络分块，最终回答仍然完整。
- 最后一个 chunk 的 usage 被正确记录。
- 返回 `finish_reason=length` 时结果被标记为截断。

## 五、自我检查标准

完成后逐项检查：

- 是否所有网络相关代码都可以用 Mock 离线测试？
- 是否区分了可重试异常和不可重试异常？
- 是否测试了空输入、边界值、缺失字段和异常输入？
- 是否用中位数而不是单次结果评价延迟？
- 是否在流结束时处理了 `[DONE]`、`finish_reason` 和 `usage`？
- 是否能解释一次请求、多个响应 chunk、多个 `yield` 之间的关系？
