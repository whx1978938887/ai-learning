# Day 21：AI 办公助手整合

**今天的目标：**把检索、受控工具、状态和人工确认组合成一个可以本地演示、行为可审查的办公助手原型。

## 1. 先划定助手可以做什么

办公助手可能涉及天气、新闻、待办和邮件。不要一开始就接入真实账户；用 Fake（假工具）返回固定结果，优先验证流程。

区分“草稿”和“执行”：

- 查询天气/新闻：通常是只读。
- 写一条待办：可能改变用户数据，可撤销与否要说明。
- 准备邮件草稿：可供用户检查。
- 发送邮件：对外不可轻易撤回，应在用户确认后执行。

所有外部文字（用户输入、网页、文档和工具结果）都要当成不可信数据。工具权限仍由应用控制，而不是由模型决定。

## 2. 把流程拆成步骤和状态

示例目标：“告诉我天气，并准备一条相关待办；如果有需要联系同事，只生成邮件草稿。”

1. 读取用户问题和当前用户身份。
2. 使用假天气工具查询。
3. 根据实际工具返回值生成建议草稿。
4. 展示待办/邮件目标与具体内容。
5. 用户查看、修改、取消或确认待办。
6. 邮件默认仅保存在草稿状态；发送是单独、明确的确认步骤。
7. 显示哪些操作成功、失败、取消，是否造成副作用。

状态至少可记录 `current_step`、`user_id`、工具结果、草稿内容、确认状态和错误状态。不要把敏感信息写入不必要的日志。

## 3. 本地 Mock 示例

```python
def fake_weather(city: str) -> dict[str, str]:
    return {"city": city, "forecast": "rain"}

def make_suggestion(result: dict[str, str]) -> str:
    if result["forecast"] == "rain":
        return "带伞（待办草稿）"
    return "查看天气（待办草稿）"

weather = fake_weather("Taipei")
todo_draft = make_suggestion(weather)
email_status = "草稿；未发送"
print(weather, todo_draft, email_status)
```

预期结果包含 `forecast: rain`、待办草稿“带伞”以及邮件状态“未发送”。此例不调用网络，也不写入账户。

## 4. 把“草稿”与“真正写入”分成两个节点

可以把工具拆成 `make_todo_draft()` 和 `save_todo()`：前者只返回待展示文字，不产生副作用；后者才写入待办存储。邮件同理，`make_email_draft()` 与 `send_email()` 不应是一回事。分开后，测试能单独确认生成建议不会意外执行外部操作。

确认界面要显示具体信息，例如“将把‘带伞’新增到 Alice 的个人待办列表”，而不是只问“继续吗？”。确认后若内容、目标或收件人改变，旧确认不再适用，应重新展示并确认。用户取消后，状态变成 `cancelled`，后续节点检查此状态并立即结束。

## 5. 用状态记录部分成功

操作可能前半段成功、后半段失败。例如天气查询成功，待办草稿已显示，但生成邮件草稿失败。系统应分别标记每步，而不是只说“助手失败”或“全部完成”。可记录当前步骤、整体状态、已发生的副作用和稳定错误码。例如 `weather_lookup / failed / todo_saved=false / weather_timeout`，使用户和开发者知道没有待办被写入。

真实系统日志应避免保存不必要的邮件正文、密钥或私密信息。开发练习用固定错误码和假时间即可，不需要收集用户数据。若失败发生在写入之后，要先核对操作结果再重试，避免重复创建待办。

## 6. 错误、取消与审计

工具可能失败、超时或用户无权访问。界面应准确说明当前步骤，以及已完成的副作用。例如天气查询失败、待办草稿尚未保存、邮件未发送。审计记录（用于回顾操作的必要记录）应包括操作类型、时间、结果和确认状态，不要为了“可观测”而保存全部私密对话。

开发测试可构造三个分支：天气工具返回 `TIMEOUT`；用户身份无权创建待办；用户在邮件确认前取消。逐项检查状态和调用记录，不只检查最后一句话。超时后系统应说明没有获得天气结果；无权限时不要尝试换用户身份重跑；取消后后续节点不得继续。这样即使没有真正的天气、待办或邮件服务，也能验证完整的失败处理路径。

## 8. 先用流程表测试，不必先搭完整 Agent

将每个场景写成“起始状态 → 事件 → 预期状态”，可以直接用普通 Python 或纸笔验证：

| 起始情况 | 事件 | 预期结果 |
|---|---|---|
| 天气查询中 | 工具超时 | `failed`，不创建待办 |
| 草稿已展示 | 用户取消 | `cancelled`，写入调用为 0 |
| 草稿已展示 | 用户确认且身份有权限 | 保存一次，状态为 `completed` |
| 草稿已修改 | 沿用旧确认 | 拒绝执行，重新展示确认 |

这类表格叫场景测试：它关注的是用户可观察行为与副作用，不要求已有图形界面或模型。等每种路径都明确后，再把步骤搬到 LangGraph 或其他状态编排框架，才容易检查每个节点有没有绕过确认。

保存状态时把“建议内容”和“已执行动作”分开。例如 `todo_draft="带伞"` 不等于 `todo_saved=true`；前者只是文本，后者必须来自真实待办工具的成功返回。工具返回失败时，界面应展示草稿仍可复制，但不能说待办已保存。所有测试可使用内存数据，不必连接真实办公账户。

一个有用的验收方式是对照事件顺序：查询成功、生成草稿、用户确认、保存待办、显示完成。取消发生在确认之前时，顺序必须停止于取消；服务失败时则显示失败，不应跳到“已保存”。若错误发生在保存后但界面未收到确认，先用待办 ID 核对状态再决定是否重试，避免重复创建。

## 常见初学错误

- 让“生成邮件内容”和“发送邮件”成为一个无法中断的动作。
- 把假工具结果当成外部真实信息。
- 工具失败后仍对用户说“已经完成”。
- 忽略取消按钮，或取消后仍继续后续写操作。
- 让一个看似只读的工具拥有不必要的写权限。

## 练习（由浅入深）

1. **热身：给流程步骤标风险。**标出天气查询、待办草稿、邮件草稿、邮件发送分别是只读还是有副作用。验收：发送邮件有明确确认边界。
2. **跟做：实现本地流程。**运行 FakeWeather 示例；加入用户取消分支。验收：取消时不保存待办、不发送邮件，状态显示“已取消”。
3. **独立完成：画办公助手状态图。**覆盖天气服务失败、无权限、用户修改草稿、确认和取消。验收：每步注明输入/输出和副作用；无确认时发送函数调用次数为 0；错误信息说明当前步骤和是否已写入数据。

## 今日验收与阶段复盘

- 助手所有外发、删除等高影响操作都有可审查的用户确认。
- 用户能检查草稿、操作目标和参数。
- 失败/取消时状态如实反映副作用是否发生。
