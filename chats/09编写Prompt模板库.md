# 编写 Prompt 模板库：文案生成、代码生成与数据提取

Prompt 模板库不是一堆可以复制的长提示词，而是一组**有明确用途、输入约定、输出约定和检查方法**的可复用任务说明。好的模板既能让人快速填入新内容，也能让团队知道它适用于什么、不适用于什么。

本文从设计方法开始，逐步搭建文案生成、代码生成和数据提取三类模板，并介绍如何维护和评估模板库。

## 一、什么情况下值得做成模板

适合沉淀为模板的任务通常有以下特点：

- 任务会重复出现，例如每周写产品介绍、生成相似代码或整理客户反馈。
- 输入和输出的形状相对稳定，但每次具体内容不同。
- 任务有一组需要持续遵守的规则，例如品牌语气、技术约束或字段定义。
- 结果可以用清单、示例或程序进行检查。

如果任务只发生一次、目标还不清楚，先用普通提示词探索需求，不必急着把它包装成模板。

## 二、从需求提炼模板

写模板前先回答六个问题：

| 问题 | 要明确的内容 |
| --- | --- |
| 谁会使用？ | 使用者的经验、工作流程和需要的解释程度 |
| 什么时候使用？ | 适用任务和触发条件 |
| 输入是什么？ | 必填变量、可选变量、格式和示例 |
| 要执行什么？ | 可检查的动作、依据和处理顺序 |
| 输出是什么？ | 结构、语言、长度、取值范围和额外文字规则 |
| 怎样判断合格？ | 事实、格式、风格、功能或边界检查 |

尽量把要求写成模型可以执行和使用者可以检查的句子。例如，“写得更有吸引力”不够具体；“突出一个主要卖点，避免夸大功效，正文不超过 120 字”更容易执行。

## 三、通用模板骨架

下面的骨架适用于多数重复任务。删除无关部分，保留真正影响结果的要求即可。

```text
# 模板名称：<任务名称>

## 用途
<适用场景；说明不适用的情况>

## 输入
- <变量名>：<含义、格式、是否必填>
- <变量名>：<含义、格式、是否可选>

## 指令
你要完成的任务：<具体动作和目标>
处理规则：
- <判断或生成规则>
- <约束、禁止事项和优先级>
- <信息不足、冲突或无效输入时的处理方式>

## 输出
- 结构：<字段、段落、代码文件或其他形式>
- 格式：<Markdown、JSON、纯文本等>
- 限制：<长度、字段类型、允许值等>
- 额外文本：<允许或禁止前言、解释、代码围栏等>

## 输入内容
<在此插入变量>
```

模板中的 `<变量名>` 是需要使用者填写的占位符，不是要原样发给模型的内容。实际使用前，要把占位符替换为值，或由程序安全地绑定变量。

### 让模板更稳定的要点

1. **一份模板解决一个主要任务。** 不要把写文案、定价、SEO 分析和广告策略都塞进同一条指令。
2. **区分固定规则和每次变化的输入。** 固定规则留在模板正文，变化内容用命名清楚的变量。
3. **规定缺失信息的处理。** 可以要求标记“未提供”、提出澄清问题，或只在明确假设后继续；不要让模型自行补事实。
4. **处理互相冲突的要求。** 明确优先级，例如“事实准确优先于营销表达”“现有项目接口优先于重构建议”。
5. **给变量划定边界。** 使用清晰的开始和结束标记，减少输入内容与指令混淆。
6. **只有在规则难以描述时才加 Few-shot 示例。** 示例要覆盖正常情况和容易出错的边界情况，并确保与规则一致。

## 四、模板示例：产品文案生成

### 适用场景

根据已经确认的产品资料撰写简短介绍。它不适用于凭空编造产品参数、功效、评价或承诺。

### 可复用模板

```text
你是一名注重事实准确和可读性的产品文案编辑。

任务：根据“产品资料”撰写一段面向目标受众的产品介绍。

写作规则：
- 只使用产品资料中明确提供的信息，不要虚构性能、认证、评价或效果承诺。
- 优先突出与目标受众最相关的 1 至 2 个卖点。
- 语气：{语气，例如清晰、友好、克制}
- 正文长度：{字数范围}；不包含标题。
- 如果资料不足以支持具体卖点，简要说明缺少什么资料，不要猜测。
- 避免空泛口号、重复表达和绝对化用语。

输出：
标题：一行
正文：一个自然段
补充说明：只有在资料不足时输出；否则省略

目标受众：
<<<
{目标受众}
>>>

产品资料：
<<<
{产品资料}
>>>
```

### 使用前检查

- `{产品资料}` 是否包含可核实的产品特征？没有的话，不应期待模型编造卖点。
- `{目标受众}` 是否具体到用户需求或使用场景？
- 字数范围是否适合实际渠道？不同渠道可以建立不同模板，而不是继续增加复杂条件。
- 输出是否要经过品牌、法规或事实审核？如有要求，应纳入工作流程，不能把模型输出视为自动批准的文案。

## 五、模板示例：代码生成

### 适用场景

在已有代码库中实现范围明确的功能。若上下文不足，应让模型先指出所需信息，而不是想当然地创建接口或依赖。

### 可复用模板

```text
你是一名谨慎的 {语言或技术栈} 工程师。优先遵循现有项目的代码风格和架构。

任务：
在提供的上下文中实现以下需求：
{需求描述}

约束：
- 只修改完成任务所必需的内容；不要顺手重构无关代码。
- 复用项目已有的函数、类型、依赖和错误处理方式。
- 不要臆造未提供的 API、文件、环境变量或数据库字段。
- 保持类型安全；对无效输入和失败情况进行明确处理。
- 如果关键信息缺失或需求冲突，先列出具体问题，不要输出貌似完成的实现。

项目上下文：
<<<
{相关代码、接口、目录结构或约定}
>>>

交付要求：
1. 说明修改了什么以及原因。
2. 列出新增或修改的文件。
3. 提供或更新与改动直接相关的测试。
4. 说明运行了哪些验证；未运行的验证也要明确标注。
```

### 如何给足代码上下文

- 提供相关类型、调用方式和现有实现，而不是只给一句功能愿望。
- 说明语言和运行环境版本、框架、重要依赖及不能改变的接口。
- 把相关代码放在明确边界内；如代码很长，先给入口、关键函数和错误信息。
- 对代码生成任务，要求模型说明验证方式；生成的代码仍须在项目中检查、运行和测试。

> 如果模型不能直接读取或修改你的仓库，不要把“请检查整个项目”当作有效上下文。需要由使用者提供必要文件，或使用确实能访问仓库的工具。

## 六、模板示例：从文本提取数据

### 适用场景

从非结构化文本中提取可供程序处理的字段。抽取应忠于原文；模型不负责填补缺失事实。

### 可复用模板

```text
任务：从“待处理文本”中提取记录，并输出一个合法 JSON 数组。

抽取规则：
- 只提取原文明确出现的信息，不推断、不补全、不改写事实。
- 每条记录都必须包含以下字段：
  - name：字符串；原文未提供时为 null
  - date：字符串，格式 YYYY-MM-DD；原文没有明确日期时为 null
  - amount：数字；原文没有明确金额时为 null
- 原文存在多条记录时，每条记录输出一个对象；保持原文顺序。
- 不确定某值是否符合字段定义时使用 null，不要猜测。
- 不要把“未知”“不适用”和“原文没有提到”混为一谈；如果这些状态需要区分，请先调整字段设计。

输出要求：
- 只输出 JSON，不要代码围栏、注释或解释。
- 必须是合法 JSON，字段名和字段类型符合定义。

待处理文本：
<<<
{待处理文本}
>>>
```

### 用程序校验结果

提示词无法单独保证格式与事实正确。交给程序处理前，应至少解析 JSON、检查顶层类型、必需字段、字段类型和值域。实际项目还应根据业务规则检查日期、金额范围、重复记录和来源依据。

例如，Python 中可以先做基础解析：

```python
import json

records = json.loads(model_output)
if not isinstance(records, list):
    raise ValueError("模型输出必须是 JSON 数组")

required_fields = {"name", "date", "amount"}
for index, record in enumerate(records):
    if not isinstance(record, dict):
        raise ValueError(f"第 {index + 1} 条记录必须是对象")
    if set(record) != required_fields:
        raise ValueError(f"第 {index + 1} 条记录字段不符合约定")
    if record["name"] is not None and not isinstance(record["name"], str):
        raise ValueError(f"第 {index + 1} 条记录的 name 必须是字符串或 null")
    if record["date"] is not None and not isinstance(record["date"], str):
        raise ValueError(f"第 {index + 1} 条记录的 date 必须是字符串或 null")
    if record["amount"] is not None and (
        isinstance(record["amount"], bool)
        or not isinstance(record["amount"], (int, float))
    ):
        raise ValueError(f"第 {index + 1} 条记录的 amount 必须是数字或 null")
```

这只是基础结构校验。日期是否有效、数字是否超出业务范围等，需要按实际应用进一步验证。校验失败时应明确报错、重试或交由人工处理，不要静默地把错误结果当成成功结果。

## 七、模板库的组织与维护

模板库可以按任务类型分目录，也可以先用单个目录并采用编号和统一命名。无论选择哪种方式，每份模板都建议包含以下元信息：

```text
名称：
用途：
负责人：
版本：
最后验证日期：
输入变量：
输出约定：
已知限制：
```

维护建议：

- **命名清楚**：用“任务 + 目标”的名称，例如“提取会议行动项”，避免“万能 Prompt”。
- **标记版本**：规则、字段或输出格式有变化时更新版本，并记录可能影响的调用方。
- **保持示例有效**：规则更新后，重新检查 Few-shot 示例和对应的预期结果。
- **避免复制分叉**：多个模板共有的规则应统一维护；当用途或验收标准不同，则保留独立模板。
- **记录限制**：注明已知失败场景、模型或工具前提、是否需要人工复核。
- **管理敏感数据**：示例使用虚构或脱敏资料，不要将密钥、个人信息或客户机密写入模板库。

## 八、用小型测试集评估模板

不要只看一条漂亮的示例输出。为每个重要模板准备一组固定测试输入，至少包含：

1. **正常输入**：资料完整、格式常见。
2. **缺失信息**：某些字段或背景没有提供。
3. **边界情况**：空内容、极长输入、多个实体或特殊字符。
4. **歧义或冲突**：原文有多种解释，或输入要求与模板规则冲突。
5. **不可信内容**：待处理文本中夹带要求模型改变任务的文字；模板应把这类内容视作数据，不作为新的任务指令。

为每个案例定义检查项，例如：

| 检查项 | 例子 |
| --- | --- |
| 事实正确 | 不新增输入中没有的产品特性或数据 |
| 完整性 | 应提取的记录和必需字段没有遗漏 |
| 格式有效 | JSON 能解析，字段和类型符合约定 |
| 约束遵循 | 字数、语言、允许值和禁止事项均符合要求 |
| 失败透明 | 无法判断时标记未知或报告缺少资料，而不是猜测 |

比较模板版本时，使用相同的测试集，并记录模型、关键参数和结果。若有多个合理答案，验收标准应检查必要属性，而不只是逐字匹配一个“标准答案”。

## 九、练习：把临时 Prompt 变成模板

把下面的临时需求改写成一份可复用的模板：

> 看看这些客服意见，帮我总结主要问题。

先自行补全以下项目：

1. 使用场景和不适用范围。
2. 输入变量及多条意见的分隔方式。
3. “主要问题”的判定规则；一条意见是否可以对应多个问题？
4. 空内容、信息不足、意见冲突时如何处理。
5. 输出字段、允许值和额外文字规则。
6. 至少三个测试案例：正常、缺失和歧义输入。

完成后用同一批案例反复测试，再根据具体失败类型调整模板。每次只改动一组相关规则并重新验证，避免因一次改动过多而无法判断效果。

## 十、最终检查清单

- [ ] 模板只服务于一个清楚的主要任务。
- [ ] 适用场景、输入变量和缺失信息处理方式明确。
- [ ] 规则可执行、没有明显冲突，并写明重要优先级。
- [ ] 输出结构、类型、允许值和额外文字要求清楚。
- [ ] 示例与规则一致，并覆盖关键边界情况。
- [ ] 为输出准备了适当的格式或业务校验。
- [ ] 使用代表性测试输入检查过效果和失败处理。
- [ ] 记录版本、限制、验证日期，并避免在示例中保存敏感信息。

**核心思路：先定义任务和验收标准，再把重复部分固定为模板；模型负责生成候选结果，使用者或程序负责验证结果。**
