# 结构化 Prompt 设计：角色设定、任务描述、输出格式与 Few-shot

结构化 Prompt 不是把提示词写得很长，而是把模型完成任务所需的信息说完整、说清楚，并让结果更容易检查。本文聚焦四个常用部分：**角色设定、任务描述、输出格式和 Few-shot 示例**。

## 一、为什么要结构化

比较下面两种要求：

> 帮我看看这条用户反馈。
> 你是产品反馈分析员。请阅读下面的用户反馈，判断主要问题属于哪个类别，提取用户明确表达的情绪，并用不超过 40 字概括问题。类别只能从“性能、易用性、价格、功能、其他”中选择；信息不足时标记为“其他”，不要猜测。按指定字段输出，不要附加说明。

第一种要求没有说明任务边界、判断标准或结果形式。模型需要自行猜测，回答可能每次都不一样。第二种要求把预期行为和限制显式写出，便于稳定输出和后续评估。

结构化提示词通常回答四个问题：

| 部分 | 要回答的问题 | 主要作用 |
| --- | --- | --- |
| 角色设定 | 模型以什么专业视角工作？ | 提供视角、语气和专业边界 |
| 任务描述 | 具体要处理什么？依据什么规则？ | 明确输入、操作、范围和约束 |
| 输出格式 | 结果要长什么样？ | 让答案易读、易检查或可供程序使用 |
| Few-shot | 什么样的输入和输出算合格？ | 用示例展示抽象规则和边界情况 |

这四部分不是每次都必须全部出现。简单开放问题可以只写任务；需要一致的分类、抽取或转换时，输出格式和示例通常更有帮助。

## 二、角色设定：给视角，不是贴头衔

角色设定应帮助模型理解**关注重点、表达方式和能力边界**。只写一个身份名称通常不够：

> 你是一名资深专家。

“资深专家”没有说明在哪个领域、要优先考虑什么，也没有限定不确定时该怎么做。可以将角色写得更可执行：

> 你是一名重视可验证证据的产品反馈分析员。你负责归纳用户明确表达的问题，不推断用户没有说出的原因；遇到信息不足时标记为“无法判断”。表达简洁、中性。

角色设定的实用检查点：

- **领域**：分析员、编辑、导师、客服质检员等，选与任务相关的身份。
- **关注点**：准确性、可读性、风险、用户体验等，说明优先级。
- **边界**：不编造、不越权、不将猜测当事实；不确定时怎么处理。
- **语气**：只在语气确实影响结果时指定，例如中性、友好、简洁。

角色不能代替任务。即使设定了“你是优秀的数据分析师”，也仍需明确要分析什么、依据什么标准、交付什么结果。

## 三、任务描述：把动词、对象和规则写出来

任务描述是 Prompt 的核心。可以按以下顺序检查是否交代清楚：

1. **输入是什么**：一段反馈、一封邮件、一份文章，还是多条记录？
2. **执行什么动作**：分类、提取、比较、改写、总结，还是回答问题？尽量使用可检查的动词。
3. **依据什么标准**：类别定义、优先级、评分规则或判断条件是什么？
4. **有哪些约束**：长度、范围、语言、禁止事项、缺失信息的处理方式。
5. **怎样处理歧义**：允许澄清、标为未知，还是在明确假设后继续？

模糊描述：

> 总结这段反馈并给建议。

更具体的任务描述：

> 阅读反馈，先用一句话概括用户遇到的问题，再从给定类别中选择一个最符合的类别。只依据原文，不推断技术原因。如果原文不足以判断具体类别，选择“其他”。不要提出解决方案。

注意区分“限制”和“质量标准”：

- 限制规定不能做什么，例如“不得超过 40 字”。
- 质量标准规定怎样才算好，例如“概括需保留用户遇到的具体症状”。

规则应尽量避免互相冲突。比如同时要求“只输出一个标签”和“解释分类理由”，模型就不知道应不应该附加解释。把要求拆开，或明确哪条优先。

## 四、输出格式：定义结构和失败时的表示

“格式清晰一点”太含糊。应明确输出的字段、类型、取值范围和额外文字规则。

例如，要求模型返回一条反馈分析结果：

```text
类别：从“性能、易用性、价格、功能、其他”中选择一个
情绪：从“正向、中性、负向、无法判断”中选择一个
摘要：不超过 40 字，只概括原文明确表达的问题
```

如果结果需要被程序读取，字段约束可以更严格：

```text
只输出一个 JSON 对象，不要使用 Markdown 代码围栏或添加前后说明。
字段：
- category：字符串，只能是“性能”“易用性”“价格”“功能”“其他”之一
- sentiment：字符串，只能是“正向”“中性”“负向”“无法判断”之一
- summary：字符串，最多 40 个汉字
```

设计输出格式时逐项检查：

- 是纯文本、表格、JSON，还是固定字段清单？
- 字段是否必填？允许哪些值？
- 没有证据、输入为空或无法判断时，填什么？
- 是否允许格式以外的解释文字？
- 长度限制按字符、句子还是项目数计算？

结构化格式能减少歧义，但不能自动保证内容正确。仍要检查字段定义是否完整、规则是否冲突，以及模型是否真的遵守格式。

### 用 Python 校验模型返回的 JSON

Prompt 只能要求模型按 JSON 输出，不能单靠一句指令保证 JSON 一定合法。拿到模型返回的文本后，可以用标准库 `json` 解析，再检查字段和值域：

```python
import json

ALLOWED_CATEGORIES = {"性能", "易用性", "价格", "功能", "其他"}
ALLOWED_SENTIMENTS = {"正向", "中性", "负向", "无法判断"}


def parse_feedback_result(model_text: str) -> dict[str, str]:
    result = json.loads(model_text)
    if not isinstance(result, dict):
        raise ValueError("模型结果必须是 JSON 对象")

    expected_fields = {"category", "sentiment", "summary"}
    if set(result) != expected_fields:
        raise ValueError(f"字段必须恰好为：{sorted(expected_fields)}")
    if result["category"] not in ALLOWED_CATEGORIES:
        raise ValueError("category 不在允许的类别中")
    if result["sentiment"] not in ALLOWED_SENTIMENTS:
        raise ValueError("sentiment 不在允许的情绪值中")
    if not isinstance(result["summary"], str) or len(result["summary"]) > 40:
        raise ValueError("summary 必须是最多 40 字的字符串")

    return result


model_text = '{"category":"性能","sentiment":"负向","summary":"订单页面加载很慢"}'
print(parse_feedback_result(model_text))
```

这里的校验和 Prompt 各司其职：Prompt 引导模型生成目标结果，Python 校验则在结果不符合约定时明确报错。实际使用时，还要决定 JSON 解析失败后是重试、记录错误，还是返回人工处理。

## 五、Few-shot：通过示例展示规则

Few-shot 是在提示词中提供一个或多个“输入—理想输出”示例，让模型从具体案例中理解分类边界、输出风格或格式。它尤其适合规则难以仅靠一句定义说清楚的任务。

```text
示例 1
输入：打开订单页面要等十几秒，其他页面倒是正常。
输出：
类别：性能
情绪：负向
摘要：订单页面加载很慢

示例 2
输入：会员价格上调后，学生优惠也取消了。
输出：
类别：价格
情绪：负向
摘要：会员涨价且取消学生优惠
```

### 示例怎么选

- 选能代表真实输入的例子，不要只选最简单、最规整的句子。
- 示例之间保持同一套标签、字段和输出风格。
- 覆盖容易混淆的类别，展示区分依据。
- 加入边界情况，例如信息不足、同时提到多个问题、没有明显情绪。
- 示例必须与文字规则一致；示例冲突时，模型可能学到错误规则。
- 示例数量不是越多越好。先用少量、有区分度的示例，观察错误后再补充。

### 示例和规则各自负责什么

文字规则适合表达普遍约束，例如“只能使用给定类别”“没有证据时不要推断”。示例适合展示具体边界，例如一句话同时提到速度和价格时如何选主类别。不要只堆示例而不定义标签含义，也不要期待一个例子覆盖所有输入。

## 六、逐步组装一个完整 Prompt

目标：分析一条用户反馈，输出类别、情绪和简短摘要。

### 第一步：只写任务

> 分析下面这条用户反馈，告诉我它主要在说什么。

这句话没有类别范围、判断标准和输出结构。模型可能给出一段自由发挥的建议。

### 第二步：补充角色与边界

> 你是一名产品反馈分析员。只依据用户明确写出的内容，不推断技术原因或未表达的意图；信息不足时不要猜测。

角色提供了分析视角和证据边界，但仍没定义具体交付物。

### 第三步：明确任务和分类规则

> 阅读反馈，从“性能、易用性、价格、功能、其他”中选择一个最主要的类别；判断情绪；用一句话概括具体问题。若无法从原文判断类别或情绪，分别使用“其他”或“无法判断”。不要提出解决方案。

现在任务的动作、类别和未知情况的处理方式都比较清楚。

### 第四步：规定输出并加入示例

> 只按“类别、情绪、摘要”三个字段输出，不要添加额外说明。摘要不超过 40 字。参考示例中的字段和值域；实际分析时仍以本次输入为准。

再附上前一节的示例，并在 Prompt 末尾明确标出待分析的实际反馈。实际使用时，最好清楚分隔指令、示例和用户输入，避免模型把输入内容误当成额外指令。

### 完整结构草稿

```text
角色：你是一名重视证据的产品反馈分析员。表达简洁、中性，不推断用户没有明确写出的原因。

任务：阅读用户反馈，从“性能、易用性、价格、功能、其他”中选择一个最主要的类别；判断情绪；用一句话概括问题。无法判断情绪时使用“无法判断”；无法归入其他具体类别时使用“其他”。不要提出解决方案。

输出格式：只输出以下三个字段，不要添加额外说明。
类别：一个允许的类别
情绪：正向 / 中性 / 负向 / 无法判断
摘要：不超过 40 字

示例：
输入：打开订单页面要等十几秒，其他页面倒是正常。
输出：
类别：性能
情绪：负向
摘要：订单页面加载很慢

待分析反馈：
{{在这里填入一条反馈}}
```

这是一个可修改的草稿，不是所有任务的固定配方。任务简单时可以删除无用部分；遇到错例时，应先判断是角色、任务规则、输出约束还是示例没有讲清楚，再有针对性地修改。

### 用 Python 组织 Chat Completions messages

很多聊天模型 API 用 `messages` 数组表达对话。常见兼容格式中，`system` 放角色和稳定规则，`user` 放示例输入或当前任务，`assistant` 放示例的理想回答。Few-shot 就是把几组示例放在真实输入之前；调用模型时，这些消息作为同一次请求的上下文发送。

下面的例子只使用 Python 标准库，可以直接运行并查看将要发送的请求结构，不会发起网络请求：

```python
import json


def build_feedback_messages(feedback: str) -> list[dict[str, str]]:
    return [
        {
            "role": "system",
            "content": (
                "你是重视证据的产品反馈分析员。只依据用户明确表达的内容，"
                "不要推断原因或提出解决方案。分析反馈的主要类别、情绪和问题摘要。"
                "category 只能是性能、易用性、价格、功能、其他之一；"
                "sentiment 只能是正向、中性、负向、无法判断之一；"
                "无法判断类别时使用其他，摘要最多 40 字。"
                "只输出一个 JSON 对象，字段必须为 category、sentiment、summary，"
                "不要添加 Markdown 代码围栏或其他说明。"
            ),
        },
        {
            "role": "user",
            "content": "打开订单页面要等十几秒，其他页面倒是正常。",
        },
        {
            "role": "assistant",
            "content": json.dumps(
                {
                    "category": "性能",
                    "sentiment": "负向",
                    "summary": "订单页面加载很慢",
                },
                ensure_ascii=False,
            ),
        },
        {
            "role": "user",
            "content": "会员价格上调后，学生优惠也取消了。",
        },
        {
            "role": "assistant",
            "content": json.dumps(
                {
                    "category": "价格",
                    "sentiment": "负向",
                    "summary": "会员涨价且取消学生优惠",
                },
                ensure_ascii=False,
            ),
        },
        {
            "role": "user",
            "content": f"请分析下面的反馈：\n<feedback>\n{feedback}\n</feedback>",
        },
    ]


messages = build_feedback_messages("登录后页面一直转圈，退出重开才恢复。")
payload = {
    "model": "your-model-name",
    "messages": messages,
    "temperature": 0.2,
    "stream": False,
}
print(json.dumps(payload, ensure_ascii=False, indent=2))
```

运行后重点观察：角色和通用规则集中在 `system`；每个示例是一对 `user` / `assistant` 消息；真实输入放在最后一条 `user` 消息。不同服务商支持的消息角色可能不同，应以对应 API 文档为准。若要实际调用，把 `payload` 交给你自己的客户端即可；先确认 API 地址、模型名、密钥和依赖配置，不要把密钥写进 Prompt 或提交到代码仓库。

## 七、常见失误与调试方法

| 现象 | 常见原因 | 可以尝试的改进 |
| --- | --- | --- |
| 输出太泛、像通用建议 | 任务动作和范围不明确 | 指定输入、处理动作和需要忽略的内容 |
| 分类结果不稳定 | 标签边界模糊或类别重叠 | 定义类别含义，补充易混淆的对照示例 |
| 输出字段缺失 | 没说明字段必填或缺失值 | 列全必填字段，规定无法判断时的值 |
| 模型添加额外解释 | 没有限定格式外文本 | 明确“只输出指定内容，不附加说明” |
| 示例学歪了 | 示例与规则冲突或覆盖单一 | 检查示例一致性，补充边界和反例 |
| Prompt 越写越长但效果没变 | 重复指令多、没有针对错误诊断 | 每次只改一个因素，用固定输入比较前后结果 |

**调试原则：**固定一组输入，每轮只改一个因素，并记录旧 Prompt、新 Prompt 和输出差异。否则多个改动同时发生时，很难知道哪条规则起了作用。对生成任务可以多次运行观察稳定性；对分类和抽取任务则要另外核对正确性，不能只看格式整齐。

## 八、动手练习

文中的代码示例用于说明核心写法；下面的练习只给任务，不附完整实现答案。请自己写 Prompt 和代码，再用几条固定输入验证；如果使用模型 API，记录模型、参数和实际输出，保证修改前后可比较。

### 练习 1：把模糊要求改成结构化 Prompt

把“帮我总结一下这封邮件”改写成一个结构化 Prompt。邮件可能包含背景、多个请求和截止日期。结果需要区分事实与推测，并让读者能快速找到发件人的诉求。

要求：写出角色设定、任务描述和输出格式；说明缺少日期或请求不明确时如何处理。先不要添加 Few-shot。

### 练习 2：设计分类规则与边界示例

设计一个反馈分类 Prompt，类别为“性能、易用性、价格、功能、其他”。至少准备 6 条测试输入，其中包括：

- 一条明显属于每个主要类别的反馈。
- 一条同时提到两个类别的反馈。
- 一条没有足够信息判断类别的反馈。

自己决定多类别冲突时选主类别还是允许多标签，并把这条规则写进 Prompt。至少为两个容易混淆的情况写 Few-shot。

### 练习 3：设计信息抽取 Prompt

从一段活动通知中抽取活动名称、日期、开始时间、地点和报名方式。通知可能缺少某些信息，也可能出现多个时间或地点。

明确每个字段的值类型、缺失值表示方式，以及遇到多个候选值时的处理规则。使用至少 4 条测试输入检查边界情况。

### 练习 4：用实验比较 Few-shot 的作用

挑选一个分类或信息抽取任务，建立同一组至少 8 条测试输入。分别测试：

1. 只有任务描述。
2. 任务描述加输出格式。
3. 任务描述、输出格式和 Few-shot。

记录每种设置下的正确率、格式合规率和典型错误。分析示例是否改善了边界判断，还是只让输出更像示例。

### 练习 5：构造一条失败用例并修 Prompt

从前面练习中选出一条模型答错或格式不合规的输入。不要直接追加“请认真回答”之类的泛化指令；先判断失败来自哪里，再只修改相关部分，并重跑同一组测试输入。记录改动前后差异，确认修复没有破坏原本正确的案例。

## 九、自我检查清单

提交自己的 Prompt 前逐项检查：

- 角色是否提供了与当前任务相关的视角，而不是只有一个头衔？
- 任务的输入、动作、依据和范围是否明确？
- 限制与质量标准是否区分清楚，规则之间有没有冲突？
- 信息不足、类别冲突和字段缺失时是否有明确处理方式？
- 输出字段、允许值和额外文本规则是否可验证？
- Few-shot 是否覆盖真实边界，且与规则保持一致？
- 是否用固定测试集验证过，并检查正确性与格式，而不只是“看起来不错”？
- 每次修改是否只针对一个可解释的问题？
