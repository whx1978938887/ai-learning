# Day 35：使用 FastAPI 封装 Agent

**今天的目标：**把 Agent 作为边界清楚的 HTTP API 提供给客户端，做到输入先校验、权限先确认、错误可理解、任务可追踪。

## API 是什么

API（应用程序编程接口）是程序之间约定的请求与响应格式。FastAPI 是 Python 的 Web 框架，可以根据类型定义验证请求、生成接口文档并返回 JSON。把 Agent 包在 API 后，浏览器/脚本不必知道内部如何调用模型，但 API 必须保护内部能力。

一个请求的安全顺序通常是：接收请求 → 验证身份 → 验证字段/长度 → 检查资源权限和配额 → 调用 Agent → 映射结果/错误 → 记录不含秘密的审计信息。不能先调用昂贵模型，再发现输入超长或用户无权限。

## 请求与响应要约定

**Schema**（数据结构约束）决定字段、类型和边界。例如问题不能为空且最多 2,000 个字符。成功响应需给出可用结果或任务 ID；错误响应给出稳定类别和可采取动作，不返回密钥、堆栈、内部主机名。

Agent 任务可能比一次 HTTP 请求的等待时间长，因此将“创建任务”和“查询任务状态”分开。`POST /tasks` 校验后返回 `202 Accepted`（已接受、仍在处理）和任务 ID；`GET /tasks/{id}` 返回 queued/running/done/failed。任务 ID 本身不是授权凭证，查询时仍需确认用户拥有该任务。

## 最小的 FastAPI 输入示例

此片段展示本地请求校验，不依赖云模型：

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class TaskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/tasks", status_code=202)
def create_task(body: TaskRequest):
    # 这里只返回演示结果；真实 Agent 应在此后做身份/权限检查并排队执行。
    return {"task_id": "demo-001", "status": "queued"}
```

将这段代码保存为 `main.py` 并安装 FastAPI 与 Uvicorn 后，可用 `uvicorn main:app --reload` 在本机启动开发服务器；打开 `/docs` 能看到自动生成的交互式接口说明。`--reload` 适合开发，不应作为生产部署设置。

在真实服务中不能把固定的 `demo-001` 当作生产任务 ID；需为每次任务生成唯一标识、存储所有者和状态，并检查认证。`/health` 只给出最少健康状态，不输出环境变量。

## 错误与测试

按边界返回错误：格式/长度问题用 422；无有效身份用 401；已登录但无权操作用 403；资源不存在/不属于当前用户可用 404；依赖超时应返回可识别的暂时错误。不要把每一种失败都转成 200 “成功”，也不要把内部异常直接传给客户端。

自动测试至少覆盖正常创建、空/超长输入、未认证、无权限、Agent/工具超时，以及用户只能查询自己的任务。外部模型和工具用 Mock 可让测试快速、稳定且无需付费。

## 常见错误

- 让模型/工具在请求校验和权限检查之前运行。
- 无限等待模型响应，导致连接占用和客户端重试。
- `/health` 输出环境变量或深层异常。
- `401` 和 `403` 混为一谈，或错误响应泄露内部调用细节。
- 只测试成功路径，不测试超时、越权与重复提交。

## 深入理解：一次 HTTP 请求如何穿过 API

浏览器或程序向 URL 发送请求，HTTP 方法表达意图：`GET` 通常用于读取，`POST` 通常用于提交/创建。请求体可用 JSON 表示，响应也可返回 JSON。FastAPI 根据 Pydantic 模型将输入解析为 Python 对象，并在进入业务处理前检查类型和限制；失败时返回验证错误。这样可把边界条件放在统一入口，而不是让每个模型调用处临时猜测输入是否有效。

例如客户端提交：

```json
{"question":"这份手册的报销期限是什么？"}
```

服务端应检查 `question` 是字符串、去除空白后非空、长度未超过设定上限，然后才进行身份授权、知识库权限检查和 Agent 调用。更进一步可限制请求 JSON 大小、每分钟请求量和单用户并发数，以免有人提交超大内容或反复触发付费模型。

API 的每层负责不同事情：schema 校验回答“输入形状对不对”；身份验证回答“请求者是谁”；授权回答“这个人能访问此数据吗”；业务规则回答“这个操作在当前状态允许吗”；Agent 负责产生候选回答或工具建议；响应映射负责用稳定契约呈现结果。把这些层分开后，测试可以准确指出问题来源。

## 为什么长任务使用任务 ID

HTTP 请求通常不应无限保持连接等待模型或多个工具。若工作超过客户端和代理的超时，客户端可能重发请求，造成重复成本或重复副作用。长任务模式让 `POST /tasks` 做快速校验并登记任务，返回 `202` 和 `task_id`；后台工作器执行流程；客户端周期性调用 `GET /tasks/{id}` 获取状态。任务状态可以是 `queued`、`running`、`done`、`failed` 或 `needs_review`，并为失败提供安全的错误类别。

任务 ID 不等于访问权限。查询时仍验证身份并确认任务所有者；否则攻击者若猜到他人的 ID，可能读到答案或文档内容。对于提交重复请求，可接受客户端幂等键或先检测同一用户是否已创建相同操作；任务内部工具还要按副作用类型决定能否重试。

## 认证、授权与错误码的示例

假设 Alice 已登录但尝试查询 Bob 的任务。身份验证成功，所以不是 401；Alice 不拥有该任务，因此应拒绝访问。可返回 403，或为了不暴露资源是否存在而对不属于她的任务统一返回 404，具体策略需保持一致。无登录信息一般是 401；请求格式错误是 422；用户每分钟配额超限可用 429；内部/供应商故障应返回通用错误码并带 `request_id`。响应里不能包含环境变量、上游密钥或堆栈。

测试时不仅断言状态码，还要检查响应体没有泄露字段，并确认 Agent Mock 没有被调用。例如无权限用例的关键验收是“403/404 返回，Mock 调用次数仍为 0”。这直接证明校验发生在执行前。

## 健康检查与自动化测试如何分工

`/health` 可用于判断进程和必要依赖是否基本可用，但不宜调用昂贵模型或返回配置详情。复杂系统可区分存活检查（进程是否还在）与就绪检查（现在能否接新请求）；如果模型供应商暂时不可用，服务是否仍可处理健康探测要由运行目标决定。

测试用例可以用 FastAPI 的测试客户端发送请求，依赖注入把真实模型服务替换成 Mock。覆盖正常响应、空/超长内容、认证失败、资源越权、模型超时、供应商限流和重复提交。超时测试应检查 API 在预定时间内结束，并返回任务失败/待确认状态；不可依赖真实云 API，否则测试会花钱且受网络波动影响。

## 生产前还要补的边界

示例代码为了说明请求 schema 而省略了持久化队列、认证中间件、数据库和速率限制，不能直接当成生产服务。真实部署要使用 TLS（加密传输），将凭据存于安全的运行时秘密管理中，限制请求和输出大小，设置总超时，记录最小必要审计字段，并考虑取消、重试、并发和数据保留。开发服务器的 `--reload` 会监听文件变化，适合开发，不是生产进程管理方案。

## 动手练习

1. **热身：**为 `/tasks` 写请求字段和边界。验收：空字符串与超过 2,000 字符的输入在模型调用前被拒绝。
2. **引导：**按上面示例实现或设计 `/health`、任务创建和状态查询。验收：返回任务 ID/状态；任务属于某用户，查询时需再次授权。
3. **独立：**使用 Mock 覆盖正常完成、非法输入、401/403、依赖超时。验收：检查状态码、无秘密错误消息、重复运行稳定；任何错误路径都不泄露堆栈。

## 复习与词汇

- **复习：**先验证请求能避免无效输入消耗模型/工具资源；先授权能阻止未许可动作。
- **HTTP 状态码：**表示请求处理结果的数字；**202：**已接收、尚未完成；**超时：**等待超过设定上限；**Mock：**测试中替代真实依赖的可控假实现。
