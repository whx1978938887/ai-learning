# Day 23：文档入库生命周期

**今天的目标：**把“上传一次文档”看成有多个步骤、可能失败和重试的生命周期，规划幂等的创建、更新、删除和索引迁移。

## 1. 入库是一条流水线

入库（ingestion）是把源文件变成可搜索记录的过程，通常包括：

```text
接收文件 → 校验 → 解析 → 分块 → 向量化 → 写入索引 → 标记完成
```

每步都可能失败：类型不支持、文件损坏、向量服务不可用、写入一半成功等。为任务保存可观察状态，例如 `queued`（排队）、`processing`（处理中）、`completed`（完成）、`failed`（失败）以及失败原因。大文件处理可以放入后台队列，让用户查询进度；“异步”仅表示请求先返回、处理稍后完成，并不自动保证任务成功。

## 2. 幂等：安全地重复提交

幂等操作是相同请求重复执行后，不会不断制造额外结果。网络断线时客户端可能不知道上次是否成功，于是重试。若每次都新建文档和 chunk，索引会重复。

可以用稳定文档 ID（例如应用生成 ID）或内容摘要识别重试；每条 chunk 也要有稳定 ID。相同文件再次提交时，应用可以检测内容没变而跳过；内容变了则替换该文档的旧 chunk。内容哈希可帮助比较版本，但它不加密，也不授权访问（Day 13 有本地示例）。

## 3. 更新、删除和多步失败

数据库和向量索引不一定共享同一事务。可能出现：向量已写入，但任务状态更新失败。重试时应按稳定 ID 做覆盖/检查，并核对状态，而不是盲目追加。还应在更新/删除期间定义用户能否看到旧版本，避免混合新旧片段。

删除涉及源文件、提取文本、向量、metadata、缓存等副本。列出清理步骤和结果验证。若某一步失败，保留待清理状态并可重试；不要报告“全部删除”除非实际确认。

## 4. 一个简化的可重试处理思路

可以把每个文档任务设计成“读取当前状态—执行一个小步骤—写回结果”，每次写入都使用确定的文档/片段 ID：

```text
若状态为 received：校验并解析，保存 parse_version
若状态为 parsed：分块，每块按 doc_id + chunk_index 生成稳定 ID
若状态为 chunked：写向量；已存在同 ID 记录则更新/核对，而非追加
若所有片段核验完成：最后将状态标为 completed
```

这是帮助理解的伪流程，不是可直接用于生产的数据库事务代码。关键在于：任务状态和索引内容要能互相核对；重复运行某阶段不应生成额外副本；状态尚未确认时不要报告成功。可记录 `attempt_count`、最后错误和下一次可重试时间，避免无限快速重试。

失败重试也要区分错误类型。文件格式无效通常重试不会修好，应标记需用户更换文件；暂时不可用的存储可能稍后重试；权限错误不能靠重复运行绕过。每类错误都应有终止或人工处理条件。

## 5. Embedding 版本迁移

不同 embedding 模型的向量通常不能直接比较，切换模型/维度时要将全部或部分文档重新向量化。迁移计划可包括：记录旧索引版本、为新版本建立独立索引、用同一评测集比较、切换查询流量、保留回滚路径，并在确认后清理旧索引。具体策略取决于存储能力，不是每个系统都能原子切换。

迁移时还要对查询向量使用的模型做同样的版本标记：不能只更新文档向量，却让查询仍生成另一种空间里的向量。记录每批索引的 `embedding_model`、`dimensions` 和构建时间，用于检查兼容性。若新索引结果变差，保留旧索引可帮助恢复服务并调查差异。

## 6. 具体走一遍“写入成功但状态没更新”

假设任务处理到 chunk `doc-7-02`：向量库已写入该 ID，但应用在将任务状态设为 `completed` 前崩溃。恢复时先读任务记录，发现它仍是 `processing`；接着按稳定 chunk ID 检查索引。若该 ID 已存在，就核对文档版本和内容摘要，而不是再创建新的随机 ID。确认片段正确后继续剩余步骤，最后更新任务状态。若内容不一致，按明确的覆盖/隔离策略处理并记录错误。

这依赖稳定 ID 和可检查状态，并不代表任意系统都有事务保证。若两个后台工作者同时处理同一文档，还需使用任务锁、版本检查或其他并发控制，防止一个 worker 删除另一个刚写的新版本。学习原型可先模拟串行重试，并明确注明尚未处理并发。

## 7. 删除为什么要验证多个位置

删除请求可以有可追踪的状态，例如 `delete_requested → deleting → deleted`。某个副本清理失败时进入 `delete_pending`，而不是报告全部完成。清理成功后分别检查源文件存储、索引和缓存；重试时，对已经不存在的记录视为已清理，避免把正常情况误报成严重错误。

如果文件在删除期间又被重新上传，必须区分新版本和旧任务的重复提交。可用文档版本号区分，让旧清理任务不能误删后来建立的新版本。课程作业可在状态图或文字步骤中说明，不必搭建真实后台服务。

## 常见初学错误

- 只写“上传成功”，却不显示解析/向量化是否完成。
- 网络超时后无条件重复插入。
- 更新只追加新 chunk，不清理旧版本。
- 删除只移除原始文件，旧向量仍能召回。
- 未记录 embedding 版本，导致无法解释新旧索引差异。

## 练习（由浅入深）

1. **热身：写生命周期状态。**为上传、解析、向量化、完成、失败列出状态和一个失败原因。验收：`failed` 能说明在哪一步失败。
2. **跟做：模拟重复提交。**用内容哈希作为教学文档 ID，连续提交相同文本两次。验收：索引记录数仍为 1；文本改动后识别为新版本并替换旧片段，而不是无声追加副本。
3. **独立完成：设计可恢复流程。**模拟向量写入成功但状态更新失败，并模拟删除时某一步失败。验收：重试不重复创建、不谎报完成；可查看待处理状态；原文、chunk、向量和元数据都有删除核对项；写出 embedding 版本迁移与回滚步骤。

## 今日验收与复习

- 每个入库任务有状态和可定位失败原因。
- 重复提交和重试不会重复增加记录。
- 更新、删除和 embedding 迁移有明确流程与验证方法。

**复习卡片：**向量写入成功、任务状态更新失败时，怎样重试才能避免重复或丢数据？

**小词典：**入库＝把文档处理并写入可检索系统；异步＝任务在请求返回后继续运行；幂等＝安全重复同一操作；迁移＝从旧索引/格式切换到新版本；回滚＝出现问题后恢复旧版本。
