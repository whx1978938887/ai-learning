# Day 11：分块清洗与 Embedding

**今天的目标：**在 Day 10 的加载和切分基础上，学会克制地清洗文本，并理解 Embedding（文本向量化）为什么能支持语义检索。

## 1. 切块参数的取舍

Chunk 是供后续搜索的文本片段。太大时一个片段可能包含多个主题，召回后上下文嘈杂；太小会把定义、条件或列表拆开。Overlap（重叠）可保留相邻边界上的信息，但也会让相同文字出现在多个片段中，带来重复和存储成本。

不存在适合所有文档的唯一 chunk size。说明书、邮件、表格和代码结构不同，先用一组固定问题试切，再检查真正需要一起理解的内容是否留在同一块。每个块应保留来源、标题、页码（若有）和稳定 ID。

## 2. 清洗：去噪，不改事实

清洗（normalization/cleaning）是修正明显的格式噪声，例如去除空白行、统一换行、删除确定重复的页眉。它不是替作者改写内容。页眉可能在某种文档里其实是标题；代码中的空格可能有意义；编号、负号或标点也可能是事实的一部分。

做每条规则时问三个问题：它针对什么噪声？可能误删什么？如何记录处理结果？保留原文件或原始文本有助于排查。空文档、乱码、重复段落可分别标记，不要无声地变成“已成功索引”。

例如，把连续空格合并通常不影响普通句子，但若文本是 Python 代码，缩进可能决定程序含义；删除重复页眉有助检索，但页眉若恰好是章节标题就可能误删上下文。稳妥的练习方法是保留 `raw_text`（原始提取文本）和 `clean_text`（清洗文本），抽查前后差异，并记录所用规则。可以先打印同一段处理前后的文本，人工确认规则真的只移除了目标噪声。

## 3. Embedding：把文本表示成数字

Embedding（嵌入向量）是将一段文字变成一串数字的表示。向量可以粗略理解为文字在某个多维“意义空间”中的坐标：意思相近的文本，在训练得合适的模型生成的向量里往往较接近。这让“如何退货”和“退货流程是什么”有机会互相检索到。

典型流程：

1. 用同一个 embedding 模型把文档片段变成向量。
2. 将向量和片段文本、来源等元数据一起保存。
3. 用同一兼容模型把用户问题变成向量。
4. 比较问题向量与文档向量的相似度，取最相近的候选。

很多系统使用 cosine similarity（余弦相似度：比较两个向量方向相近程度），但具体计算和归一化方式以所用库为准。以下仅演示数字向量与相似度，**不是**真实文字的 embedding：

```python
import math

def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    if na == 0 or nb == 0:
        raise ValueError("零向量没有方向，不能计算余弦相似度")
    return dot / (na * nb)

print(round(cosine([1, 0], [0.8, 0.2]), 3))
```

输出约为 `0.970`。向量模型/维度通常必须兼容；更换模型后，新旧向量可能无法比较或意义不一致，所以通常要重算对应索引。Embedding 只帮助排序相似文本，不能证明文本真实、答案正确，也不能授予访问权限。

余弦相似度只比较方向，不理解句子真假。`[1, 0]` 和 `[0.8, 0.2]` 方向接近，因此分数高；如果输入是“ 两年保修”和“二年保修”，真正的 embedding 模型可能产生相近向量，但本页 `cosine()` 函数不会把文字变成数字。文字向量须由指定 embedding 模型计算。

还要确认向量维度兼容：长度为 3 和长度为 4 的向量通常不能逐项比较。换模型时，即使维度碰巧一样，向量所处的语义空间也可能不同。应在索引元数据记录模型名称、版本和维度，并让查询端使用兼容设置；不能把旧模型产生的向量和新模型查询向量混用后，就将排序解释为正常结果。

Embedding 也不包含访问授权。假设 Alice 和 Bob 的两段文字语义完全相同，向量搜索都可能将它们排得很靠前；是否能显示哪一段仍由应用权限规则决定。实际流程应先依据可信身份过滤候选，再把允许的文本交给模型。

## 4. 把切块和向量分成两个可观察步骤

调试时不要把“向量化”误当成“分块”。先打印分块结果，确认每个块保留标题、句子和来源；再单独确认模型为每个块返回了一个向量，且向量维度符合索引要求。这样如果命中不符合预期，就可以分辨是文本切得不对，还是模型向量/检索配置不匹配。

假设笔记写着：“会员可在购买后 30 天内退货。清仓商品不适用此规则。”如果把两句话分成两个很短的 chunk，检索“清仓商品可以退货吗？”时可能只找到第一句，导致条件丢失。合理重叠或按自然段切分能让规则和例外同时出现；验收时要查询这类边界问题，而不是只查询第一句。

切块实验可用三个具体问题检查，而不需要先有真实模型：问规则期限、问例外条件、问规则与例外如何组合。人工查看检索到的文本是否同时包含相关句子。若期限问题成功、例外问题失败，先检查例外是否进入对应 chunk；若两个事实都在块中但排序不理想，再检查检索方法。把不同故障分开，避免把所有问题都归咎于 embedding。

## 5. 用小表格检查清洗与检索预期

| 原始片段 | 处理决定 | 理由 |
|---|---|---|
| `购买后 30 天内退货` | 保留 | 关键事实 |
| `第 4 页｜公司手册` | 视文档检查 | 可能是重复页眉，也可能是唯一标题 |
| `x = a  +  b` | 保留缩进/空格规则 | 代码格式可能有意义 |
| 只有空白字符的块 | 标记 empty | 不应作为成功内容索引 |

记录决定后，再用固定问题查看返回片段是否含完整条件。向量检索给出的高相似度只是一种候选排序；若用户问的是 `E-17`，还要考虑编号的精确匹配和关键词索引。

一个容易忽略的兼容性问题是向量归一化和距离定义。某些库使用距离，数值越小可能表示越近；另一些返回相似度，数值越大可能表示越近。不要只看到数字就断言好坏，应查当前库文档并用“完全相同文本、明显不同文本”做小测试，确认结果排序符合预期。记录实际使用的距离度量，之后才有可解释的比较基线。

语义检索对同义表达有帮助，但精确编号、产品代码、罕见专名等场景，关键词检索有时更可靠；后面会比较混合检索。

## 常见初学错误

- 用一条成功查询就宣称分块参数最佳。
- 盲目清除所有重复行，误删章节标题、列表或代码缩进。
- 把随机数字当成真正的 embedding，并据此声称实现了语义搜索。
- 文档向量用模型 A、查询向量用不兼容的模型 B。
- 认为相似度高就代表事实正确或可以访问。

## 练习（由浅入深）

1. **热身：看清 overlap。**把 `ABCDEFGHIJ` 按 `size=4` 分别用 `overlap=0` 和 `overlap=1` 切分。验收：说明后一组为何有重复字符，以及这如何减少边界断裂。
2. **跟做：制定清洗规则。**对“重复页眉、全空白、疑似乱码、代码片段、重复正文”逐条写保留/移除/需人工确认，并说明依据。验收：每项有理由；代码和事实不会被泛化规则直接删除。
3. **独立完成：小型向量实验。**用同一真实 embedding 工具（若本地已有）或课程提供的 mock 向量，对同义文本、不同主题文本、编号文本排序。验收：明确注明向量来源；记录查询、排序和预期差异；没有真实模型时，只验证余弦函数并标明它不做文本 embedding。
