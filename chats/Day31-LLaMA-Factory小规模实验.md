# Day 31：LLaMA-Factory 小规模微调实验

**今天的目标：**为一次可复现的小实验做准备；没有适合的 GPU 时完成配置和数据审查即可，不必购买硬件。

## 先问“实验是否值得启动”

LLaMA-Factory 是用于管理模型微调流程的开源工具。启动训练前先确认：微调确实比 Prompt、RAG 或工具方案更适合当前目标；基座与数据许可满足用途；训练/验证文件没有混在一起；设备资源可承受。训练启动本身只是程序跑起来，不是模型变好的证据。

把实验当成可复核的科学记录：其他人要能知道用了哪个基座、哪批数据、什么软件和硬件、哪些参数、何时停止，以及如何比较结果。随机种子可减少随机初始化/抽样差异，但不同硬件和软件仍可能造成不完全一致。

## 配置逐项读懂

| 配置 | 它决定什么 | 检查问题 |
|---|---|---|
| 基座与版本 | 从哪个模型开始 | 名称/版本可固定？许可证允许用途？ |
| Tokenizer/模板 | 文本怎样变成模型输入 | 对话格式与模型是否匹配？ |
| 数据路径 | 读取哪份训练/验证数据 | 文件存在、可解析、无秘密？ |
| 微调方法/目标模块 | 更新哪些参数 | 当前模型架构支持吗？ |
| 学习率、batch、epoch | 每次更新幅度、样本批量和遍历次数 | 是否过大导致不稳定/过拟合？ |
| 输出目录/checkpoint | 保存结果和中间版本 | 空间足够？不会覆盖基座或重要实验？ |
| 日志/验证/终止条件 | 如何观测并判断停止 | 有无固定指标、资源上限、异常停止规则？ |

**batch** 是一次更新使用的样本数量；**epoch** 是完整看过训练集一次；**checkpoint** 是训练中的模型保存点。它们只是控制手段，不存在所有任务通用的“最佳数值”。先从工具文档与现有硬件建议起步，再做小范围实验。

## 安全的试跑顺序

1. 静态检查数据路径、字段、授权、切分和输出路径。
2. 用少量样本做 **smoke test**（冒烟测试：快速确认关键环节能运行），检查格式解析、Tokenizer、模型能加载、输出目录可写。
3. 只在资源允许时做短实验；观察 GPU/内存、速度、loss、日志和 checkpoint。
4. 验证 checkpoint 可读取；与基座在同一验证集比较，不把 loss 单独当成功。
5. 保存依赖版本、配置、数据版本/哈希、硬件信息、日志位置和实验结论。

抽象实验记录示例（是审查模板，不是直接可交给任意版本工具的配置文件）：

```yaml
base_model: 固定的模型名称与版本
license_checked: true
train_data: data/train.jsonl
validation_data: data/validation.jsonl
output_dir: outputs/experiment-001
seed: 17
resource_limit: 运行不超过本机可用资源
stop_if: 显存不足、loss异常或验证指标恶化
```

实际参数名会随 LLaMA-Factory 版本和模型类型变化，使用前核对对应版本文档；不要复制旧配置就假定适配。

## 深入理解：一次训练配置具体在决定什么

配置文件不是一组神秘的“最佳数字”，而是实验的可执行说明。基座模型和版本决定起点及许可边界；Tokenizer 将文字切成模型所识别的 token；对话模板规定 system/user/assistant 内容如何排列；数据路径决定训练程序实际读到哪些样本；LoRA 目标模块决定哪些层接入适配器；学习率控制每次参数更新幅度；batch 决定每次累计多少训练样本；epoch 决定完整遍历数据几次。输出目录、日志和 checkpoint 则决定结果是否可追踪与恢复。

例如对话样本可能是：

```json
{"instruction":"将这句话分类","input":"包裹何时送达？","output":"物流查询"}
```

但具体工具可能期望 `messages` 数组，也可能要求 `prompt`/`response` 字段；不同模型模板也可能不同。需要先确认数据转换器和模板约定，检查一条样本被转换后的最终 token 文本，确认问题和答案顺序正确、结束标记没有丢失。若样本被误读为空回答，训练进程仍可能启动，却是在学习错误目标。

学习率过大可能导致训练不稳定或遗忘原有能力；过小则可能在有限步数内变化很少。epoch 增加不等同质量增加，多轮重复少量数据会提高记忆样本的风险。batch 受显存限制，改变 batch 也会改变更新节奏。因而超参数要从模型与任务的文档建议开始，在验证集上观察，并记录每次只改了什么；不能把网上复制来的固定值当作所有模型通用答案。

## Smoke test 怎样逐步做

冒烟测试的目标不是证明模型已学会任务，而是尽早确认整条实验管道没有明显接线错误。建议分层：

1. **数据层：**程序能读取文件；每行可解析；必需字段非空；样本数与预期相符；随机抽查输入和答案。
2. **格式层：**样本成功转成模型模板；查看一条最终文本，确认角色标记、特殊 token 和截断位置合理。
3. **加载层：**基座和 Tokenizer 能按固定版本加载；许可、缓存位置和输出目录明确。
4. **训练层：**用少量样本、少量步数运行；日志出现有限数值；没有显存溢出或空梯度等错误。
5. **保存/读取层：**checkpoint 已生成，并能重新加载；用一条测试提示检查生成接口可工作。

若没有可用 GPU，可以完成数据检查、模板预览、配置审查和 README 记录，不要试图运行会卡死电脑的大模型。也可以用很小的公开兼容示例做配置演练，但必须区分“检查流程”与“对目标模型完成训练”。

## 可复现记录的具体例子

一份实验记录可以包含：实验 ID、日期、基座名称与确切版本、许可证检查链接、LLaMA-Factory 与依赖版本、数据集版本/校验和、训练和验证样本数、随机种子、关键参数、显卡型号/显存或“未运行”、日志位置、输出 checkpoint、停止原因和初步评测。不要把私有数据、访问令牌或带个人信息的日志放在公开仓库。

校验和是对文件内容计算的指纹，用来发现数据文件是否改变。若数据内容改了但仍沿用同一个版本名，后来就可能把两个实验错认成同一数据。记录版本和校验和能让比较更可靠，但不证明数据授权合法或样本质量良好。

## 如何决定是否继续扩大训练

先看训练能否稳定执行、验证 loss 是否出现异常，再用固定验证样本检查实际输出格式和任务表现。若格式错、答案被截断或验证指标变差，先停下来诊断，不要因为 checkpoint 已经生成就继续烧资源。训练 loss 下降只说明模型更能拟合训练数据；是否有用还需在独立测试集上与基座对照，并检查安全、延迟和成本。

## 常见错误

- 把训练集和验证集路径写反；或将测试集拿来调参。
- 模型模板与 Tokenizer 不匹配，导致看似运行但输入格式不正确。
- 忘记输出路径，覆盖旧实验；没留 checkpoint 却期待可恢复。
- 直接开长训练，等数小时才发现数据格式错。
- 无 GPU 时为了“完成课程”付费租卡或购买设备。

## 动手练习

1. **热身：**解释 epoch、batch、checkpoint、smoke test。验收：能分别举出实际作用。
2. **引导：**按配置表审查一个虚构实验。验收：基座/许可证、数据路径、验证隔离、输出目录、资源和终止条件均有明确答案。
3. **独立：**若有合适本地设备，运行只加载/解析数据的最小冒烟流程；否则提交静态审查记录。验收：可追踪软件/数据版本、种子、硬件和失败条件；没有把“开始训练”当成质量提升。

## 复习与词汇

- **复习：**长训练前做 smoke test，可尽早发现字段、路径、模板或环境错误，避免耗费时间和资源。
- **Tokenizer：**把文字切成模型处理的 token；**loss：**训练过程中衡量预测误差的数值；**复现：**凭记录重做并比较实验。
