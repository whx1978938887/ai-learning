# Day 2：流式输出、生成参数与模型比较

**今天的目标：**建立正确的流式处理模型，并设计一次公平的模型质量、速度和成本比较。

## 知识点

### 流式输出与错误处理

服务端可在一个 HTTP 响应中逐步发送内容。网络读取块、SSE 事件和模型 token 是不同边界；客户端需缓存字节、增量解码 UTF-8，再按 SSE 事件分隔符解析。传输中断或完整事件格式错误要明确报告，不能假装回答成功。

完整链路是：一次请求 → 一次响应头 → 响应体逐步到达 → 多个 SSE 事件 → 客户端累积增量 → 完整回答。Python 生成器调用时先创建迭代器，迭代到 `yield` 才执行并暂停；`yield` 次数不等于 HTTP 请求次数、网络读取次数或 token 数。HTTP/1.1 的 chunked framing、HTTP/2 帧和 SSE 事件属于不同层，HTTP 客户端一般已经处理传输 framing。

解析器应对字节做增量 UTF-8 解码，在缓冲区找到完整空行分隔后再处理 SSE；一个网络块可能包含多个事件，一个事件也可能横跨多个块。`data:` 可有多行，标准 SSE 会以换行拼接数据字段；兼容服务的 `[DONE]` 是应用协议结束标记，不等于 TCP 关闭。结束时检查残留缓冲区，完整事件 JSON 错误应暴露；UTF-8 错误和 JSON 错误最好可区分。最终 chunk 可能带 `finish_reason` 或 usage，字段以供应商协议为准。

### 错误分类、退避与参数

常见策略：

| 情况 | 一般策略 |
| --- | --- |
| 401/403、400/422 | 立即报错；重复请求通常不能修正密钥或参数 |
| 429 | 有限重试，优先尊重合法的 `Retry-After`，同时遵守总等待上限 |
| 500/502/503/504、临时连接/读取超时 | 可有限重试；检查请求是否幂等及流是否已部分输出 |
| 流中断/完整事件解析失败 | 标记结果不完整；丢弃或保留部分内容须由产品策略明确规定，不能当作成功 |

指数退避的基础延迟可写为 `min(base_delay * 2**attempt, max_delay)`；加入随机抖动以避免大量客户端同时重试。应明确最终等待也不能超过上限。`max_retries=3` 通常表示初次调用之外最多再试 3 次。把 `sleep`、随机数和时钟做依赖注入，单测用假函数而不真实等待。熔断器可用 `CLOSED → OPEN → HALF_OPEN` 状态，冷却后只放一个探测请求，避免故障期间继续冲击。

若 `Retry-After` 是合法的非负秒数，按服务端建议等待并受本地最大等待策略限制；缺失、格式错误、负数或超过允许上限时回退到指数退避。抖动后的最终等待仍须被封顶。

`temperature` 和 `top_p` 都影响采样，不宜同时大幅调整；先固定其中一个，在相同测试集做对照。不同供应商的范围、默认值和字段名有差异，不要把某个数值区间当通用法则。输出上限只约束生成部分（具体字段按接口文档），`finish_reason="length"` 代表可能截断；不要静默保存为完整回答。

### 模型比较

固定输入、Prompt、参数和评分标准；质量看正确性、证据和格式，速度区分首 token 延迟和总耗时，成本按实际 token 用量与单价计算。单次试用不能代表稳定表现。

### 用一个生活例子理解流式

非流式像等整封信寄到再打开；流式像快递员逐件送来，你边收到边读。用户因此更早看到首段内容，但整份回答仍可能失败或被截断。流式不代表模型更聪明，也不代表每个网络包里恰好有一个 token。

```text
服务端产生内容
  ↓
TCP/HTTP 传输的任意字节块（可能切在中文字符中间）
  ↓
UTF-8 增量解码成文字
  ↓
SSE 空行分隔成事件（一个块可含多个事件，一个事件也可横跨多个块）
  ↓
解析事件中的 JSON
  ↓
取出内容增量、拼接，直到结束标记
```

SSE 是一种在 HTTP 响应体里组织“服务器发来的事件”的文本格式。常见形状如下，空行表示事件结束：

```text
data: {"delta":"你好"}

data: [DONE]

```

`data:` 后的内容是事件数据；空行才是这里的事件边界。不能按“每次 `read()` 就是一条事件”来写，因为网络层可以任意切块。UTF-8 的一个汉字也可能由多个字节组成，若在字节不完整时强行独立解码，会报错或产生乱码。详见[Day 6 的解析器练习](./Day06-多轮历史流式集成与测试.md)。

### 重试不是“失败就再试”

退避的目的，是让繁忙服务先喘口气，并避免很多客户端在同一时刻同时再次请求。假设第一次失败后的基础等待是 1 秒，下一次是 2 秒，再下一次是 4 秒；实际代码会设置最大次数和等待上限，并加一点随机抖动。

| `attempt`（从 0 开始） | 公式 `min(1 × 2**attempt, 5)` | 基础等待 |
| ---: | --- | ---: |
| 0 | `min(1, 5)` | 1 秒 |
| 1 | `min(2, 5)` | 2 秒 |
| 2 | `min(4, 5)` | 4 秒 |
| 3 | `min(8, 5)` | 5 秒 |

这只是基础等待示例，不是服务商固定要求。若 API 回了 `Retry-After`，应用可以在本地策略允许的范围内尊重它。有限重试还要考虑请求是否已经部分显示给用户：若流式输出显示了半个答案，再重试并拼接第二个答案可能让用户看到重复或互相矛盾的内容。

### 模型比较要像公平考试

比较模型时，把问题、提示词、参数和评分规则当成“考卷”固定下来。若 A 模型做简单题、B 模型做难题，分数没法公平比较；若评分者知道模型名，也可能无意识偏好某一个。可隐藏模型名后按同一评分表打分。

- **TTFT（首 token 时间）**：从发出请求到第一个内容到达，影响“开始回答快不快”。
- **总耗时**：从请求开始到完整结束，表示整件事花多久。
- **正确性/质量**：按任务专用规则打分，不能由“回答很流畅”替代。
- **成本**：如果 API 提供 token 用量和单价，分别计算输入和输出成本；字符数不等于 token 数。
- **样本量**：同一个模型至少跑多个不同案例；多次测延迟时看中位数等统计量，同时保留失败记录。

例：假设单价是输入每百万 token 2 元、输出每百万 token 8 元，某次用了输入 1000、输出 200 token，则估算为 `(1000×2 + 200×8) / 1,000,000 = 0.0036 元`。数字仅用来演示公式，实际单价应查看当前服务商价格页和实际用量。

## 分层练习（由易到难）

1. **热身：**用自己的话区分网络字节块、SSE 事件、模型 token。自测：能举出“一个块含两个事件”和“一个事件跨两个块”两种情况。
2. **跟做：**手工切分上面的两条 SSE 事件，模拟解析器缓存：第一块不完整时先不输出事件；收到空行后才交付完整事件。自测：`[DONE]` 不是回答正文。
3. **独立挑战：**为 401、429、503、连接超时分别选择“立即停止、有限重试、标记不完整”等策略，并写出原因。自测：所有重试都有次数和最大等待；若已向用户展示部分回答，不会悄悄把两次回答拼成一次成功。
4. **小实验：**设计 5 个固定问题，至少一个资料不足的问题；为两个假模型填写质量、格式、TTFT、总耗时和用量表。自测：题目和评分标准一致，结论指出样本数量，不凭单次结果宣布胜负。

常见错误：按网络块切字符串当 SSE；把温度调高就认为模型知识更多；对 401 无限重试；忽略失败样本只报告最快的一次；用字符数冒充 token 用量。

## 动手练习

1. 将一条 `data: {...}\n\n` SSE 事件拆成三个字节片段，写出解析器应如何缓存并在完整事件到达后解析。
2. 判断 503、401、超时哪些可能重试；给重试次数设上限并加入抖动。
3. 设计 5 条固定测试问题（含无答案问题），建立正确性、格式、首 token 时间、总耗时、用量和估算成本表。
4. 手算 `base_delay=1`、`max_delay=5` 时 `attempt=0..3` 的基础延迟，并说明抖动后如何仍保证总延迟不超过上限。对 503 后成功和 401 立即失败分别设计假 `sleep` 测试。
5. 为抽取、摘要和创意写作选择一组参数起点；把起点写成待验证假设，不写成普遍最优值。

## 今日验收

- 能说明网络块不等于 SSE 事件，且字符编码也可能跨块。
- 错误处理区分可重试和不可重试类别，并有最大次数。
- 模型对比表先设质量门槛，再比较速度与成本。
- 质量可用固定 rubric 盲评；延迟多次重复看中位数或分位数，不用单次结果代表模型。

质量可分别检查事实正确、任务完成度、格式合规和多次输出一致性。可采用“先设质量门槛，再淘汰不达标模型，最后在达标模型中比较 P50/P95 延迟和单位请求成本”的顺序。TTFT 影响用户感知首屏，整体耗时反映任务完成时间；不同模型比较时固定题目、Prompt、参数、输出长度、网络与重复次数。

| 模型/版本 | 案例 | 质量分/错误 | 格式有效 | TTFT | 总耗时 | 输入/输出 token | 估算成本 |
| --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |  |

TTFT = 首个内容到达时间 - 请求开始时间；总耗时 = 完成时间 - 请求开始时间。输出速度可用输出 token 数除以 `完成时间 - 首 token 时间`。按“每百万 token”计价时，成本为 `(输入 token × 输入单价 + 输出 token × 输出单价) / 1,000,000`。固定模型版本、提示词、参数、用例和网络条件；每模型/用例建议多次运行并报告中位数，同时记录失败请求和 usage 缺失。

示例评分维度：推理看结论与计算是否正确；事实问答看证据与范围；结构化任务看能否解析、字段是否正确。可为每项定义 0–2 分或 0–10 分的 rubric，并在不知道模型名称时盲评。流式调用可要求服务返回 usage（若 API 支持），不要用字符数代替真实 token 数。
