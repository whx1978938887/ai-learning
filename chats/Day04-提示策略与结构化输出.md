# Day 4：Zero-shot、Few-shot 与结构化输出

**今天的目标：**比较提示策略，并让模型输出可由程序检查的数据。

## 知识点

Zero-shot 是不提供示例的基线；Few-shot 用少量示例展示规则和边界。复杂问题可拆成可检查步骤，但步骤提示不能保证正确，也不要求输出冗长的内部推理。负向要求应配替代动作，例如“无证据时输出 `unknown`”。

JSON 必须先能被解析，再校验字段、类型、枚举和业务规则。Markdown 表格适合阅读展示，不应当作可靠接口。格式正确不等于内容真实。

### 何时使用不同提示策略

- **Zero-shot**：先用清楚规则建立基线；适合常见任务、规则明确或暂时没有可靠示例的场景。
- **Few-shot**：当错误集中在分类边界、风格或格式时，加入少量真实且互相一致的示例；示例不是参数训练，不会永久改变模型。
- **步骤提示**：任务确有多条件检查时，把步骤写成可核验的动作和交付物；简单任务强行加步骤会增加成本和冗余。
- **负向约束**：把“不要瞎编”改为“只使用输入证据；信息缺失时输出 `unknown` 并列出缺少字段”。禁止项要配替代行为。

### 结构化结果校验

一个典型 JSON 任务应说清顶层类型、必填字段、字段类型、允许值、未知值、是否允许额外文字。示例：

```text
只输出一个 JSON 对象。字段：
- order_id：整数
- amount：数字，缺失为 null
- status：只能为 pending、shipped、unknown
只使用输入中明确的信息，不要代码围栏或说明文字。
```

接收端需用标准 JSON parser 解析，再做 schema 和业务校验。Markdown 表格则检查固定表头/列序、每条记录一行、缺失值约定和表格外文字。可用模型 API 的结构化输出能力时也要校验业务内容。

## 从示例策略走到可校验结果

先把 Zero-shot 当作“不给参考答案，直接按题目作答”；Few-shot 像考试前给几道带解析的例题。例题有帮助的前提是它展示了模型容易混淆的边界，而且例题正确、彼此一致。只增加例题数量，不一定会让结果变好，也会占用输入长度和费用。

例如分类任务中，“速度很慢”与“按钮颜色不好看”分别属于性能和视觉体验。若团队对“卡顿时算性能还是易用性”容易分歧，就把这个边界写成例子，再用同一组测试题比较加入例子前后的错误数。不能只挑成功案例，至少包含常见、缺资料、模糊和冲突输入。

“按步骤做”也要理解为明确、可检查的操作，不需要要求模型输出冗长的内部思考过程。例如可以要求“先找原文证据，再选择枚举类别，最后检查字段是否齐全”，接收程序只需要校验最终类别与证据字段。

### JSON 有两道不同的关

1. **语法关**：这串字符是不是合法 JSON？例如键和值要用双引号，不能有多余逗号。
2. **业务关**：字段和值是否符合本应用的规则？例如 `status` 是否属于允许集合、`order_id` 是否真的是整数。

合法 JSON 不一定是正确结果。`{"order_id": "三十七"}` 语法合法，但若接口要求整数仍不合格。反过来，模型回答“订单号 37”内容也许正确，但不是契约要求的 JSON。

离线 Python 校验示例：

```python
import json


def parse_order(text: str) -> dict[str, object]:
    try:
        value = json.loads(text)
    except json.JSONDecodeError as exc:
        raise ValueError("模型返回的内容不是合法 JSON") from exc

    if not isinstance(value, dict):
        raise ValueError("最外层必须是 JSON 对象")
    if set(value) != {"order_id", "amount", "status"}:
        raise ValueError("字段必须恰好是 order_id、amount、status")
    if type(value["order_id"]) is not int:
        raise ValueError("order_id 必须是整数")
    if value["amount"] is not None and type(value["amount"]) not in (int, float):
        raise ValueError("amount 必须是数字或 null")
    if value["status"] not in {"pending", "shipped", "unknown"}:
        raise ValueError("status 不在允许值中")
    return value
```

程序遇到错误时要决定如何处理：重试一次、请模型修正、转人工或拒绝这次结果。不能直接填上默认值，因为默认值会把“不知道”伪装成“确定”。Markdown 表格适合人读；若程序要处理数据，通常优先用 JSON 或其他定义明确的数据格式。

## 分层练习（由易到难）

1. **热身：**判断以下哪项是语法错误、哪项是业务错误：`{"status": "pending"}`；`{"order_id": "37", "amount": 120, "status": "pending"}`；`{"order_id": 37, "amount": 120, "status": "done"}`。自测：前者少字段，第二项类型错，第三项状态值越界；它们都是不同层次的问题。
2. **跟做：**运行上面的 `parse_order`，依次输入正确 JSON、少字段、错类型和非法 JSON。自测：只有正确对象通过，其余分别给出明确错误。
3. **独立挑战：**为活动信息设计一个 JSON 契约，包含标题、开始日期、地点、费用。自测：明确哪些字段可为 `null`；“未提到费用”不能擅自填 0 或“免费”。
4. **策略对照：**对 6 条相同反馈做 Zero-shot 和 Few-shot 比较。自测：记录每类错误数量，不只写“更自然”；示例要覆盖混淆边界。

常见错误：把 Few-shot 误认为模型训练；把“格式看起来像 JSON”当成通过校验；把未知误填为 0/免费；期待负面约束自动解决权限和注入问题。

## 动手练习

1. 对同一组 6 个输入比较 Zero-shot 和加入两个边界示例的 Few-shot，记录错误变化。
2. 从“订单 37，金额 120 元，待发货”抽取 JSON：`{"order_id":37,"amount":120,"status":"pending"}`。
3. 为 JSON 写校验：必填字段、整数订单号、数值金额、允许状态；测试缺字段、错误类型和未知状态。
4. 加一条输入要求模型忽略既定规则的文本，确认它作为待处理数据，而不是新的可信指令。
5. 为无记录、缺颜色、模糊日期和冲突记录分别选定 `null`、空数组或“待确认”等一致约定。

参考 JSON 结果：

```json
{"order_id": 37, "amount": 120, "status": "pending"}
```

再把活动记录转换成固定列顺序的 Markdown 表格。缺失地点统一写“未提供”，只有原文明示免费时才写“免费”；不要把“未知费用”推断成免费。每一行对应一条记录，并检查列数、列序、漏项和表格外说明文字。

## 今日验收

- 能解释示例改变了哪类错误，而不只说“感觉更好”。
- 非法 JSON 或不合规字段会被明确拒绝，不能静默填默认值。
- 内容正确性、格式合规性分开记录；固定测试集至少包含正常、缺失、歧义和冲突样例。
- `null`、空数组、“未提供”和“无法判断”不是同义词，要按字段语义选择并保持一致。
